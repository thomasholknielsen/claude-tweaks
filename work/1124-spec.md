# 1124: record-worktree without --run corrupts a different live session's run-state.json

Surface: backend

## Current State

bin/hooks.js record-worktree, when invoked without an explicit --run (including a bare --help invocation), falls through to a fallback resolver that mutates a DIFFERENT run's run-state.json -- clobbering its worktree and sessionId fields -- instead of erroring or being a true no-op.

Reproduced 3 independent times in a single /dispatch firing on 2026-08-20, across three different dispatched subagents (build,test calls for records #643, #658, #667), each time hitting a different live sibling run's run-state.json. Each occurrence was caught and hand-repaired in-run by the agent that caused it, reconstructing correct worktree/sessionId values from events.jsonl/session-transcript evidence -- but that repair is best-effort reconstruction from indirect evidence, not a guarantee, and one occurrence hit the run-state file of a genuinely live sibling session mid-run.

## Deliverables

- record-worktree invoked without --run (including --help) must either error clearly (e.g. "record-worktree requires --run") or be a true no-op -- it must never write to a run-state.json belonging to any run other than the one explicitly named.
- Cover the --help case specifically, since that is the invocation shape observed to fall through the fallback-resolver path each time.

## Acceptance Criteria

- A regression test with two concurrent run directories (each with its own run-state.json) asserts that calling record-worktree --help (or any invocation omitting --run) from a shell not clearly scoped to either leaves BOTH files byte-unchanged.
- A test asserts record-worktree invoked without --run exits non-zero with a clear message, rather than silently falling through to a fallback resolver that guesses a target run.

## Technical Approach

`resolveRunArg`-style implicit-resolution fallback in `bin/hooks.js`'s `record-worktree` handler currently treats any invocation without `--run` (including an unrecognized `--help` flag) as "no explicit run" and falls through to a "newest non-terminal run" guess. Reject any unrecognized flag (including `--help`) before reaching that fallback, and require `--run` to be present and resolvable before any write to `run-state.json` — the same unknown-flag/explicit-`--run` posture #1012's mutating-verbs hardening establishes for the other four verbs; align this fix with that work if #1012 lands first, rather than duplicating a second implementation of the guard.

### Key Files

- `plugin/bin/hooks.js` — `record-worktree` handler and its `--run` resolution path

## Gotchas

- Related: #1012 hardens the same fallback-resolver pattern across all five mutating verbs — check for overlap/sequencing before building this fix in isolation, since a shared fix there may already cover this record's scope.
- The `--help` case is the one every observed incident actually hit — any fix that only guards a bare no-flags invocation and misses `--help` (or other unrecognized flags) does not close the incident.
