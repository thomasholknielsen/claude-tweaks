# 1329: wd-ambiguous cross-worktree matches + repeated status-line contract violations during a flow build phase

Surface: backend

## Current State

During a single `/claude-tweaks:flow` run (a small, low-risk record) in worktree mode, with at least two other unrelated worktrees active concurrently, `events.jsonl` recorded two kinds of avoidable noise that didn't cause any incorrect action but represent tooling friction:

1. **`wd-ambiguous` cross-worktree matches** — four `wd-ambiguous` events fired during the test/flow steps, each matching a completely unrelated, differently-named worktree instead of the run's own assigned worktree, even though the run's own exact worktree path was a real, resolvable candidate at the time.
2. **Repeated status-line contract violations** — five `contract-violation` events fired during the build phase, each triggered by a dispatched subagent's turn opening with narrative prose ("Waiting for the batch-A task review to complete.", "Standing by for the batch-B review notification.") instead of the required Subagent Contract status token (`DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` / `BLOCKED`).

`plugin/bin/lib/hooks/pre-tool-use.js`'s E1 gate (~line 1082-1094) is the site that emits `wd-ambiguous`: for each git target, it checks `actual === assigned` first (the run's own worktree, no event) before falling through to `otherWorktrees.has(actual)` (a different live run's worktree, event fires). The report implies this exact-match check should have short-circuited before the ambiguous-match branch ever ran, but didn't.

`plugin/bin/lib/hooks/subagent-stop.js`'s E3 check (~line 43-52) is the site that emits `contract-violation`: it reads the transcript's true last assistant text and tests it against `STATUS_RE` (`^(DONE|DONE_WITH_CONCERNS|NEEDS_CONTEXT|BLOCKED)\b`). The file's own header comment already documents this hook as best-effort and prone to a different known false-positive (a dispatch template with its own valid first-line contract, e.g. `superpowers:subagent-driven-development`'s task-reviewer). This report is explicitly **not** that case, and not issue #750's case either (superpowers' bolded `**Status:** DONE` template) — it's a genuine prose-only reply with no status token present at all, surfacing during `/flow`'s build phase where subagents are dispatched (candidate site: `plugin/skills/dispatch/SKILL.md` Step 5's per-file-overlap-group Task dispatch, or `/build`'s own dispatch — not yet confirmed).

## Deliverables

1. Root-cause why `wd-ambiguous` matched an unrelated worktree instead of short-circuiting on the exact-match branch when the run's own assigned worktree was a valid, resolvable candidate — fix the resolution/comparison so a genuine exact match is never reported as ambiguous.
2. Root-cause which build-phase dispatch site(s) produce subagent replies opening with narrative prose instead of the required status token, and either fix the dispatch prompt(s) to enforce the status-line requirement on every reply the hook can observe, or narrow `subagent-stop.js`'s check so it doesn't misfire against a reply shape that isn't actually a contract violation.

## Acceptance Criteria

- A regression test (or reproduction) demonstrates `wd-ambiguous` does not fire when the run's own assigned worktree realpath is present among the candidate worktrees for a git target — only genuine ambiguity (no exact match available) triggers the event.
- A regression test (or reproduction) demonstrates build-phase dispatched subagents' observed replies always open with a required status token, or the previously-flagged dispatch site is confirmed to now emit one; if the fix is instead a narrower `subagent-stop.js` check, a test demonstrates the hook no longer flags the specific prose pattern from this report as a violation while still catching genuine prose-only replies.
- Existing tests covering `checkWorktreeRequired`/E1 wd-ambiguous behavior and the E3 `subagent-stop.js` status-line check (`tests/bin-lib/hooks/`) still pass.
- `npm test` passes in full.

## Technical Approach

Investigate both hook sites independently — they share no code path and are two distinct defects filed together because they occurred in the same run.

**`wd-ambiguous` (pre-tool-use.js E1 gate, ~line 1057-1094):** trace how `assigned` (`safeReal(ctx.runState.worktree)`) and each target's `actual` (`safeReal(top)`) are computed for the specific git command that triggered the false match. Likely candidates: a realpath/symlink normalization mismatch between how `ctx.runState.worktree` was recorded at claim time versus how the target path resolves at hook-fire time, or `gitTargets()`/`toplevel()` resolving to a path that doesn't match `assigned` even though it's logically the same worktree. Add enough tracing (or a targeted unit test reproducing the concurrent-worktree scenario) to distinguish a genuine resolution bug from truly unprovable ambiguity before changing the gate's logic.

**`contract-violation` (subagent-stop.js E3 check, ~line 43-52):** identify the exact build-phase dispatch call site(s) whose subagent turns can produce a "waiting/standing by" narrative reply — start with `plugin/skills/dispatch/SKILL.md` Step 5 (two Task calls per file-overlap group) and `/claude-tweaks:build`'s own dispatch step, per `plugin/skills/_shared/subagent-output-contract.md`'s Implementer Status Protocol (every dispatched agent must report one of the four statuses as the first line of its reply). Determine whether the dispatch prompt at that site fails to inline the status-line requirement (fixable by adding it), or whether `lastAssistantText()` is picking up an intermediate turn that isn't the subagent's true final reply (fixable by narrowing what `subagent-stop.js` treats as "final").

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — E1 gate; `wd-ambiguous` event emission (~line 1092) and the exact-match / otherWorktrees comparison logic (~line 1057-1110)
- `plugin/bin/lib/hooks/subagent-stop.js` — E3 check; `contract-violation` event emission and `STATUS_RE`/`lastAssistantText()` logic
- `plugin/skills/_shared/subagent-output-contract.md` — canonical Implementer Status Protocol every dispatch site must inline
- `plugin/skills/dispatch/SKILL.md` — Step 5, a candidate build-phase dispatch site to check for a missing/incomplete status-line requirement in its Task prompt template

## Gotchas

- `subagent-stop.js`'s own header comment documents it as best-effort by design (SubagentStop fires unreliably for Task dispatches per claude-code#27755) and already carries one known false-positive class — confirm this report's prose pattern is a genuine defect distinct from that documented unreliability before changing the hook's behavior.
- Issue #750 in this repo covers a related but distinct symptom: a false-positive `contract-violation` on superpowers' own bolded `**Status:** DONE` template. This record is specifically about prose-only first lines carrying no status token at all — don't conflate the two fixes or regress #750's resolution.
- Neither reported symptom caused an incorrect action in the run that surfaced them (every commit/push landed in the correct worktree per the run's own decision log) — this is tooling friction/noise reduction, not a correctness-critical fix.
