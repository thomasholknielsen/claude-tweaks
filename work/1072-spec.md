# 1072: apply-refine-labels.js — failed batch actions are never logged to decisions.md (FAILED not a valid append.js status)

Origin: ledger resolve gate

Defer-reason: needs-human-decision

## Current State

plugin/bin/apply-refine-labels.js run() only calls deps.appendEntry (an AUTO decisions.md line) on the success path (ok.push, line ~143-150). Its catch block (~line 165) only does failed.push({issue, error}) — no decisions.md entry at all. plugin/skills/backlog/refine-mode.md Step 5 (unchanged, still canonical) documents a FAILED {time} — … template whose closing summary counts these lines for its required failed tally. plugin/bin/lib/log-decision/append.js STATUSES enum (["AUTO","STAGED","KEPT-PROMPT","SCANNED","REFUSED"]) has no FAILED member, so the CLI cannot emit that template as-is even if it tried. Neither test file (tests/apply-refine-labels.test.js, tests/apply-refine-labels-run-dir-anchoring.test.js) exercises this — one test explicitly pins the current no-log-on-failure behavior as expected (run: --run given does not log for a failed action).

## Deliverables

- [ ] Decide the shape: (a) extend append.js STATUSES to add a failure status (shared-module blast radius — other consumers), or (b) keep apply-refine-labels.js success-only and add explicit instruction in refine-lanes.md (or refine-mode.md Step 5) telling the executing agent to parse the CLI JSON failed array and log each entry itself via its existing free-text decisions.md write path.
- [ ] Implement the chosen shape.
- [ ] Update/add test coverage proving a failed batch action produces a decisions.md entry the closing-summary failed tally can count.

## Acceptance Criteria

A gh issue edit/comment call inside an apply-refine-labels.js --run batch that fails produces a decisions.md line (directly from the CLI, or from the calling skill reading the JSON failed array) that refine-mode.md Step 5 closing summary can count toward its failed tally — with a test proving it.
