# 1192: recordDecline concurrency test flakes ~2/3 runs even in isolation

Surface: backend

## Current State

`tests/bin-lib/declined-learning/store-concurrency.test.js`'s "recordDecline serializes concurrent writers under an effectively-unbounded lock budget — no lost entries under real cross-process concurrency" test fails intermittently (~2/3 runs observed) even when run in isolation, not just under concurrent sibling-session machine load:

```
error: "worker 1's decline entry must not be lost to a concurrent writer's stale snapshot"
```

Discovered while running the full suite after merging origin/main into an unrelated `/flow` batch branch (worktree-flow-9record-batch) — this test file was never touched by that batch, and the failure reproduces on a clean re-run of the file alone (2 fail / 1 pass across 3 isolated runs).

## Deliverables

- [ ] Investigate `recordDecline`'s lock-then-write path (`plugin/bin/lib/declined-learning/store.js`) for a real race that loses a concurrent writer's entry, not just a timing-sensitive test assertion.
- [ ] Fix the underlying race if one exists, or widen/restructure the test's concurrency assertion if the race is test-harness-only (spawned worker timing), following the same self-calibration approach used for a similar flake in #1127.

## Acceptance Criteria

- `node --test tests/bin-lib/declined-learning/store-concurrency.test.js` passes reliably across multiple consecutive isolated runs (not just once).

## Technical Approach

Start with `plugin/bin/lib/declined-learning/store.js`'s `recordDecline` and its lock-acquisition/write-then-release sequence — confirm whether two workers can both read a stale snapshot before either writes (a lost-update race), or whether the test's own worker-spawn/timing assumptions are the actual source of flakiness.

## Gotchas

- Reproduce first with several isolated `node --test` runs of just this file before concluding root cause — the observed 2/3 failure rate in isolation argues against pure machine-load flake, but confirm before assuming a real lock bug.
