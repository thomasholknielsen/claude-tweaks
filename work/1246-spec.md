# 1246: issue-claims.md has no repair/force-release procedure for a corrupt claim blob, though release-claim.js's exit-5 message now points to it

Surface: backend

## Current State

`plugin/bin/release-claim.js`'s `unreadable` outcome message (added in #817) reads: "cannot determine ownership (not a competing claim; repair or force-release required, see `_shared/issue-claims.md`)". `plugin/skills/_shared/issue-claims.md` documents the `unreadable` classification (`classifyClaimBlob` fails closed to `reclaimable: false`, treated identically to `'live'`) and exit code `5`, but has no section describing what "repair" or "force-release" of a corrupt claim blob actually means in practice — there is no procedure distinct from the existing stale/tombstone re-claim mechanics ("The lock" step 4 / the Release bullet) for the classify-failure case specifically. #817's own spec named "an explicit repair/force-release path" as one of two acceptable approaches (Technical Approach section) and the diff chose the other (a distinct exit code) — leaving the repair path itself undocumented while a runtime message now promises it exists.

## Deliverables

Add a short "Repairing an unreadable claim blob" procedure to `_shared/issue-claims.md` (e.g. a conditional-overwrite `PUT` using the corrupt blob's own current sha, the same mechanics as the existing stale/tombstone re-claim, but explicitly for the classify-failure case) that a human or `/tidy`'s sweep can follow, so `release-claim.js`'s exit-5 message points to real guidance rather than an aspirational cross-reference.

## Acceptance Criteria

- `_shared/issue-claims.md` contains a procedure a human can follow to repair or force-release a claim blob that `classifyClaimBlob` reports as `'unreadable'`.
- The procedure is reachable from (or referenced by) `release-claim.js`'s exit-5 message and the acquire-path `'unreadable'` handling ("The lock" step 6), so both consumers of the classification point at the same guidance.

## Technical Approach

Add a new `### Repairing an unreadable claim blob` subsection to `_shared/issue-claims.md`, placed after "The lock" section's existing claim/release procedure (after the "List all claims" bullet, before `### Group claiming`). Document the repair as a conditional-overwrite `PUT`/`create_or_update_file` call using the corrupt blob's own current blob sha (read from the contents API's own response metadata, not from the unreadable content) — structurally the same mechanics "The lock" step 4 and the Release bullet already use for the `'tombstone'`/`'stale'` re-claim, scoped explicitly to the `'unreadable'` classify outcome. Cross-reference the new subsection from `release-claim.js`'s exit-5 message (already pointing generically at `_shared/issue-claims.md`) and from "The lock" step 6's `'unreadable'` handling, so both consumers land on the same procedure.

### Key Files

- `plugin/skills/_shared/issue-claims.md` — add the "Repairing an unreadable claim blob" procedure
- `plugin/bin/release-claim.js` — verify the exit-5 message's cross-reference resolves to the new section once it exists

## Gotchas

- The corrupt blob's own blob sha must still be read successfully from the GitHub contents API/MCP response even though its *content* fails `classifyClaimBlob`'s JSON parse — the sha is response metadata, not something extracted from the unreadable content itself.
- This is a repair path, not a new claim-state transition: `classifyClaimBlob` should keep reporting `'unreadable'` as `reclaimable: false` (fails-closed-to-live) — the new section documents a human/`/tidy`-invoked override, not a change to the acquire-path's own fail-closed behavior.
