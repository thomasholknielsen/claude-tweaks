# 1328: residue.js: pipeline-run-dir `remedy: auto` classification does not check whether the run's worktree is still locked

Surface: backend

## Current State

residue.js (`plugin/bin/lib/residue/probes/pipeline-runs.js`) classifies an un-archived `status: clean` pipeline-run-dir finding as `remedy: auto` — eligible for automatic Phase-1 fix-now archival during `wrap-up/residue-sweep.md` — based only on `run-state.json`'s own `status` field. It never checks whether that run's recorded `worktree` (a path string stamped by `record-worktree`/`post-tool-use.js`'s `path.resolve(worktreePath)`, per `bin/lib/hooks/context.js`/`bin/lib/hooks/post-tool-use.js`) is currently `locked`.

Observed on #1295's own wrap-up: residue-sweep flagged `.claude-tweaks/pipelines/2026-08-23T181549-record-357` (a different, unrelated record) as `remedy: auto`, even though `git worktree list` showed `.claude/worktrees/dispatch-record-357` as `locked` — i.e. a live sibling session still actively holds it. Blindly following `remedy: auto` here would have archived a run directory a concurrent session is still using, corrupting its state out from under it — the exact hazard `_shared/pipeline-run-dir.md` and the worktree-lock discipline elsewhere in this plugin exist to prevent.

The plugin already has the right vocabulary for this exact case: `plugin/bin/lib/residue/probes/worktrees.js`'s `probeWorktrees` reports a locked worktree as `remedy: 'record'` with an evidence string naming the lock, and `residue-sweep.md` maps that case ("a locked worktree a live session still holds") to `blocked-external`. That mapping is applied to worktree findings, not to the pipeline-run-dir finding — `probePipelineRuns` (called from `plugin/bin/residue.js` as `probePipelineRuns({ cwd })`, with no `scope` passed today) has no way to cross-check lock state.

## Deliverables

- In `plugin/bin/lib/residue/probes/pipeline-runs.js`'s `probePipelineRuns`, before assigning `remedy: 'auto'` to a `status: clean` finding, cross-check whether the finding's recorded `worktree` (from that run's own `run-state.json` `worktree` field, when non-null/non-empty) is currently `locked` — using the already-resolved `scope.worktrees` list (`plugin/bin/lib/residue/scope.js`'s `resolveScope`/`parseWorktrees`, which already parses `path`/`branch`/`locked`/`lockReason` from `git worktree list --porcelain`) rather than re-invoking git from this probe.
- Thread `scope` into `probePipelineRuns` from `plugin/bin/residue.js`'s existing call site (`probePipelineRuns({ cwd })` → `probePipelineRuns({ cwd, scope })`) — `scope` is already resolved earlier in `main()` for the other probes.
- When the recorded worktree matches a `scope.worktrees` entry that is `locked`: downgrade to `remedy: 'record'`, with an evidence string naming the lock (mirroring `probeWorktrees`'s `lockedEvidence` wording/shape), so `residue-sweep.md`'s existing "locked worktree a live session still holds" → `blocked-external` mapping applies instead of an unsafe auto-archive.
- When `worktree` is null/empty, or does not match any currently-locked entry in `scope.worktrees`: keep `remedy: 'auto'` as today — unchanged behavior for the common case.

## Acceptance Criteria

1. A `status: clean` pipeline-run-dir finding whose recorded `worktree` matches a currently-locked entry in `git worktree list --porcelain` resolves to `remedy: 'record'`, not `remedy: 'auto'`.
2. A `status: clean` pipeline-run-dir finding whose `worktree` is null/empty, or does not match any locked worktree, keeps its current `remedy: 'auto'` classification — no regression, confirmed against the existing tests in `tests/bin-lib/residue/probes-pipeline-runs.test.js`.
3. A new test in `tests/bin-lib/residue/probes-pipeline-runs.test.js` pins both branches (locked → `record`, null/unlocked → `auto`), constructing a fixture `scope`/`scope.worktrees` value directly rather than shelling out to real git.
4. `npm test` passes.

## Technical Approach

Add an optional `scope` parameter to `probePipelineRuns({ cwd, scope })`. For each `status: clean` finding, read `state.worktree` from that run's `run-state.json`. When it's a non-empty string, look it up against `scope.worktrees` (matching on `.path`, the same field `probeWorktrees` already keys on) and check `.locked`. If a match is found and it's locked, set `remedy: 'record'` and build an evidence string naming the lock (branch + lock reason, following `probeWorktrees`'s `lockedEvidence` pattern) instead of the current hardcoded evidence string. Otherwise, keep the existing `remedy: 'auto'` path and evidence string unchanged. `plugin/bin/residue.js`'s `main()` already resolves `scope` before calling `probePipelineRuns` — just pass it through at that one call site.

### Key Files

- `plugin/bin/lib/residue/probes/pipeline-runs.js` — add the worktree-lock cross-check before assigning `remedy: 'auto'`
- `plugin/bin/residue.js` — pass the already-resolved `scope` into the existing `probePipelineRuns({ cwd })` call
- `tests/bin-lib/residue/probes-pipeline-runs.test.js` — add tests pinning the locked and null/unlocked branches

## Gotchas

- `scope.worktrees` entries carry `.path` as reported by `git worktree list --porcelain`; `run-state.json`'s `worktree` field is stamped via `path.resolve(...)` (`post-tool-use.js`), not necessarily realpath-canonicalized the same way `bin/lib/hooks/context.js`'s `worktreeMatches` does for its own comparison. Match the two consistently (exact string compare is fine if both sides are already resolved absolute paths without symlink differences; realpath both first if not) — don't let a silent path-form mismatch mean the cross-check never actually fires.
- The existing tests in `tests/bin-lib/residue/probes-pipeline-runs.test.js` call `probePipelineRuns({ cwd: root })` with no `scope` at all — `scope` must be optional (treat a missing/empty `scope.worktrees` as "no lock information available," i.e. behave exactly as today) so those existing calls keep passing unchanged.
