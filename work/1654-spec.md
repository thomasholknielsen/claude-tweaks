# 1654: dispatch's group-size guard has no policy.yml lever — wire GROUP_SIZE_GUARD_DEFAULT through the schema

Defer-reason: genuinely-larger

## Current State

`plugin/bin/lib/issues/grouping.js`'s `GROUP_SIZE_GUARD_DEFAULT = 10` is a hardcoded magic threshold. It's overridable via an `options` param, but never actually passed by its only real caller (`plugin/skills/dispatch/queue-pull-script.md`'s `partitionGroupsBySizeGuard(groups)` call), and it isn't wired into `policy.yml` the way comparable tunables (`auto-fix-threshold`, `tidy-aggressiveness`) are per `plugin/bin/lib/policy-schema.js`'s `POLICY_KEYS`. A repo with a genuinely large legitimate file-overlap bundle (e.g. a 12-file refactor) has that group silently excluded from headless `next` dispatch selection with no way to adjust it short of editing plugin source.

## Deliverables

Register a new policy key (e.g. `dispatch-group-size-guard`) in `POLICY_KEYS` with an appropriate type (check whether `policy-schema.js`'s type vocabulary supports a numeric lever, or add one), wire it through `resolve-policy.js`, update `queue-pull-script.md`'s inline script to resolve and pass it into `partitionGroupsBySizeGuard`, and document it in `policy-schema.md` alongside `auto-fix-threshold`/`tidy-aggressiveness`.

## Acceptance Criteria

Default behavior is unchanged (threshold of 10) when the lever is unset. A project setting the lever in `policy.yml` changes dispatch's headless `next` group-size exclusion threshold. Existing dispatch/grouping tests pass, plus a new test covering the policy-driven override.
