# 1402: events.jsonl cross-run contamination: fallback-attributed events land in the wrong run's log

Surface: backend

**Related:** #1410, #1425, #1431

## Current State

`#1033`'s wrap-up resume discovered that its own pipeline run directory's `events.jsonl` (`.claude-tweaks/pipelines/2026-08-24T151817-record-1033/events.jsonl`) contains six events that describe *other*, unrelated worktrees and records — `dispatch-record-1389` (a `commit`/push event), `dispatch-record-1388` (a `worktree-staleness` check), and `specify-record-1194` (two `skill_invoked` events, one `ask-user-question` event, and one `pre-compact` event). None of these concern record #1033's own worktree (`dispatch-record-1033`) or branch. Every one of the six carries `"attribution":"fallback"`, and `bin/friction-events.js --run <this-run-dir>` returns them all as `"_source":"primary"` — i.e. they were written directly into this run's own `events.jsonl`, not merged in from a secondary source. This means some hook-layer event-logging call, running under a "fallback" attribution path (unable to determine the true owning run directory from its actual context), resolved to record #1033's run directory for events that belonged to entirely different runs.

This matches the general failure class already named in project memory (`hooks-record-worktree-no-run-flag-hazard` — "record-worktree without --run corrupts another session's state"), but the concrete mechanism here is the *event-attribution* fallback specifically, not `record-worktree` itself.

Confirmed present in this checkout (`plugin/bin/lib/hooks/context.js`):
- `resolveRun(cwd, env, sessionId)` (`context.js:216-247`) is the sole producer of `attribution: 'fallback'`. Two distinct fallback branches exist: an unknown-`sessionId` branch (`context.js:226-236`, used when the caller's identity can't be established at all) and a known-but-unowned-`sessionId` branch (`context.js:238-246`, used when the session doesn't own any existing run). Both pick "the newest non-terminal run dir that isn't claimed by another session" as a guess (`iterRunDirsWithState`, newest-first) — with no check that the guessed run dir has any actual relationship (shared worktree, shared branch) to the event being logged.
- Every hook call site that appends a fallback-attributed event goes through `appendEvent(runDir, type, data, attribution)` (`context.js:481`), which stamps `{ attribution }` onto the record only when `attribution === 'fallback'` (`context.js:495`) — callers include `post-tool-use.js` (`worktree-staleness` at line 435, `ask-user-question` at line 533, and a third site at line 587), `pre-compact.js` (line 13/18), and `skill-invocation.js` (line 67). Any of these firing inside a second, concurrent session whose own run isn't yet session-owned will misattribute into whatever unrelated run `resolveRun` guesses.
- `bin/friction-events.js`'s `run()` (`friction-events.js:78-93`) reads the queried run's `events.jsonl` verbatim (`readEvents(runDir, 'primary')`) with no filtering against the run's own owning worktree/record — so a fallback-misattributed event survives all the way to the Friction lens's evidence output.
- A sanctioned exception already exists at `context.js:210-217` (console execution, `#413`): that code path *deliberately* acts on a run whose owning session may be gone, and its own comment explicitly says "Do not 'fix' this by tightening the ownership check" — any fix here must not regress that path.

Root cause (which fallback branch actually produced these six events, and why the guess landed on #1033's run dir specifically) has not been isolated in this session — that isolation is the deferred work.

## Deliverables

- Root-cause which of `resolveRun`'s two fallback branches (`context.js:226-236` or `context.js:238-246`) produced the six cross-run events on 2026-08-24 ~15:25-15:47Z, and why the "newest non-terminal, unowned run" guess landed on record #1033's run directory specifically (likely a shared-session or shared-CWD ambiguity across concurrently active worktree sessions).
- Either: (a) fix the attribution mechanism so it never writes to a run directory it isn't authoritatively bound to (mirroring the `--run`-flag discipline `record-worktree` already uses), while preserving the `#413` console-execution exception's deliberately loose ownership check, or (b) if some cross-run fallback write is intentional, have `friction-events.js` filter fallback-attributed events whose referenced worktree/record doesn't match the queried run before returning them.
- Add a regression test pinning that `friction-events.js` never returns an event referencing a different worktree than the one the queried run directory owns.

## Acceptance Criteria

- AC1: The event-attribution code path that produced these six events is identified and named (file:line) — the starting candidates are `context.js:226-236` and `context.js:238-246`, per the Current State section above.
- AC2: A fix lands (or a documented reason why cross-run fallback attribution is intentional, with `friction-events.js` filtering to compensate), without regressing the `#413` console-execution exception at `context.js:210-217`.
- AC3: A test exists that fails on the original bug (a fallback-attributed event for a different worktree leaking into a queried run's friction-events output) and passes after the fix.

## Technical Approach

Start by reproducing the misattribution deterministically rather than re-deriving it from the historical `events.jsonl` snapshot: drive `resolveRun` (or the hook entry points that call it) with two concurrent fake `iterRunDirsWithState` results — one run owned by session A, one unowned — and a call from session B with no owning run of its own, then assert which run dir it resolves to. This isolates AC1 without needing to reconstruct the original timing race.

Once the exact fallback branch is confirmed, pick between the two Deliverables options based on what the reproduction shows:
- If the fallback guess can be made worktree-aware cheaply (e.g. `resolveRun` already has `cwd` — check whether the guessed run dir's `worktreePath` state field matches `cwd` before accepting it as a target), prefer fixing at the source (option a) — this fixes every consumer, not just the Friction lens.
- If tightening `resolveRun` risks the `#413` exception or other callers that rely on the current loose fallback, prefer the `friction-events.js`-side filter (option b): compare each event's implied worktree/record (from its `_runDir`'s own `run-state.json`, or a `worktree` field on the event itself if one exists) against the queried run's worktree before including it.

### Key Files

- `plugin/bin/lib/hooks/context.js` — `resolveRun` (fallback branches, lines 226-236 and 238-246) and `appendEvent` (line 481) are the attribution/write path under investigation.
- `plugin/bin/friction-events.js` — `run()` (lines 78-93) and `readEvents()` (lines 51-63) are where option (b)'s filter would land if chosen.
- Existing tests for these two files (wherever `tests/bin-lib/hooks/` and `tests/` cover `context.js`/`friction-events.js` today) — extend rather than duplicate.

## Gotchas

- `context.js:210-217`'s `#413` console-execution exception deliberately tolerates a foreign-owned or `null` `ownedRun.dir` — do not tighten the ownership check in a way that breaks console execution's ability to act on a run whose session has already ended.
- The asymmetry documented at `context.js:203-209` is load-bearing: an *unowned* run may still legitimately be the caller's own (ownership is only stamped by `record-worktree`, which a run without a worktree never calls), but a run owned by a *different, known* session is never the caller's — a fix must preserve this distinction, not collapse both fallback branches into one stricter check.
- Practical impact observed so far is log noise only — the Friction lens's own membership rule already excludes cross-session bystander events from judgment — so this is a correctness/reliability fix for the Friction lens's "aggregate volume"/"avoidability" judgments under concurrency, not a currently-user-visible bug.
