# 1407: decisions.md FAILED status: undocumented, uncounted by calibration and wrap-up console fast path

Origin: spec #1072 review (architecture)

Defer-reason: pre-existing-outside-diff

## Current State

`_shared/auto-decision-log.md`'s canonical STATUS vocabulary table (and `plugin/bin/lib/log-decision/append.js`'s `STATUSES` array) documents exactly five statuses: `AUTO`/`STAGED`/`KEPT-PROMPT`/`SCANNED`/`REFUSED`. `FAILED` decisions.md lines are not part of that vocabulary, but two independent hand-composed writers already emit them: `plugin/skills/backlog/refine-mode.md` Step 5's own `FAILED {time} — …` template (pre-existing, predates #1072) and, since #1072, `plugin/bin/apply-refine-labels.js`'s catch block (`deps.appendEntry` with a hand-built `- FAILED …` line, bypassing `append.js`'s `formatEntry`/`STATUSES` gate on purpose — #1072's review verified extending the enum would touch multiple consumers, so the CLI writes the line directly instead).

Two readers of `decisions.md` don't recognize `FAILED` as a kind:
- `plugin/bin/lib/calibration/decisions-classifier.js`'s `KIND_RE` (`/^-\s+(AUTO|STAGED|KEPT-PROMPT|REFUSED|SCANNED)\b/`) — a `FAILED` line falls through to `{ kind: 'other' }` and is silently excluded from every calibration bucket `plugin/bin/lib/calibration/aggregate.js` computes (refusedCount, reversibilityDist, etc.). `plugin/bin/calibration-report.js` scans every archived run dir under `.claude-tweaks/pipelines/archive`, including refine-mode's own standalone-auto run dirs, so this is a real (if minor) undercount today, not hypothetical.
- `tests/wrap-up-console-fast-path-scanned-exclusion.test.js`'s `DECISION_BEARING_STATUSES` list (`['AUTO', 'STAGED', 'KEPT-PROMPT', 'REFUSED']`), mirroring `plugin/skills/wrap-up/review-console.md`'s Empty-console fast path condition — also omits `FAILED`. Verified during #1072's review that this specific gap is currently unreachable in practice: `apply-refine-labels.js --run` is only ever invoked from `plugin/skills/backlog/refine-lanes.md` against refine-mode's own "standalone-auto run dir" (`_shared/pipeline-run-dir.md`), never against a `/flow` `$PIPELINE_RUN_DIR` that `review-console.md`'s fast path actually gates — so no live wrap-up console has silently skipped over a real failure yet. That separation is incidental, not enforced, so it's worth documenting rather than relying on.

Neither reader crashes or misclassifies a `FAILED` line as some other status — the failure mode is silent non-attribution, not corruption.

## Deliverables

- [ ] Add `FAILED` to the documented status vocabulary in `_shared/auto-decision-log.md`'s STATUS table (with a short description: a batch write attempt that errored, kept separate from `AUTO`/`REFUSED` since it has no "revert" or "no valid Defer-reason" semantics).
- [ ] Extend `plugin/bin/lib/calibration/decisions-classifier.js`'s `KIND_RE` to recognize `FAILED` and decide (with `aggregate.js`) whether/how a failed-count bucket should surface in calibration reports.
- [ ] Extend `tests/wrap-up-console-fast-path-scanned-exclusion.test.js`'s `DECISION_BEARING_STATUSES` (and `review-console.md`'s prose condition) to include `FAILED` as decision-bearing, so the Empty-console fast path can't silently skip a run whose only content is an unresolved failure, even if today's only two writers happen not to reach it.
- [ ] Decide whether `append.js`'s `formatEntry`/`STATUSES` should gate `FAILED` too (bringing both existing hand-composed writers onto the shared formatter) or whether hand-composition stays the documented pattern for this one status — either way, update the vocabulary doc to match reality.

## Acceptance Criteria

A `decisions.md` file containing only a `FAILED` line (no `AUTO`/`STAGED`/`KEPT-PROMPT`/`REFUSED`) is treated as decision-bearing by the wrap-up console's fast-path test, and `calibration-report.js`'s aggregate output visibly accounts for `FAILED` lines (a named bucket, not silent `'other'`) — both backed by a test.
