# Pending-review branch durability (dispatch-originated runs)

Run this before rendering the consolidated console below, never after — it ends in a blocking `AskUserQuestion` that a headless firing never returns from, so a step scheduled after it does not run on the very path it exists to protect. A dispatched **bundle** reaches this console and no other: every per-spec `/claude-tweaks:wrap-up` deferred its own under `MULTISPEC_REVIEW_DEFER=1`.

**Gate the read.** Read `_shared/pending-review-durability.md` — the scope guard, the worktree-safe push, the existing-open-PR check, the draft-PR creation, and the push/PR failure fallbacks — only when `CLAIM_RUN_ID` is set and non-empty (dispatch-originated; an interactive human-run `/claude-tweaks:flow` never sets it), **and** this run used a worktree strategy, **and** this `/flow` invocation's step list contained `review` and that step passed for every spec that ran. That third clause is the outcome condition, enforced here rather than only asserted inside the file: a `wrap-up`-only invocation is `dispatch/two-call-gate.md` section 5's failure-path teardown call, which reaches a console with `CLAIM_RUN_ID` set on a genuinely `failed` run. A run that aborted at a spec's HARD-GATE — or continued past one under `keep-going` — fails it too; those specs appear in the Not run / Failed footer below, and that footer being non-empty is itself the signal to skip. Otherwise skip this section entirely and do not read the file.

One branch is shared across every spec in the run, so this is one push and one draft PR for the whole bundle — that file's own bundle rule fixes which record supplies the PR title and how the rest are referenced. It never calls `close-run` and never clears the run's worktree assignment; the parent run dir stays intact for the console below and for "Shared teardown" afterwards.

**Its outcome record lands at the PARENT run dir's root** (`{parent-run-dir}/pending-review-durability.md`), not in any `spec-{N}/` subdirectory — one bundle, one record. No per-spec Verification Brief reads it: every spec reached `/wrap-up` Phase 4's execution step, and posted its brief, before this console ran (see "When to run" above; acceptance labeling is not among the items `wrap-up/execution-and-verification.md`'s `MULTISPEC_REVIEW_DEFER` branch defers). That is an ordering fact, not a location bug — moving the file cannot fix it. So on this path **a push or PR-open failure is carried to each record by its own `gh issue comment`**, per that file's Step 5, before the console renders; on success the PR's `Refs #{m}` lines are the per-record signal. Surface the record's three lines as an Auto-applied row in the console below either way.

**Two provenances, one sequence.** Five sections — Skill updates, Documentation updates, Journey updates, Configuration updates, Reference repairs — are **engine-rendered**: their row numbers and content come verbatim from the `--spec-state` engine call in "When to run the consolidated console" step 3, which takes `{n}` as its `--start-at` argument. Every other batch section — Auto-applied, Pending review, Low-confidence findings, Contested findings, Cleanup actions, Issue closures, Translated briefs — plus the three per-item sections that sit outside the global sequence (Queue writes, Memory updates, Upstream feedback, per the note above) is **prose-aggregated**: composed by hand from each spec's own `decisions.md`/`staged/` reads (step 2 above). `{n}` is therefore 1 (the start of the global sequence) plus the row count of every prose-aggregated section that renders *before* the engine block in the template — Auto-applied, Pending review, Low-confidence findings, Contested findings.
