### Original Framing
`bootstrap-steps.md` Step 6 documents `.worktrees/` (project root) as "the standard worktree directory," citing superpowers v5.1.0's preferred path and claiming it is the only directory `/superpowers:finishing-a-development-branch` cleans up. But the native `EnterWorktree` harness tool actually creates worktrees under `.claude/worktrees/` — confirmed live (4 active there, 0 under `.worktrees/`). The task as posed: "determine which convention is actually correct going forward" — update the doc to make `.claude/worktrees/` the standard, or confirm `.worktrees/` remains correct for the git-fallback path — plus investigate whether cleanup handles `.claude/worktrees/` worktrees today. The reflected summary leaned toward promoting `.claude/worktrees/` to the standard.

### Reframed Problem
"Which single directory is canonical" is a false dichotomy — it forces two deliberately separate ownership domains onto one throne. The two paths are not competing claims; they are the outputs of two mutually-exclusive creation paths that superpowers' own `using-git-worktrees` Step 1 explicitly separates: Step 1a (native tool — `EnterWorktree` → `.claude/worktrees/`, harness-owned) versus Step 1b (git fallback — `git worktree add` → `.worktrees/`, superpowers/plugin-owned, used *only* when no native tool exists). Step 6 collapses that two-branch design into a single "the standard directory is X" sentence, erasing the very distinction the upstream skill is built around.

The reframe also relocates the actual defect. It is not "the doc names the wrong path." It is that **Step 6's remediation advice is dangerous relative to reality**: the instruction to "migrate a legacy `.claude/worktrees/` directory to `.worktrees/`" would relocate a *live, harness-registered* worktree into the one path where a different, unrelated cleanup mechanism (superpowers' `finishing-a-development-branch`) will later delete it out from under the harness's own bookkeeping. It labels the native tool's current, tried-first, by-design output as obsolete cruft. The INBOX item has the causality backwards — the doc isn't lagging reality; its "fix" would manufacture a state-desync bug. (Verified: this migrate instruction exists at `bootstrap-steps.md:155` **and** `init/SKILL.md:96` — any correction must touch both.)

The deeper, higher-cost question the label debate obscures: **does either side's cleanup contract actually hold?** Superpowers deliberately declines to clean `.claude/worktrees/` (it is not superpowers' to own). The plugin invokes `EnterWorktree` but references `ExitWorktree` nowhere and documents no harness-side teardown. So 4 accumulated worktrees under `.claude/worktrees/` is at least as plausibly a symptom of "nothing closes these" as evidence of a healthy standard path — a missing half of a lifecycle, not a documentation typo.

### Key Assumptions Surfaced
- **That there is one correct directory at all** — unvalidated as stated; native-owned and fallback-owned worktrees may permanently, correctly land in different places, maintained by different parties. Forcing them into one "standard" is a possible category error, not a bug to reconcile.
- **That the 4-vs-0 observation is evidence** — invalidated. It is non-distinguishing: because the native tool always wins when present (Step 1a beats 1b), a repo with `EnterWorktree` will *always* show this distribution regardless of whether `.worktrees/` is current or obsolete. It falsifies neither hypothesis; it is the designed outcome.
- **That `.claude/worktrees/` is a stable contract worth documenting as permanent** — unvalidated. It is an unversioned implementation detail of a harness the plugin neither owns nor version-pins. Whatever path is written down today can move silently in a future harness release, reproducing this exact "incidental rediscovery."
- **That the drifted claim is about this repo** — invalidated as framed. It is a claim about *external* dependency behavior (a harness tool + a separate plugin). This plugin's own drift-watcher (`harness-health`) audits this repo's docs against this repo's code — it does not watch claims about third-party tool behavior. This is a recurring risk class, not a one-off.
- **That `.claude/worktrees/` is uniformly treated as "legacy"** — invalidated. The repo contradicts itself: `subagent-output-contract.md:39` documents `.claude/worktrees/<name>/` as the *normal, expected* location a dispatcher runs from, while the init files call it legacy-to-migrate-away. The plugin already relies on it being real and current in one place while telling users to abandon it in another.

### Blind Spots Identified
- **The cleanup investigation is being under-weighted.** The problem statement appends it as "also needs investigation" rather than as co-equal scope, and the original leaning picked the cheap one-file doc edit as the path of least resistance. This is the item whose cost compounds silently — orphaned worktrees accumulate unnoticed until it is a mess months later — while the label fix is cosmetic and reversible anytime.
- **The "cross-file promise" anti-pattern (this repo's own, logged 4× in CLAUDE.md).** Promoting `.claude/worktrees/` to "standard" while never touching the cleanup step ships a doc-side promise whose producer-side behavior was never verified — worktrees created the newly-"correct" way would silently stop getting cleaned up by superpowers.
- **The location-agnostic solution already exists in-repo and isn't being reused.** `bin/lib/hooks/worktree-detect.js` decides worktree-ness structurally (`GIT_DIR != GIT_COMMON`), fully convention-agnostic; and `git worktree list` is *already* the discovery mechanism in `wrap-up/cleanup-procedures.md`, `wrap-up/SKILL.md`, and `tidy/SKILL.md`. The defect is a location-*sensitive* pattern (hardcoded path strings in prose) coexisting with an established location-*agnostic* one in the same system.
- **The "blanket-ignore breaks a needed sibling" pattern (also this repo's own).** If any fix later adds `.claude/worktrees/` to an exclusion/policy/cleanup allow-list without equally preserving `.worktrees/` for the still-valid fallback path, the fallback's worktrees become the new invisible orphan case.
- **`bootstrap-steps.md` may carry other unverified external-tool assertions** stated as fact rather than checked empirically — the same class of claim that drifted here.

### Constraints to Carry Forward
- The cleanup logic that would need to change lives inside **superpowers, a separate plugin this repo depends on but does not own**. No doc edit inside claude-tweaks can change superpowers' cleanup behavior — at most it can accurately describe it.
- `finishing-a-development-branch` cleans only `.worktrees/`/`worktrees/` and **deliberately leaves anything else alone** (per an upstream provenance-based-ownership model: whoever creates a worktree owns its cleanup). Treat "superpowers does not clean `.claude/worktrees/`" as intended behavior to document, not a bug to file against superpowers — but verify this against the actually-installed superpowers version before relying on it (see Open Questions).
- The git-fallback path (Step 1b) currently defaults to `.worktrees/` for the no-native-tool case, and any fix should preserve both paths rather than overwrite one with the other — pending the ADR-level decision below on whether that two-domain split is worth keeping permanently. [ADR-candidate — deciding to keep two permanently separate, separately-owned worktree domains rather than converging on one is a non-obvious, hard-to-reverse architectural stance once docs and consumers assume it.]
- The `worktree.always` policy gate is out of scope as a severity dimension: `worktree-detect.js`'s isolation check is purely structural and convention-agnostic, so whichever directory this settles on has **no bearing** on whether the gate recognizes a worktree.
- The "migrate legacy `.claude/worktrees/` → `.worktrees/`" instruction must be corrected in **both** `bootstrap-steps.md:155` and `init/SKILL.md:96` (and reconciled against `subagent-output-contract.md:39`, which treats that path as normal).
- Prefer runtime discovery (`git worktree list`) over asserting an externally-owned, unversioned path string as a permanent fact in prose; if a path must be stated, attach an explicit "verified as of {date}, harness-owned implementation detail" caveat rather than presenting it as a stable contract. [ADR-candidate — choosing runtime discovery over static documentation trades doc simplicity for resilience against dependency drift, a genuine and consequential tradeoff.]

### Open Questions for Brainstorming
- Is the upstream provenance-based-ownership model (harness owns `.claude/worktrees/` cleanup, superpowers owns `.worktrees/`) real and current in the **actually-installed** superpowers version in this repo — not just in a Draft design doc or an arbitrary cached version? What version is installed, and does its `finishing-a-development-branch` cleanup match the claim?
- If the harness owns `.claude/worktrees/` cleanup, **what actually performs it, and when?** Is there a working `ExitWorktree`/teardown contract at all, or are the 4 accumulated worktrees evidence that nothing closes them? Should the plugin invoke or document a close step?
- Should the fix delete the "standard directory is X" assertion entirely and replace Step 6 with a description of the two ownership domains + a runtime-discovery instruction — rather than picking a winner?
- Where should the boundary sit between "describe external tool behavior accurately (with a dated caveat)" and "don't assert externally-owned facts at all, query git instead"? Which consumers currently hardcode a path and should switch to `git worktree list`?
- Is the missing external-dependency-behavior drift category worth a mechanism (e.g., extending `harness-health` or a periodic check), given this incident was found only incidentally?
- Does `bootstrap-steps.md` (or Step 6's neighbors) contain other unverified assertions about harness/superpowers behavior that should be spot-checked in the same pass?
