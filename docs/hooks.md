# Hooks

All hook registrations route through `plugin/bin/hooks.js <event>` — one dispatcher, one module per event in `plugin/bin/lib/hooks/`. Rules:

- **Never break a session.** Every path — including a PreToolUse deny — exits 0; no module ever sets a non-zero `exit`. A deny is communicated entirely via `hookSpecificOutput.permissionDecision: 'deny'` in the stdout JSON, not the process exit code (see `pre-tool-use.js`'s own header comment for why exit 2 doesn't work for this). New modules must pass the garbage-stdin invariant test in `tests/hooks-dispatcher.test.js`.
- **Tiered posture per `_shared/auto-mode-contract.md`:** block (E1 wrong-checkout commit; the `worktree-always` policy gate), warn (non-blocking systemMessage), inform (SessionStart additionalContext), log (append to the run dir's `events.jsonl`). What that gate covers, what it deliberately doesn't, and its one `.claude-tweaks/pipelines/` exemption are stated once — in `plugin/skills/_shared/policy-schema-coverage.md`'s `worktree-always` coverage block, pinned to `pre-tool-use.js`'s exported `GATE_COVERAGE` by `tests/hooks-gate-coverage.test.js`. Don't restate the list here or anywhere else; five files did and all five went stale `[IL-93]`.
- **Project-agnostic by construction:** modules key off plugin-owned state (`$PIPELINE_RUN_DIR`, `.claude-tweaks/pipelines/`, `.claude-tweaks/policy.yml`), never off project structure. E1/E2/E3 no-op without a resolved run dir — the `worktree-always` policy gate is the one PreToolUse check that is deliberately run-independent, since its job is to require a worktree even before any pipeline run exists. `post-tool-use.js`'s closing-keyword check (warn tier) is the analogous exception on the PostToolUse side — it fires on any `git commit` regardless of run-dir state, since the gap it catches (a fix commit made outside the structured `/specify` → `/build` → `/wrap-up` pipeline, with no closing keyword) is exactly a commit that would never resolve a run dir in the first place. The deferred-subproject capture check (also warn tier) mirrors this on `Write`: it fires on any write to `docs/superpowers/specs/*-design.md` regardless of run-dir state, since a brainstorming session that hasn't reached `/specify` yet has no pipeline run dir to gate on either.
- **Ambiguity resolves to allow** — E1 denies only provable mismatches. A recorded worktree whose path no longer exists also resolves to allow (fail-open) — tear-down without close-run ends enforcement, not the session. Ownership counts toward provability: `record-worktree` stamps the recording session's id (`CLAUDE_CODE_SESSION_ID`), and a wrong-checkout commit from a *different* session is allowed with a warn (`wd-foreign-session` event) instead of denied; missing identity on either side falls back to deny.
- Run-dir state files written by hooks: `events.jsonl` (append-only typed events) and `run-state.json` (status: active | interrupted | clean, worktree assignment, owning session id). Skills write run-state only through `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" record-worktree <path>` / `close-run` (plus the one creation-time stamp: wrap-up Phase 1 writes the initial `run-state.json` with `createdBy` when it creates a standalone run dir). `resolve-run-dir --create` (#692) may mint the run *directory* itself (mkdir, plus `decisions.md`/`staged/` under `--standalone`) — but it never touches `run-state.json`: that first write is still exclusively `record-worktree`/`close-run`'s, or wrap-up's own creation-time stamp above. **A second creation-time stamp (#500):** `post-tool-use.js`'s `stampAdHocRunDir` mints and stamps a `{ts}-adhoc-standalone` run dir directly (both the `resolve-run-dir --create --standalone` mint and the `run-state.json` write, in-process — this is hook code itself, not a skill, so the "skills write run-state only through the CLI" rule above doesn't apply to it) when an `EnterWorktree` call finds no run dir already owned by this session — closing the ad-hoc-worktree-dev-session blind spot in `skills/reflect/full-mode.md`'s Friction Lens. It never overwrites an already-owned run: gated on `ctx.ownedRun.dir` being null, so a formal pipeline's own `PIPELINE_RUN_DIR`/`record-worktree` stamp is never shadowed.
- **`record-worktree` requires `--run` — no implicit fallback (#1124).** Before #1124, omitting `--run` fell through to the newest-non-terminal-run resolver (the "Two resolutions, not one" note below), which could silently target and corrupt a *different*, live sibling session's `run-state.json` — reproduced 3 times independently in one firing against this same subcommand, including via a bare `--help` invocation (the fallback resolved before argument parsing ever rejected the call). `record-worktree` now refuses outright — `claude-tweaks: record-worktree requires --run`, non-zero exit, no write of any kind — whenever `--run` isn't passed explicitly; every sanctioned caller already names its own run directory, so nothing legitimate relies on the old guess. Always pass an explicit, anchored `--run <dir>` naming this session's own run directory, even for a help/diagnostic call.
- **Archived is terminal (#208), writer side only since #1103's fix-wave-1.** Once a run-id exists under `.claude-tweaks/pipelines/archive/{run-id}/`, `run-dir-resolve.js`'s `resolve()` — the one writer chokepoint for `.claude-tweaks/pipelines/{run-id}/` creation — refuses to (re-)create or reuse a live directory sharing that run-id's name (adopted `PIPELINE_RUN_DIR` env var, `newestMatch` reuse, and both `--create` mint branches all carry the guard); this half fails OPEN on a read error other than "doesn't exist" — an unreadable `archive/` creates exactly as it did before this invariant existed, never silently suppressing a genuinely unfinished run. The reader side (`context.js`'s `iterRunDirsWithState`) no longer treats mere existence of `archive/{run-id}/` as proof of a completed archive: `archiveRunDir` (`reconcile/archive-merged.js`) creates that directory via `fs.mkdirSync` as its very first action, before any content moves, so an existence-only reader check stranded any run whose archival then failed partway (git-mv-failed, commit-failed, tracked-entry, move-failed, …) as permanently "already archived" — the literal double-nesting bug #1103 reports. The reader now relies solely on the archive twin's own `run-state.json` genuinely reading `status: 'clean'`; a resurrected or corrupted twin state, or an empty/incomplete twin, no longer hides the live run dir.
- **An explicit `--run <dir>` must be *anchored*, not merely real** (`#790`/`[IL-127]`). The eight subcommands that accept it — `record-worktree`, `record-pr`, `spec-status`, `close-run`, `teardown-run`, `check-resume-freshness`, `check-staged-inventory`, `archive-run` — resolve the value against the caller's cwd and then require it to sit under the main checkout, the same adoption-time check `_shared/pipeline-run-dir.md` applies to `PIPELINE_RUN_DIR`. A path that exists but resolves inside a linked worktree is ordinarily a shadow copy `git worktree remove` later destroys, so it is refused (`--run path rejected: …`) and nothing is recorded, rather than written to the shadow; a cwd with no determinable git root is refused separately, with its own distinct reason. One narrow exception (`#280`): a worktree-local candidate that resolves inside a linked worktree of this same repo, under a run-id-shaped `.claude-tweaks/pipelines/` segment, and is already an *initialized* run dir (carries `decisions.md`, `run-state.json`, or `config.yml` — not a bare `mkdir`), with no counterpart at the same pipelines-relative path under the main checkout, is adopted instead of refused — the recovery path for a session whose harness refused every main-checkout write and so had no anchored copy to name in the first place; see `_shared/pipeline-run-dir.md`'s "Worktree-local `--run` fallback (#280)". Refusal still exits 0 — the never-break-a-session invariant is not widened. `bin/wrap-up-engine.js` and `bin/materialize.js` carry the same guard on their `--run-dir`, where it surfaces as exit 2 instead (`docs/plugin-structure.md`'s command reference). The two resolver CLIs — `bin/resolve-profile.js` (`--run-dir`) and `bin/resolve-policy.js` (`--run`) — carry the *anchored-or-outside* variant instead (`worktree-detect.js`'s `checkRunDirAnchoredOrOutside`, exit 1, #1065): paths outside any checkout stay accepted for their documented journey/test use; the two-rule split's canonical statement is `plugin/skills/_shared/pipeline-run-dir.md`'s Anchoring section (the CLI-argument-boundary guard).
- Hook processes are spawned with the harness's own environment, so a `PIPELINE_RUN_DIR` exported inside a Bash tool call does not reach them; hooks instead resolve runs from the Bash call's cwd, and a commit issued from inside a worktree that contains no `.claude-tweaks/` resolves no run dir and is allowed (fail-open).
- **New pipeline-bookkeeping write verb: `hooks.js` subcommand, or a standalone sibling CLI?** `record-worktree`/`close-run`/etc. are `hooks.js` subcommands because they're hook-adjacent run-state writes with no independent precedent. `bin/log-decision.js` (#686) and `bin/stage-item.js` (#637) are standalone CLIs instead, each mirroring the other's shape (arg-parsing, `--run` anchoring, injectable-deps) rather than becoming `hooks.js` subcommands — once one pipeline-bookkeeping write CLI ships standalone, its sibling follows the same shape rather than forcing a rename into `hooks.js` (a silent breaking rename CLAUDE.md's expand-contract discipline forbids). Default to a standalone `bin/{name}.js` sibling when a same-purpose precedent CLI already exists; default to a `hooks.js` subcommand only for the first one, or for state genuinely coupled to hook enforcement itself.
- **Two resolutions, not one** (`context.js`'s `resolveRun`, since 6.47.0): enforcement reads the newest non-terminal run *regardless of owner* — E1's foreign-session warning exists precisely to tell a bystander the checkout belongs to someone else's worktree. Anything that **writes** (event breadcrumbs, `interrupted`/`lastEvent` stamps) uses the ownership-scoped `ctx.ownedRun` instead: a run owned by another session is never written to, and an unowned run is written to but tagged `attribution: "fallback"`. Ownership is stamped only by `record-worktree`, so runs that never provisioned a worktree stay unowned by design `[IL-96]`. Fallback attribution additionally skips *unadopted mints* — run dirs carrying neither `run-state.json` nor `decisions.md` (a `dispatch` Step 4 / `flow` Step 2.8 mkdir that no invocation initialized) — so an empty mint can never absorb foreign events; consequently the no-`--run` CLI fallback (`record-pr`/`close-run` — `record-worktree` no longer has one, #1124) only ever resolves an adopted run (#721). **Worktree-aware since #1410:** a candidate is also skipped when `classifyOwnership` (#1098's composite session+worktree-binding predicate) classifies it `'foreign'` — provably bound to a different, still-live worktree than the caller's own cwd, regardless of session id. This closes the cross-worktree shape (a concurrent sibling worktree's event — e.g. an `ask-user-question` answered in one session — landing in an unrelated run's `events.jsonl`, tagged `attribution: "fallback"`) without narrowing the fallback for any candidate lacking a provable worktree binding — `classifyOwnership` fails open to `'indeterminate'`, never `'foreign'`, on unprovable evidence. Both sides of that comparison must be provable, which bounds how far the skip reaches: the caller's own cwd must itself resolve inside a *linked* worktree (a caller in the main checkout — where most hook firings happen — classifies `'indeterminate'` and still guesses into the candidate), and the candidate's recorded `worktree` must still exist on disk as a directory. `classifyOwnership` also returns `'foreign'` on a bare session-id mismatch, but neither fallback arm reaches that branch: the unknown-caller arm has no session id to compare against, and the known-caller arm only ever tests candidates whose `run-state.json` records no `sessionId` at all.
- **Background convergence (`integration-model: pr-first` only):** `plugin/bin/lib/reconcile/` (fast-forward, worktree reap, claim release, run-dir archive, branch archival, merged remote-branch pruning, console execution, red-tip detection) runs from SessionStart and dispatch's own trigger points — a session that opened a run's PR need not be the one that finishes it, since state converges from GitHub, not from session continuity. **SessionStart splits the set in two (#820)**, and only SessionStart: the cheap read/detect checks (fast-forward, red-tip, console detection) run inline in the hook's own process, while the write-only janitorial ones (claim release, run-dir archive, branch archival, merged remote-branch pruning, worktree reap) run in a detached `node plugin/bin/hooks.js reconcile-background` child process — so their outcome is surfaced exactly once, on a LATER SessionStart firing, always one session's worth of latency behind. The inline pass additionally short-circuits entirely when another session in the same repo already ran it within a short TTL (`plugin/bin/lib/reconcile/cache.js`), trading that much staleness for a session start that costs nothing when sessions arrive in bursts. The `reconcile` subcommand and dispatch's own trigger points are unaffected — they still run the full set in one process. Red-tip is the one unconditional, inform-tier check in the set — a failing CI conclusion on the integration branch's tip surfaces at SessionStart regardless of `merge-verification` policy, since it's the only coverage for direct pushes no merge gate ever sees. Run-dir archive convergence has a blind spot, not a guarantee: `archive-merged.js` iterates via `iterRunDirsWithState`, which permanently skips any run whose `run-state.json` already reached `status: clean` — so a run that reached `clean` without being archived (a teardown path that marks terminal but misses the move) is invisible to this sweep forever, not just delayed. Archival must happen as part of teardown itself; `plugin/bin/residue.js`'s `pipeline-run` probe is the separate backstop that reads `.claude-tweaks/pipelines/` directly to catch dirs that already fell into this gap. Worktree reap never touches the calling session's own cwd, regardless of PR/lock state (#644, `reap-merged.js`'s `isOwnCwd`, skip reason `own-cwd`); a path stuck at `move-failed`/`removal-failed` for `RESIDUE_ESCALATE_THRESHOLD` consecutive passes (`cache.js`, persisted across process invocations so `reconcile-background` and the `reconcile`/`reconcile-summary` subcommands observe the same streak) escalates once via `escalate-residue.js` and never re-escalates while still failing. `node plugin/bin/hooks.js reconcile-summary` prints the one-line residue summary (`reconcile: {archived} archived, {stuck} stuck (oldest {age}), mirror ff {…}`) `/claude-tweaks:flow`'s closing report renders (`flow/summary-template.md`); the `reconcile` subcommand's JSON also carries the same line as `residueSummary`. A second, narrower blind spot (#848): `iterRunDirsWithState`'s `RUN_ID_RE` filter only recognizes the canonical dash-containing `YYYY-MM-DDT…` name — a non-canonical mint (e.g. a hand-typed `date -u +%Y%m%dT%H%M%S`, dashes dropped) is invisible to every check keyed off that enumeration, the same way an already-`clean` run is. Unlike that gap, this one is now surfaced rather than silent: `context.js`'s `findNonCanonicalRunDirs` scans for the dash-less shape and `reconcile`'s `index.js` reports any hit as a `non-canonical-run-dir` entry in `result.skipped` (naming the directories) on every pass, ahead of every other gate. All three run-dir mint sites now produce the canonical shape mechanically via `run-dir-resolve.js`'s `formatTimestamp()` (`resolve-run-dir --create`), so a fresh non-canonical name is not expected in practice — this is a defensive report, not a self-heal, since the directory is never renamed automatically.
- **`worktree-always` verdict banner (inform tier):** `session-start.js` prints one `worktree-always: ON (matched key: worktree-always|worktree.always)` / `OFF (no key)` line per session, sourced from `plugin/bin/lib/policy.js`'s `resolveWorktreeAlways` — the same resolver `pre-tool-use.js`'s gate calls, so the announcement can never disagree with enforcement (`docs/incident-log.md` `[IL-133]`). Silent when no `policy.yml` exists anywhere in the ancestor chain, and silent (falls through to the existing best-effort `catch`, no throw) on any parse failure — it cannot itself widen the never-break-a-session invariant.
- **Bookkeeping-stamps gate (block tier, IL-131):** `pre-tool-use.js`'s `checkBookkeepingStampsGate` denies a covered Edit/Write/NotebookEdit/commit/push once **this run's own** materialize commit has landed on the run's branch but `record-worktree` never stamped `run-state.json.worktree`, or — under a `pr-first` run — `record-pr` never stamped `run-state.json.pr`. Same ambiguity-resolves-to-allow posture as E1: no materialize commit yet, no resolved run, or a target outside a linked worktree all no-op. A run whose `decisions.md` already carries the mandated `PR-early run lifecycle: ... FAILED` degrade line is exempted from the PR-stamp deny — a genuine push/PR-create failure still degrades gracefully, never a hard block, and the deny message names `bin/log-decision.js` as the runnable way to log it. A second, narrower exemption (`#989`) covers the chicken-and-egg case the degrade-line exemption doesn't: a Bash `git push` whose every target is establishing that branch's upstream tracking ref for the first time (`hasNoUpstreamYet` — `@{u}` fails with a git-error exit) is allowed through even with no PR yet recorded, because that push **is** `pr-early-run-lifecycle.md` Step 2 itself — without it, the PR-stamp deny would fire on the one action a PR stamp cannot exist without, making `build/worktree-setup.md` Step 6 — the caller that invokes that whole procedure — structurally impossible to ever complete. (Note the two step numbers name two different files: `pr-early-run-lifecycle.md` itself has only Steps 1–4.) It is one-shot and never persisted as `prExempt`: a later push of an already-tracked branch still falls through to the ordinary deny when no PR was ever recorded, preserving IL-131's "keep pushing forever, never open the PR" close. Reuses `GATE_COVERAGE`'s existing tool/gitAction list — no `hooks.json` or coverage-prose change. Five scoping rules keep it from over- or under-firing:
  - **Run-scoped sentinel.** `hasMaterializeCommit(worktreeRoot, runDir)` builds its pathspec from `path.basename(runDir)` — `.claude-tweaks/pipelines/{run-id}/work` plus the multi-record `.claude-tweaks/pipelines/{run-id}/spec-*/work/*` — relative to the worktree root, where `flow/materialize.md`'s worktree-local mirror of the run dir lives. A repo-root-relative `work` pathspec could never match the canonical write location (the gate would be inert everywhere), and a widened `*/work/*` would match any legacy pre-anchoring top-level `work/*-spec.md` still in history and arm the gate on every branch. The multi-record arm needs its **trailing** `/*`: git's default pathspec wildcards only apply to the final path component, so `spec-*/work` never matches (measured).
  - **Ownership.** `ctx.runDir` reaches the gate unfiltered by session id (`ctxLib.resolveRunDir(cwd, process.env)`), so the run it names may be a live sibling session's. On a provable owner-vs-caller mismatch the gate warns instead of denying, exactly as E1 does — otherwise the deny's own `record-worktree --run` remediation would tell the agent to corrupt that sibling's `run-state.json` (the `--run` rule at the top of this list). On the `record-worktree` branch specifically — where `runState.worktree` is provably unset, so `sessionId` (stamped together with `worktree`) is almost always unset too and the owner-vs-caller comparison can barely engage — a second signal augments it (`hasDistinctOwnedRun`, #1259): a caller whose own `ctx.ownedRun.dir` already names a *different*, already-recorded run is treated as foreign even with no `sessionId` on either side. The `record-pr` branch keeps `isForeignSessionCall` alone, unchanged.
  - **Path exemptions.** A file-tool target inside `.claude-tweaks/pipelines/` or at `.claude-tweaks/policy.yml` is exempt, resolved against the *target's* own repo root (run dirs are anchored to the main checkout, so `decisions.md` normally sits outside the worktree). Without this the PR-stamp deny's own escape hatch — writing that degrade line — would itself be deniable.
  - **Foreign repos.** For the Bash branch, each git target's own main-checkout root is compared against this worktree's; a command targeting only unrelated repositories (`git -C /elsewhere commit`) is not gated. Mirrors E1's `mainRoot`/`actualMainRoot` check, including its unprovable-case posture.
  - **The run's pin, not a fresh detection.** The PR branch resolves `integration-model` through `policy-schema.js`'s `resolvePolicyConfig({ runDir })` (policy.yml + `{run-dir}/config.yml`), falling back to forge detection only when the run pinned nothing — per `_shared/integration-model.md`'s "re-detecting mid-run" anti-pattern. Both stamps already present short-circuits before any git or `gh` spawn — and so does `runState.worktree` alone once `runState.prExempt` is set: the first time the PR branch proves no further PR-stamp denial is possible for this run (model resolved cleanly to non-pr-first, or pr-first with the degrade line already logged in decisions.md — both permanent for the life of the run), it persists `prExempt: true` to `run-state.json` so every later covered call — including a `local-merge` run's steady state, which never sets `runState.pr` — skips repoInfo, `hasMaterializeCommit`, and this resolution entirely. Persisted rather than cached in-memory because each hook invocation is a fresh process. Never persisted when the resolution itself threw (a transient failure, not a provable verdict, unlike the two cached cases which are immutable for the life of the run); persisted regardless of caller session identity — unlike the worktree/PR stamps themselves, `prExempt` names no owning session, so a provably-foreign call computing it is not the corruption hazard the deny's own remediation text warns about.

**Not covered here: the harness's own compound-Bash refusal.** A worktree-isolated session's Bash tool call can be refused outright ("too complex to verify that it stays inside the worktree") for a `;`-separated sequence, a `for`/`while` loop, or other shapes the Claude Code CLI harness can't cheaply verify stays inside the worktree — this is harness code, not a module in `plugin/bin/lib/hooks/`, and nothing here can alter it.
