# Hooks

All hook registrations route through `plugin/bin/hooks.js <event>` — one dispatcher, one module per event in `plugin/bin/lib/hooks/`. Rules:

- **Never break a session.** Every path — including a PreToolUse deny — exits 0; no module ever sets a non-zero `exit`. A deny is communicated entirely via `hookSpecificOutput.permissionDecision: 'deny'` in the stdout JSON, not the process exit code (see `pre-tool-use.js`'s own header comment for why exit 2 doesn't work for this). New modules must pass the garbage-stdin invariant test in `tests/hooks-dispatcher.test.js`.
- **Tiered posture per `_shared/auto-mode-contract.md`:** block (E1 wrong-checkout commit; the `worktree-always` policy gate), warn (non-blocking systemMessage), inform (SessionStart additionalContext), log (append to the run dir's `events.jsonl`). What that gate covers, what it deliberately doesn't, and its one `.claude-tweaks/pipelines/` exemption are stated once — in `plugin/skills/_shared/policy-schema.md`'s `worktree-always` coverage block, pinned to `pre-tool-use.js`'s exported `GATE_COVERAGE` by `tests/hooks-gate-coverage.test.js`. Don't restate the list here or anywhere else; five files did and all five went stale `[IL-93]`.
- **Project-agnostic by construction:** modules key off plugin-owned state (`$PIPELINE_RUN_DIR`, `.claude-tweaks/pipelines/`, `.claude-tweaks/policy.yml`), never off project structure. E1/E2/E3 no-op without a resolved run dir — the `worktree-always` policy gate is the one PreToolUse check that is deliberately run-independent, since its job is to require a worktree even before any pipeline run exists. `post-tool-use.js`'s closing-keyword check (warn tier) is the analogous exception on the PostToolUse side — it fires on any `git commit` regardless of run-dir state, since the gap it catches (a fix commit made outside the structured `/specify` → `/build` → `/wrap-up` pipeline, with no closing keyword) is exactly a commit that would never resolve a run dir in the first place. The deferred-subproject capture check (also warn tier) mirrors this on `Write`: it fires on any write to `docs/superpowers/specs/*-design.md` regardless of run-dir state, since a brainstorming session that hasn't reached `/specify` yet has no pipeline run dir to gate on either.
- **Ambiguity resolves to allow** — E1 denies only provable mismatches. A recorded worktree whose path no longer exists also resolves to allow (fail-open) — tear-down without close-run ends enforcement, not the session. Ownership counts toward provability: `record-worktree` stamps the recording session's id (`CLAUDE_CODE_SESSION_ID`), and a wrong-checkout commit from a *different* session is allowed with a warn (`wd-foreign-session` event) instead of denied; missing identity on either side falls back to deny.
- Run-dir state files written by hooks: `events.jsonl` (append-only typed events) and `run-state.json` (status: active | interrupted | clean, worktree assignment, owning session id). Skills write run-state only through `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" record-worktree <path>` / `close-run` (plus the one creation-time stamp: wrap-up Phase 1 writes the initial `run-state.json` with `createdBy` when it creates a standalone run dir). `resolve-run-dir --create` (#692) may mint the run *directory* itself (mkdir, plus `decisions.md`/`staged/` under `--standalone`) — but it never touches `run-state.json`: that first write is still exclusively `record-worktree`/`close-run`'s, or wrap-up's own creation-time stamp above.
- **An explicit `--run <dir>` must be *anchored*, not merely real** (`#790`/`[IL-127]`). The six subcommands that accept it — `record-worktree`, `record-pr`, `spec-status`, `close-run`, `check-resume-freshness`, `archive-run` — resolve the value against the caller's cwd and then require it to sit under the main checkout, the same adoption-time check `_shared/pipeline-run-dir.md` applies to `PIPELINE_RUN_DIR`. A path that exists but resolves inside a linked worktree is a shadow copy `git worktree remove` later destroys, so it is refused (`--run path rejected: …`) and nothing is recorded, rather than written to the shadow; a cwd with no determinable git root is refused separately, with its own distinct reason. Refusal still exits 0 — the never-break-a-session invariant is not widened. `bin/wrap-up-engine.js` and `bin/materialize.js` carry the same guard on their `--run-dir`, where it surfaces as exit 2 instead (`docs/plugin-structure.md`'s command reference).
- Hook processes are spawned with the harness's own environment, so a `PIPELINE_RUN_DIR` exported inside a Bash tool call does not reach them; hooks instead resolve runs from the Bash call's cwd, and a commit issued from inside a worktree that contains no `.claude-tweaks/` resolves no run dir and is allowed (fail-open).
- **Two resolutions, not one** (`context.js`'s `resolveRun`, since 6.47.0): enforcement reads the newest non-terminal run *regardless of owner* — E1's foreign-session warning exists precisely to tell a bystander the checkout belongs to someone else's worktree. Anything that **writes** (event breadcrumbs, `interrupted`/`lastEvent` stamps) uses the ownership-scoped `ctx.ownedRun` instead: a run owned by another session is never written to, and an unowned run is written to but tagged `attribution: "fallback"`. Ownership is stamped only by `record-worktree`, so runs that never provisioned a worktree stay unowned by design `[IL-96]`. Fallback attribution additionally skips *unadopted mints* — run dirs carrying neither `run-state.json` nor `decisions.md` (a `dispatch` Step 4 / `flow` Step 2.8 mkdir that no invocation initialized) — so an empty mint can never absorb foreign events; consequently the no-`--run` CLI fallback (`record-worktree`/`record-pr`/`close-run`) only ever resolves an adopted run (#721).
- **Background convergence (`integration-model: pr-first` only):** `plugin/bin/lib/reconcile/` (fast-forward, worktree reap, claim release, run-dir archive, branch archival, merged remote-branch pruning, console execution, red-tip detection) runs from SessionStart and dispatch's own trigger points — a session that opened a run's PR need not be the one that finishes it, since state converges from GitHub, not from session continuity. **SessionStart splits the set in two (#820)**, and only SessionStart: the cheap read/detect checks (fast-forward, red-tip, console detection) run inline in the hook's own process, while the write-only janitorial ones (claim release, run-dir archive, branch archival, merged remote-branch pruning, worktree reap) run in a detached `node plugin/bin/hooks.js reconcile-background` child process — so their outcome is surfaced exactly once, on a LATER SessionStart firing, always one session's worth of latency behind. The inline pass additionally short-circuits entirely when another session in the same repo already ran it within a short TTL (`plugin/bin/lib/reconcile/cache.js`), trading that much staleness for a session start that costs nothing when sessions arrive in bursts. The `reconcile` subcommand and dispatch's own trigger points are unaffected — they still run the full set in one process. Red-tip is the one unconditional, inform-tier check in the set — a failing CI conclusion on the integration branch's tip surfaces at SessionStart regardless of `merge-verification` policy, since it's the only coverage for direct pushes no merge gate ever sees. Run-dir archive convergence has a blind spot, not a guarantee: `archive-merged.js` iterates via `iterRunDirsWithState`, which permanently skips any run whose `run-state.json` already reached `status: clean` — so a run that reached `clean` without being archived (a teardown path that marks terminal but misses the move) is invisible to this sweep forever, not just delayed. Archival must happen as part of teardown itself; `plugin/bin/residue.js`'s `pipeline-run` probe is the separate backstop that reads `.claude-tweaks/pipelines/` directly to catch dirs that already fell into this gap.
- **`worktree-always` verdict banner (inform tier):** `session-start.js` prints one `worktree-always: ON (matched key: worktree-always|worktree.always)` / `OFF (no key)` line per session, sourced from `plugin/bin/lib/policy.js`'s `resolveWorktreeAlways` — the same resolver `pre-tool-use.js`'s gate calls, so the announcement can never disagree with enforcement (`docs/incident-log.md` `[IL-133]`). Silent when no `policy.yml` exists anywhere in the ancestor chain, and silent (falls through to the existing best-effort `catch`, no throw) on any parse failure — it cannot itself widen the never-break-a-session invariant.

**Not covered here: the harness's own compound-Bash refusal.** A worktree-isolated session's Bash tool call can be refused outright ("too complex to verify that it stays inside the worktree") for a `;`-separated sequence, a `for`/`while` loop, or other shapes the Claude Code CLI harness can't cheaply verify stays inside the worktree — this is harness code, not a module in `plugin/bin/lib/hooks/`, and nothing here can alter it. Easy to conflate with this file's own `worktree-always` gate since both fire on a Bash call inside a worktree (`#174` was originally filed against the wrong one) — see `docs/skill-authoring.md`'s "Harness-level worktree Bash guard vs. the plugin's PreToolUse gate" for how the two are told apart, and `plugin/skills/_shared/scratch-worktree.md`'s "## 7. Shell constraint" for the empirically observed pass/refuse boundary.
