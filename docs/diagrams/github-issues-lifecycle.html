The GitHub-issue lifecycle

Five skills, one atomic lock. code-health and harness-health file issues; /claude-tweaks:triage is the sole grantor of build authorization; /claude-tweaks:flow executes headlessly once claimed; /claude-tweaks:wrap-up closes the loop; /claude-tweaks:tidy sweeps up drift.

THE HEADLINE

Authorization is the security boundary

An issue body is untrusted, prompt-injectable input. GitHub's own permission model is the gate: applying a status:* tier label requires triage permission, so the label is a maintainer's signature. Headless triage dispatch may only downgrade or strip a tier it reads — it never originates one. Only a human running bare /triage grants trust.

One ref, two mirrors

  • refs/claims/issue-N is the actual lock — atomic GitHub-refs test-and-set
  • An issue comment mirrors it for humans, carries TTL metadata
  • status:in-progress mirrors it again for board/UI visibility — cosmetic, no locking semantics

Backlog issues take a side door

/capture's inbox/parked issues promote via /specify directly, skipping Triage's risk/effort tiering entirely — but once a spec starts building, they join the same claim-lock and close-via-merge machinery every other issue uses.
