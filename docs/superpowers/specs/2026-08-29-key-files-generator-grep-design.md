# Key Files generated-file grep — design

Origin: work record #1321 (`needs:definition` redirect). Incident: #326's spec named only
`.github/workflows/track-issue-fixes.yml` in Key Files; the actual source of truth,
`plugin/bin/lib/issue-branch-tracking.js`'s `generateWorkflowYaml()`, was never listed, so the
build edited the generated file and not its generator.

## Problem

`/claude-tweaks:specify`'s Key Files composition (shaping mode and decomposition Step 3 — not
`/flow`'s materialize, which only *reads* Key Files; #1321's "materialize procedure" wording is
corrected here) has no check for whether a named file is itself generated by another module in
the repo. When it is, the generator is the file that must be edited, and omitting it sends the
build at the wrong target.

## Decision

Adopt a **generated-file grep**: a documented, repeatable grep procedure mirroring the existing
rename-grep in `spec-template.md`'s `### Key Files` guidance, in the opposite direction —
rename-grep finds a surface's *consumers*; this check finds a file's *producer*.

Rejected alternatives (recorded because #1321 proposed one of them):

- **#1321's multi-signal heuristic** (export-name matching `generate*/render*/build*`,
  `tests/` import tracing, "output plausibly matches"): ~20 modules in `plugin/bin/lib/` match
  the export-name pattern today and most are runtime renderers that never produce a committed
  file, so the signal is mostly noise; "plausibly matches" is not a repeatable procedure.
- **A mechanized `bin/lib` CLI**: deterministic, but classification of a hit (producer vs
  consumer) still needs a read-and-judge step, so the CLI could only emit candidates — full CLI
  contract cost for what one grep does. Revisit only if the prose check proves ad hoc in
  practice.

## The check

New paragraph in `plugin/skills/specify/spec-template.md`'s `### Key Files` guidance, placed
directly after the rename-grep paragraph, same voice. Procedure it documents:

1. For each composed Key Files entry, grep executable code — `plugin/bin/`, `plugin/hooks/`,
   `scripts/`, `tools/` — for the entry's **basename**; fall back to the repo-relative path when
   the basename is generic (`cache.js`, `index.js`). Exclude the entry itself and the
   rename-grep's historical-mention skip list (archived run specs, record bodies, incident log).
2. Read each hit and classify: a module that **generates or writes the target's content** is its
   source of truth → add it to Key Files as
   `- `{module}` — source of truth: generates `{target}``, and name the generator the primary
   edit target with the generated file secondary. A hit that merely *reads* the target is a
   consumer (rename-grep territory) → skip.
3. The paragraph carries the grep as a byte-pinnable snippet with a `{basename}` placeholder,
   e.g.:

   ```bash
   grep -rln "{basename}" plugin/bin plugin/hooks scripts tools 2>/dev/null
   ```

Conservative by construction: a module naming the exact path/basename either produces, consumes,
or documents the target, and one read disambiguates. Accepted miss: a generator that builds the
target path by string concatenation never matches — that is the conservatism #1321's Gotcha asks
for.

## Consumer wiring

- `plugin/skills/specify/spec-template.md` — the contract, stated once (new paragraph above).
- `plugin/skills/specify/shaping-mode.md` — the Key Files sentence (currently line 68) that
  cites the rename-grep gains one clause: "…plus every generator module the generated-file grep
  in the same guidance turns up."
- `plugin/skills/specify/record-creation-subissues.md` — verify at build time whether it carries
  a parallel citation needing the same one-clause touch (initial grep found none; decomposition
  Step 3 inherits via its wholesale `spec-template.md` reference).

## Test (AC 2's real-pair fixture)

One `node --test` conformance suite (e.g. `tests/spec-template-generator-grep.test.js`),
following the `skill-prose-conformance-tests` conventions:

- pins that the paragraph and its snippet exist in `spec-template.md`;
- extracts the byte-pinned snippet, substitutes `track-issue-fixes.yml`, executes it against the
  live repo, and asserts `plugin/bin/lib/issue-branch-tracking.js` appears in the output — the
  real generator/generated pair;
- a negative control substituting a basename with no producer, asserting zero executable-code
  hits — proving the check discriminates rather than flagging everything.

## Acceptance criteria

1. `spec-template.md`'s `### Key Files` documents the generated-file grep with an executable
   snippet; `shaping-mode.md`'s citation sentence names it alongside the rename-grep.
2. The conformance suite's live probe surfaces `plugin/bin/lib/issue-branch-tracking.js` from
   `track-issue-fixes.yml`, and its negative control passes.
3. No literal placeholder tokens in any composed prose (spec-shaped-body check constraint).

## Scope

One agent-sized unit: two prose paragraphs plus one test file. Decomposition is expected to
collapse (Step 2.6) with no parent — origin record #1321 shaped in place.
