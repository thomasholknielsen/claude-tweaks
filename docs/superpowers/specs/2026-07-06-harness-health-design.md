# Harness Health — Generalizing Skill-Health to Rules and CLAUDE.md

**Date:** 2026-07-06
**Status:** Approved (brainstorm 2026-07-06)
**Origin:** `/claude-tweaks:skill-health` (shipped 2026-07-05) only audits `.claude/skills/*.md`. The user wants to broaden it into an "ai-harness-health" watchman that also audits `.claude/rules/*.md` and CLAUDE.md — the other in-repo, git-tracked documentation a project accumulates over time and that can silently drift the same way skill docs do.

## Problem

`skills/skill-health/SKILL.md` explicitly states: "Not for: auditing CLAUDE.md or `.claude/rules/` (out of scope for this skill)." That boundary was deliberate at the time, but leaves two gaps:

1. `.claude/rules/*.md` (path-scoped conventions, generated by `/init` Phase 7) can go stale exactly like skills — a renamed/removed directory leaves a rule's `paths:` glob matching nothing, and nothing catches it between full `/init` reruns.
2. CLAUDE.md — the single highest-leverage document in the harness, read into every session — has no continuous drift-check at all. `/init`'s Update Mode covers it, but only when manually re-run in full.

Both gaps share the same shape skill-health already solves for skills: a rotation/staleness watchman, shared judgment logic, GitHub-issue-based findings with safe auto-apply for the additive+high-confidence+high-reversibility case. This design generalizes the existing engine rather than building a parallel one.

## Scope

**In scope:** skills (unchanged), rules (new), CLAUDE.md (new — drift-check only, never auto-applies).

**Explicitly deferred (separate future design):**
- **Memory audit** (`~/.claude/projects/{slug}/memory/`) — lives outside the repo, isn't git-tracked (no churn signal), and almost certainly isn't reachable from a cloud-scheduled Routine (different execution environment than the local machine). Needs its own plumbing design once those constraints are worked out.
- **README.md audit** — a real candidate structurally similar to CLAUDE.md, but left for a follow-on once this three-kind shape proves out.
- **Agent definitions** (`.claude/agents/*.md` or this plugin's own `agents/*.md`) — considered and dropped from scope entirely.
- **Gap detection for rules/CLAUDE.md** — "propose a brand-new artifact where none exists" (`kind: "new-skill"` today) stays skill-only. Rules and CLAUDE.md only ever produce `kind: "patch"` findings against their own existing content.

## Rename

Full rename: `/claude-tweaks:skill-health` → `/claude-tweaks:harness-health`. The old name no longer describes the scope, and this repo has **zero existing `skill-health`-labelled GitHub issues** (confirmed via `gh issue list --label skill-health --state all`), so there is no dedup-migration shim to build — a clean rename, consistent with this project's stated aversion to backwards-compatibility shims.

Renamed:
- Skill directory: `skills/skill-health/` → `skills/harness-health/` (incl. `routine-template.yml`).
- Engine: `bin/skill-health.js` → `bin/harness-health.js`, `bin/lib/skill-health/*` → `bin/lib/harness-health/*` (incl. `tests/`).
- Persistent state root: `.claude-tweaks/skill-health/` → `.claude-tweaks/harness-health/`.
- Shared judge procedure: `skills/_shared/skill-health-analysis.md` → `skills/_shared/harness-health-analysis.md`.
- GitHub label: `skill-health` → `harness-health` (and `skill-health:{classification}` → `harness-health:{classification}`).

Cross-references to update (bidirectional convention): `CLAUDE.md` (skill list, structure diagram, sub-file table), `README.md`, `skills/help/reference-card.md`, `skills/init/SKILL.md` + `skill-template.md`, `skills/routine/SKILL.md`, `skills/tidy/SKILL.md` + `scan-procedures.md`, `skills/wrap-up/SKILL.md` + `skill-curation.md`, `skills/_shared/github-pr-scan.md`, `package.json` test script. Historical docs (`docs/superpowers/plans/2026-07-05-skill-health.md`, `docs/superpowers/specs/2026-07-05-skill-health-design.md`) are left untouched as historical record — not rewritten, not cross-referenced as current.

## Unified target model & domain signals

`bin/lib/harness-health/scope.js` generalizes `listSkills()` into `listTargets(root)`, which aggregates three listers into one flat pool, each item tagged `{ kind: 'skill' | 'rule' | 'claude-md', id, path }`:

- **`listSkills`** — unchanged, `.claude/skills/*.md`, domain-path signal via the existing backtick-heuristic (`extractDomainPaths`).
- **`listRules`** (new) — `.claude/rules/*.md`. Domain-path signal uses the rule's own `paths:` frontmatter glob directly — a precise, structured signal, strictly better than the backtick heuristic skills need.
- **`listClaudeMd`** (new) — single-item list, `[{ kind: 'claude-md', id: 'CLAUDE', path: <root>/CLAUDE.md }]` if the file exists. Reuses the same `extractDomainPaths`/`domainChurn` functions unchanged — CLAUDE.md is dense with backtick-quoted paths already, so no special-casing is needed for its churn signal.

`selectTarget` (the stale-then-churn rotation algorithm) needs no algorithmic change — Phase 1 (force-pick anything unaudited past `STALE_DAYS`) and Phase 2 (score non-stale candidates by domain churn, pick highest) both run unchanged over the heterogeneous pool.

Cursor/cache keys are namespaced by kind (`"skill:auth"`, `"rule:api-errors"`, `"claude-md:CLAUDE"`) to prevent an id collision between e.g. a skill and a rule that happen to share a name.

CLI: `next-target` gains a `--kind <skill|rule|claude-md>` filter. `--skill <name>` becomes the generic `--target <id>` (optionally paired with `--kind` to disambiguate a colliding id).

## What "drift" means per kind

All three kinds share the same procedure — Step 1 mechanical evidence pre-checks → Step 2 dimension judgment → Step 5 adversarial verify gate — but which dimensions actually carry weight differs.

**Skills (unchanged):** all six original dimensions apply as today (pattern accuracy, convention drift, missing patterns, stale examples, anti-pattern gaps, decision-framework completeness).

**Rules:** a rule is one path-scoped convention, not a multi-section document, so most of the six collapse to two mechanical, high-confidence checks:
1. **Glob resolution** — does `paths:` still match ≥1 real file? Zero matches is a strong, mechanical "stale rule" finding.
2. **Convention-adherence ratio** — of files matching `paths:`, what fraction actually follow the stated convention (reuses the existing quantified grep-ratio check verbatim).

The second check needs an explicit judgment guard: a low adherence ratio has two different causes, and only one belongs to this skill. If the ratio is low because **the codebase's shape moved on** (the glob now covers files the rule was never meant for), that's documentation drift — harness-health's job. If it's low because **files that should comply, don't** (the rule is still correct; code violates it), that's a code-quality/compliance problem — `/recon`'s job. The judge must reason about *why* the ratio is low, not just report the number, to avoid manufacturing findings that are really `/recon` territory.

**CLAUDE.md:** structurally closest to a skill (multi-section prose, just repo-wide instead of domain-scoped), so the same mechanics reuse directly: stale-example `ls`/command checks over every backtick-quoted path, quantified grep-ratio checks over documented conventions/Don'ts, and a "missing patterns" scan of repo-wide commits since last audit for a new recurring convention not yet mentioned (still a `kind: "patch"` addition to an *existing* section — never a new artifact, consistent with gap-detection staying skill-only).

## New dimensions: template conformance & best-practice fit

Two dimensions are added on top of the original six, applied across all three kinds:

- **Dimension 7 — Template/Structural Conformance:** does this artifact still match the structure its own generator established?
- **Dimension 8 — Best-Practice/Harness-Performance Fit:** does it follow known practices for getting an LLM harness to actually perform well (clear triggers, no cross-skill overlap, right-sized scope, concision)?

This plugin has already authored the reference material for both — the judge reads these sources live rather than duplicating them into a frozen best-practices file, so a future tightening of the templates is picked up automatically:

| Kind | Dimension 7 reference (structural template) | Dimension 8 reference (best-practice) |
|---|---|---|
| Skill | CLAUDE.md's own "SKILL.md structure" convention (frontmatter, interaction directive, H1, lifecycle diagram, When to Use, Input resolution, workflow steps, Anti-Patterns table, Relationship table) + `skills/init/skill-template.md` | `superpowers:writing-skills` — trigger clarity, scope sizing, avoiding overlap |
| Rule | `skills/init/rules-template.md`'s frontmatter shape (`paths:` + concise imperative body) | Same file — its own guidance ("path-specific only; project-wide belongs in CLAUDE.md") *is* the best-practice check: a suspiciously broad glob (matching most of the repo) should be a CLAUDE.md convention instead |
| CLAUDE.md | `skills/init/claude-md-template.md`'s "Principles" section (150-line budget, observed-not-aspirational, required sections, Working Approach verbatim) | Same file — its Principles already are the best-practice checklist |

For CLAUDE.md specifically, this unlocks several new, largely mechanical checks:
- **Line budget** — `wc -l CLAUDE.md` vs. 150 lines, a deterministic Step-1-style evidence check.
- **Observed-not-aspirational** — flag language ("should", "TODO", "need to add") describing infrastructure that doesn't exist yet; that belongs in INBOX.
- **Working Approach present verbatim** — structural presence check (mandated unmodified in every generated CLAUDE.md).
- **Don'ts are guardrails, not wishes** — every Don't must describe an *existing* pattern (grep-checkable, same evidence style as convention-drift), never aspirational infrastructure.
- **Philosophy matches current maturity** — re-derive today's maturity signal (the same classification `/init` Phase 2h would compute) and compare to what the Philosophy section says; flags e.g. a project that shipped to real users since the CLAUDE.md was written but still reads "Greenfield."
- **Project Defaults / claude-tweaks Pipeline sections in sync with the installed plugin version** — does the documented auto-mode-policy lever list match what the currently installed claude-tweaks version actually supports? This is a distinct kind of drift, checked against the plugin's own evolving contract rather than the target project's source.

## Finding shape, fingerprint, labels

`skill` field renamed to generic `target`. New fields: `assetType: "skill" | "rule" | "claude-md"`, `category: "drift" | "template-conformance" | "best-practice"`. `kind` (`"patch" | "new-skill"`) is unchanged.

Fingerprint basis becomes `[assetType, target, section, normalizedDescription]` (adding `assetType` prevents cross-kind id collisions); id prefix `skillhealth-` → `harnesshealth-`.

Issue titles reflect asset type explicitly: "Skill drift: auth — Key Patterns", "Rule drift: api-errors — paths glob", "CLAUDE.md drift: Conventions", "New skill candidate: queue-retry-pattern".

## Auto-apply policy

Unchanged criteria for skills and rules: `additive` + `high` confidence + `high` reversibility → direct `Edit` + commit. One added condition: `assetType !== 'claude-md'` — CLAUDE.md findings **always** file as a GitHub issue for human review, regardless of classification/confidence/reversibility. CLAUDE.md governs every future session's behavior ("These instructions OVERRIDE any default behavior and you MUST follow them exactly"); an unattended routine auto-editing it carries outsized blast radius compared to auto-editing one skill's documentation.

The `category` field needs no separate auto-apply rule — a best-practice or template-conformance fix that actually changes meaning will naturally classify as `restructural` under the existing gate, routing it to a filed issue without new mechanism.

## Ripple effects on init/wrap-up (noted, not required by this design)

`/claude-tweaks:init` Phase 6 and `/claude-tweaks:wrap-up` Step 7 already consume the same shared procedure for their own scope models (currently skill-only: init's whole-codebase reconnaissance, wrap-up's finished-spec changed files). Once the shared file's Finding Shape generalizes, those two callers could propose rule/CLAUDE.md patches too, once their own scope-selection logic starts passing those files into the same judge call. That is a separate, smaller follow-on decision — this design does not require it.

## Testing approach

`bin/lib/harness-health/*.js` keeps `node --test` coverage for the deterministic parts (mirroring the existing skill-health suite): `listTargets`/`selectTarget` across the unified pool, cursor namespacing by kind, fingerprinting with the new `assetType` field, and the CLAUDE.md-never-auto-applies gate. The LLM-judgment half (the 8-dimension check) isn't unit-testable; verified via `--dry-run` runs during development, same convention skill-health already established.

## Explicitly out of scope

- **Memory audit** — different plumbing entirely (outside the repo, no git churn signal, no Routine access); a separate future design once that plumbing is worked out.
- **README.md audit** — deferred to a follow-on once the three-kind shape (skill/rule/CLAUDE.md) proves out.
- **Agent definitions** — considered, dropped from scope entirely.
- **Gap detection for rules/CLAUDE.md** (proposing brand-new artifacts) — stays skill-only; rules/CLAUDE.md only ever produce patches against existing content.
- **A cross-project harness-health rollup** — no mechanism to see status across every project it's instantiated in, same deferral skill-health's own design already made.
