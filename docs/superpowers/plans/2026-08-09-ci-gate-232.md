# CI Test Gate (#232) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions workflow that runs `npm test` on every push to `main` and every pull request, so the 2500+ test suite gates merges automatically.

**Architecture:** One new workflow file, `.github/workflows/test.yml`, alongside the existing `eval-benchmark.yml` (which stays `workflow_dispatch`-only and untouched). No install step: the repo ships zero npm dependencies (`package.json` has no `dependencies`/`devDependencies` — "test harness only"), and `node --test` is built into Node 18+, so the job is checkout → setup-node → `npm test`.

**Tech Stack:** GitHub Actions (`actions/checkout@v4`, `actions/setup-node@v4`), Node 20 (LTS, satisfies the Node 18+ floor), npm scripts already defined in `package.json`.

## Global Constraints

- Node version floor: 18+ (CLAUDE.md Stack table) — use Node 20 LTS.
- `npm run test:perf` is deliberately excluded from CI (timing budgets are machine-sensitive; excluded from `npm test` by design per docs/plugin-structure.md).
- `evals/` is a separate Node project — the workflow must not install or run it (`npm test`'s glob list already excludes it).
- Do not modify `.github/workflows/eval-benchmark.yml`.
- Triggers must be exactly: `push` restricted to `main`, plus `pull_request`. No broad `push: '**'`.
- A `concurrency` group must cancel superseded runs on the same ref (~20 pushes/day measured cadence).
- Several test suites create git fixtures that commit — a fresh CI runner has no git identity configured, so the job must set `GIT_AUTHOR_*`/`GIT_COMMITTER_*` env vars.

### Task 1: Create the CI workflow

**Files:**
- Create: `.github/workflows/test.yml`

**Interfaces:**
- Consumes: `package.json`'s existing `test` script (`node --test tests/ …` glob list) — unchanged by this task.
- Produces: a required-check-eligible workflow named `test` that later branch-protection configuration (out of scope here) can pin.

- [ ] **Step 1: Write the workflow file**

Create `.github/workflows/test.yml` with exactly:

```yaml
name: test

on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: test-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    env:
      # Several suites build git fixtures that commit; CI runners have no git identity.
      GIT_AUTHOR_NAME: ci
      GIT_AUTHOR_EMAIL: ci@invalid.example
      GIT_COMMITTER_NAME: ci
      GIT_COMMITTER_EMAIL: ci@invalid.example
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      # No install step: the plugin ships zero npm deps, and node --test is built in.
      - run: npm test
```

- [ ] **Step 2: Verify the command CI will run is green locally**

Run: `npm test` (from the worktree root)
Expected: PASS — full suite green. This is the exact command the workflow executes; a local red here means the workflow would fail on introduction, violating the spec's "green on its own introduction" acceptance criterion.

- [ ] **Step 3: Structural checks on the workflow file**

Run: `grep -c "workflow_dispatch" .github/workflows/test.yml`
Expected: `0` (this workflow must not absorb or shadow the eval workflow's manual trigger).

Run: `grep -n "branches: \[main\]" .github/workflows/test.yml`
Expected: one hit, under `push:` (narrow trigger confirmed).

Run: `grep -n "cancel-in-progress: true" .github/workflows/test.yml`
Expected: one hit (concurrency cancellation confirmed).

Run: `grep -rn "npm install\|npm ci" .github/workflows/test.yml`
Expected: no hits (zero-dep repo — an install step would be dead weight and imply a lockfile contract that doesn't exist).
