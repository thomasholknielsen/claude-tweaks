# Phase 4 execution — Execute Approved Actions and Verify

Loaded by `/claude-tweaks:wrap-up`'s Phase 4 execution step when at least one approved action exists. Holds the dry-run preview branch, the `MULTISPEC_REVIEW_DEFER` skip list, the full apply list, the closing-keyword carrier commit, and the verification checklist that gates the closure line.

**Dry-run mode.** When `--dry-run` was passed (Phase 1's Flags), skip actual execution entirely — print each planned cleanup / configuration / skill / acceptance-labeling action as a preview line instead of running it, skip the final commit and the closing line, and stop after the phase-trace report. This applies whether the Review Console rendered (which already previewed instead of applied — see `review-console.md`'s "Dry-run mode") or was skipped — and the console has only two skips: `MULTISPEC_REVIEW_DEFER=1`, and the empty-console fast path.

Execute the cleanup planned in Phase 4's cleanup-planning step (canonical list in `cleanup-procedures.md`) plus the configuration / skill updates approved at the Review Console — the console is the sole approval gate, in every mode. The 8 cleanup items, in execution order, are defined in `cleanup-procedures.md`'s canonical list — do not re-enumerate here. Filter rows by Condition.

**MULTISPEC_REVIEW_DEFER branch:** When `$MULTISPEC_REVIEW_DEFER=1` is set, this step SKIPS the state-changing cleanups marked deferred in `cleanup-procedures.md` (items 3 Design caches, 4 Git worktree, 6 Ephemeral dev server, 7 Issue claim release, 8 Pipeline run dir archival). Those defer to `/flow`'s consolidated multi-spec Review Console at end-of-run, which has authority to apply or override them across all specs in the run. This step still executes the idempotent cleanups (items 1 Execution plans, 2 Open items ledger, 5 Record/spec lifecycle) — those do not interact with parent-orchestrated cleanup.

After the cleanup, also apply:

- **Documentation** — apply the registry / doc edits collected by the Docs curation row and approved at the Console
- **Reference repairs** — apply the `[ref]` rows from the Broken references curation row that were **staged** and approved at the Console. Rows the console showed as **applied** are already committed (that row made its own `Initiative-Fix:` commit under a `trusted`/`unattended` ceiling per `_shared/initiative-budget.md`) — do not re-apply them and do not fold them into this step's commit; confirm them under Verify execution instead. A staged repair approved here is an ordinary edit in this step's commit, not an initiative fix, and carries no trailer: the trailer marks what was applied *without* approval, so putting it on an approved edit destroys the only signal that distinguishes the two
- **CLAUDE.md, rules** — apply the edits collected by the CLAUDE.md & rules curation row and approved at the Console
- **New docs from missing-doc detection** — for a `[doc] {file} — Create: …` row (wrap-up's own D2 gap-detection, `docs-health-integration.md`), scaffold the new file from the matching section of `skills/_shared/diataxis-genre-templates.md` and fill in real content from this work's session context, then register it in `docs/REGISTRY.md` if a registry exists. **A `[doc]` row for a genre with an unanswered `[{genre}-convention]` row is not yet actionable** — skip it this pass; it becomes actionable once that row resolves (see the Genre convention resolution bullet below)
- **Docs-health restructural filings** — for restructural docs-health findings (`docs-health-integration.md`'s D1) approved at the Console, re-run `validate-findings` without `--dry-run` and file each surviving payload via `gh issue create`, per that file's filing procedure
- **Decision records (ADRs)** — write the approved ADR files at the path the Decision records curation row resolved (`adr-curation.md` Step 3 — never a path recomputed here), using the ADR skeleton in `_shared/diataxis-genre-templates.md`, and add them to `docs/REGISTRY.md` if a registry exists. **A resolved path that already exists stops that row** — report it and leave the file untouched; never overwrite and never silently take the next free number
- **Genre convention resolution** — when a `[{genre}-convention]` row was answered (`[adr-convention]` from the Decision records curation row, a Diátaxis-genre row from the Docs curation row's D2 check, or `[journey-convention]` staged by `/claude-tweaks:journeys` Step 2 — `wrap-up/console-template.md`'s render template is genre-generic), first write the answer to `.claude-tweaks/policy.yml` as `doc-convention-{genre}: plugin` or `doc-convention-{genre}: project` (option 2 records `plugin`, since migration is how the repo conforms). For option 2 only, then execute the migration as one itemized batch: `git mv` each existing file to the plugin's grammar preserving its number/name, rewrite the matching `docs/REGISTRY.md` rows, and sweep the repo for inbound references to the old basenames (`grep -rl "{old-basename}" --include="*.md" .`) fixing each — for `[journey-convention]`, this batch also includes this run's own newly-created journey files, per `journeys/SKILL.md` Step 2's staging note. Report the file count moved and the reference count rewritten. Never migrate without that row's explicit approval. Resolving a D2 `[{genre}-convention]` row is what unblocks the matching `[doc]` row skipped above — apply it in the same pass once both are resolved
- **Skill updates** — apply patches and create new skills (items the Skills curation row staged, once approved)
- **Memory updates** — already written when resolved. The console executes, in every mode: for each `M#` item resolved to Apply — its Approve all default, an Override chunk answer, or `consoleAutoResolve`'s own auto-resolution (`review-console.md`'s Auto-resolution short-circuit) — `review-console.md`'s "On approval" step 8 wrote the memory file and appended its `MEMORY.md` index line per `_shared/learning-routing.md`'s "Memory write procedure (D4)" at batch approval or auto-resolution. This step does not write it again; it confirms it landed — see Verify execution below
- **Upstream feedback** — already filed when resolved to filed. The console executes, in every mode: for each `U#` item resolved to filed — an Override chunk answer, or `consoleAutoResolve`'s own auto-resolution (the one path where Approve all's own default is overridden to filed; see `review-console.md`'s Auto-resolution short-circuit) — `review-console.md`'s "On approval" step 9 invoked `/claude-tweaks:feedback --pre-confirmed` with the staged, already-scrubbed body at that moment — the console's own resolution satisfies `/feedback`'s confirm gate for that item unless its drift check finds the staged file changed since the console rendered it, in which case `/feedback` falls back to its own per-item confirm (`feedback/SKILL.md`'s Step 7) and files only after that. This step does not invoke `/feedback` again; it confirms the filing landed — see Verify execution below
- **Acceptance labeling** (record mode only — Phase 1's record identity; a materialized header is not required) — run `verification-brief.md`'s procedure, starting from its **Routing** section. This run closes exactly one record, so pass that record's own number as `$CLOSING_SUB_ISSUES` — the one-element closing sub-issue set that file's **Self-inclusion rule** reads (`/claude-tweaks:dispatch`'s group gate is the one caller whose set holds more than one). That file owns the routing decision, not this bullet: it sends a record with a resolvable parent to its Parent-Gate Procedure (the parent carries one gate for all its sub-issues, and this sub-issue gets none) and everything else through its Steps 1-4 — for `app-route`/`rendered-page` plans, gating on a clean visual-review pass via Step 2.5's safety net when `/review` only produced a recommendation, then applying `demo:pending` and posting the Verification Brief. Do not re-derive the parent condition here; the two call sites that bypass this step entirely (`review-console.md`'s auto-merge short-circuit and `dispatch/settle-and-merge.md`'s group gate) inherit it from that same record-mode determination, which is the point of it living there. **Gate the read:** when this run is record mode *and* (the record has a resolvable parent, *or* the record's plan kind is `app-route`/`rendered-page`), read `verification-brief.md` in this skill's directory. Conversation-based work has no work record to label — skip this bullet and do not read the file (that file's own header states the same restriction)

Commit with a message summarizing the wrap-up actions. When the run is `current-branch` mode,
include one `Fixes #{issue}` line per resolved issue in this commit message — it is the
closing-keyword carrier for current-branch runs (see `cleanup-procedures-execution.md` Section C); GitHub
closes the issues when the commit reaches the default branch. Resolve the issue set from any
materialized headers under `${RUN_DIR}/work/*-spec.md` when they exist (a multi-spec
current-branch run can resolve more than one — read each match's `record:` field), otherwise
fall back to this run's own identified record (Phase 1 — a `#`-prefixed argument, or a
branch/commit reference) as the single issue resolved. A run with neither — conversation-based
work — carries no closing keyword; there was never an issue to close.

**`worktree` mode under `integration-model: pr-first` (`_shared/integration-model.md`): no `Fixes` line here.** The run's draft PR
(`_shared/pr-early-run-lifecycle.md`) already carries one `Fixes #{n}` line per record, composed
at PR-open time — adding a second, differently-scoped set here would duplicate (and risk
disagreeing with) that authoritative list. This step's commit is an ordinary commit.

**Phase exit (`worktree` mode, `integration-model: pr-first`):** push this commit and flip
wrap-up's PR checklist row — `_shared/git-discipline.md`'s Phase-exit push section and
`_shared/pr-early-run-lifecycle.md`'s Phase-checklist update section. This is the last phase-exit
push of the run; it does not mark the PR ready for merge or touch its draft state — that
transition belongs to the merge-path sub-issue, not this one (Non-Goals). A no-op under
`local-merge` or `current-branch` mode.

### Verify execution

Before emitting the closure line, confirm every approved action actually ran:

- Plans + ledger removed — `ls docs/superpowers/plans/*{spec-slug}* docs/plans/*-ledger.md` returns nothing
- Design caches deleted (when applicable) — no `*-audit.json` / `*-recommendations.json` / `*-declined.json` for this spec remain in `docs/plans/`
- Pipeline run dir archived — `.claude-tweaks/pipelines/{run-id}/` is gone; `.claude-tweaks/pipelines/archive/{run-id}/` exists, with the `work/` subdirectory (when present) still git-tracked at its new path (skipped when `MULTISPEC_REVIEW_DEFER=1`)
- Worktree removed (worktree strategy) — `git worktree list` no longer shows the feature worktree path
- Closing-keyword carrier commit landed (record-based work: worktree strategy with a materialized header, or current-branch mode with a record identified) — `git log {default-branch} --grep="Fixes #{issue}"` shows the carrier commit for each resolved issue once merged (or `git log {feature-branch} --grep=...` if the branch is still open under "keep as-is" or a pending PR)
- Memory updates landed (when any `M#` item resolved to Apply) — the write lands outside the repository, so confirm it there, not in `git status` or the commit (it will correctly never appear in either): the proposed file exists on disk at `<memory-dir>/<name>.md` and its index line is present in `<memory-dir>/MEMORY.md`.
- Upstream feedback filed (when any `U#` item resolved to filed) — `/claude-tweaks:feedback` returned an issue URL for each such item; that URL is the verification (re-fetch with `gh issue view {number}` if confirmation is needed), not any local repository state.
- Reference repairs landed (when the Broken references curation row applied any) — `git log --grep="Initiative-Fix:" {base}...HEAD` shows one commit, and its diff touches only the files the console's applied rows named. A commit carrying that trailer alongside unrelated work is a contract violation, not a cosmetic slip: the trailer exists so `/claude-tweaks:review` can scope around unrequested edits, and a mixed commit silently removes that ability
- Acceptance labeling landed (record mode only) — **record has a resolvable parent:** the Parent-Gate Procedure's `due` branch — confirm the *parent* carries the brief and the pending disposition, using the same per-backend check below but against the parent (`$PARENT_NUM`, or the parent record) instead of `{issue}`, with one deliberate difference on `work-backend: github-issues`: test whether **any** comment on the parent contains `## Verification Brief` with a `### Confirmed` section (`gh issue view $PARENT_NUM --json comments`), never only its most recent one. A parent is a long-lived open record other people comment on, and the Parent-Gate Procedure's already-posted-brief branch (`verification-brief.md`'s **Apply the gate**) completes a partially-applied gate by adding the label alone, posting nothing — so a correctly gated parent routinely has some other comment last, and a last-comment-only test would fail this check on a gate that landed correctly and hard-stop the wrap-up below. The `local-files` branch needs no such adjustment: it reads the parent record's body, which has no comment ordering to be displaced. Its `incomplete` / `gated` / `resolved` branches land nothing on this run, which satisfies this check as-is. **No resolvable parent:** `work-backend: github-issues`: `gh issue view {issue} --json labels -q '.labels[].name'` includes `demo:pending`, and either the issue's last comment contains `## Verification Brief` with a `### Confirmed` section (`local-merge`, or a degraded `pr-first` run — `verification-brief.md`'s no-`pr`-object branch), or — when `run-state.json` carries a `pr` object — the issue's last comment is the one-line PR pointer (`Verification Brief posted to PR #`) and the PR itself carries a `brief`-kind comment (`<!-- run-comment: brief -->`, `gh pr view {pr-number} --json comments`) containing `### Confirmed`. `work-backend: local-files`: the record's body contains `## Verification Brief` with a `### Confirmed` section and its frontmatter has `acceptance: pending` — no PR concept exists for this backend, so no branching is needed here. For an `app-route`/`rendered-page` plan, confirm the safety-net gate actually resolved (no high/critical visual-review finding left unfixed) before this line was reached.

If any approved action did not land, do NOT emit the closure line. Surface the gap (`BLOCKED — cleanup step {N} did not complete: {reason}`) and stop.
