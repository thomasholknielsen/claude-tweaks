# Dispatch — Resume Confirmation

Canonical procedure for "Confirm before resuming" (`SKILL.md`'s Reporting section) — read this
file whenever the report or a conversational request ("resume it", "merge!") is about to trigger
a re-invocation of a parked run.

**Confirm before resuming.** Before running the re-invocation below — including when a human triggers the resume conversationally (e.g. replying "merge!" in chat) rather than by typing the command directly — call `AskUserQuestion`:
- `question`: `"Resume {target} toward merge? PR #{number} ({url}), CI: {status}, files changed: {count-or-list}. Declining leaves the run parked."`, `header`: `"Resume run"`, `multiSelect`: `false`
- Option 1 — `label`: `"Resume"` (append `" (Recommended)"` per the Recommended-derivation rule below), `description`: `"Re-invoke the resume command below — re-enters the Review Console for final approval"`
- Option 2 — `label`: `"Cancel"` (append `" (Recommended)"` instead when the rule below picks this option), `description`: `"Leave the run parked; do nothing"`

**Recommended-derivation rule (shared with `review-console-interactive.md`'s merge confirmation — the two must never disagree on the same state):** Resume is Recommended when the CI status below reads `passing`/`pending`/`not applicable — local-merge`/`unavailable — gh absent` — resuming is safe or at worst re-enters the console for a human look, never a blind merge. Cancel is Recommended only when CI reads `failing` — resuming would just park again at `_shared/pr-first-merge.md`'s own Step 2.5 gate having spent a cycle for nothing, so the confirmation should say so up front rather than let the human discover it one step later. Exactly one option carries `(Recommended)`, never both, never neither.

**Why this stays a separate stop from the Review Console, rather than folding the two into one.**
This confirmation and the Review Console's own merge decision (`review-console-interactive.md`'s
"Present the console") answer different questions at different scopes, even on a run where both
fire in the same session: this one decides whether to re-enter a parked run's worktree/context at
all — a session-continuation call the human can make from the report alone, without reading the
console's full batch (staged skill/doc/config updates, queue writes, memory updates, upstream
feedback, cleanup actions). Collapsing them would force this confirmation to either render that
whole batch sight-unseen or hide it behind a "Resume" click that turns out to also be an "approve
everything" click — the same improvised-third-stop shape `_shared/auto-mode-contract.md`'s
bookend rule forbids elsewhere. And resuming doesn't guarantee reaching the merge at all: the
Override option at the console can still skip or modify it. With both defaults now derived from
the same CI-status rule above, the two stops can no longer contradict each other on the same
state — that was the actual harm; the fix is consistent defaults, not fewer stops.

**No `autonomy`-ceiling carve-out (#546).** This gate stays unconditional at every ceiling tier, including `unattended` — deliberately, not by oversight. Two reasons converge. First, parking itself is a `supervised`/`trusted`-only condition: at `unattended`, `consoleAutoResolve` completes the Review Console inline instead of resting on it (`SKILL.md`'s Reporting section) — so a resume attempt reaching a live `unattended` ceiling is already the rare case (a run parked under a lower ceiling, later raised), not the common one, and a carve-out keyed to `unattended` would apply almost nowhere it fires. Second, in that rare case the resume trigger is still human-initiated by construction — there is no automated caller of this path today (`SKILL.md`'s Reporting section) — so nothing upstream has authorized this specific act of re-entering this specific parked run's worktree/context. Every capability in `_shared/autonomy-ceiling.md`'s Bookkeeping capabilities table skips an ask some earlier, upstream decision already covered (a grant, a policy default, an already-entered console); this gate is the opposite shape, the one moment nothing upstream covers. Silencing it would not reduce automation friction — nothing automated calls it — it would only remove the live human's own authorization of the resume itself. A future automated resume caller would need to earn its own carve-out on its own evidence; this rationale does not pre-authorize one.

Source the confirmation's values live, never from a stale report: PR number/URL from the run's `run-state.json` `pr` field (or `gh pr list --repo {owner}/{repo} --head {branch}` when unset), CI status from `gh pr checks {number}` (or `gh pr view {number} --json statusCheckRollup`, summarized as `passing`/`failing`/`pending`), and files changed from `gh pr diff {number} --name-only` (a count, or the list when short — 5 files or fewer). When `gh` is absent, CI status and files-changed both read as `unavailable — gh absent`, and the PR reference falls back to the run's `run-state.json` `pr` field (number/URL only, no live `gh` call needed). This degrades rather than bridging to MCP because pull-request operations have no MCP fallback in the first place — `_shared/github-write-transport.md`'s CRUD mapping carries no pull-request row, the same established reason `_shared/pr-early-run-lifecycle.md`'s degrade table gives for PR creation. If that field is also unset (a stale or malformed run), the PR reference instead reads `unknown — see {run-dir}`. Either way the confirmation still renders with whatever fields are available — it never blocks the resume on a missing `gh` binary. The CI status shown is also decided on, once, per `_shared/pr-first-merge.md`'s Step 2.5 (Merge-verification gate) resume rule: green → resume proceeds; red → the confirmation says so and the run stays parked; pending → arm `--auto` only when the state read shows `mergeStateStatus: BLOCKED` (the forge is what holds it), else this same confirmation carries the choice — never the 15-minute watch. Under `integration-model: local-merge` (no PR — `_shared/integration-model.md`), substitute the branch name and worktree path for the PR reference, `git -C {worktree} diff --stat {integration-branch}...HEAD` for files changed, and CI status reads `not applicable — local-merge`. Declining (option 2) stops here — nothing below runs, and the run stays parked exactly as it was; this is the one path where "resuming" does not proceed toward the console at all.

Before re-adopting, run `_shared/run-resume-freshness.md`'s probe against `{run-dir}`: `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" check-resume-freshness --run "{run-dir}"`. A `BLOCKED` result means the parked run's worktree is still held by a live process or was committed to recently — report that line verbatim in place of the confirmation above and stop; do not re-adopt. The actual resume mechanism, on an `OK` result, is re-adopting the same run directory: `PIPELINE_RUN_DIR="{run-dir}" /claude-tweaks:flow "{target}" wrap-up`, run from inside the group's still-assigned worktree (`{run-dir}`'s own worktree — parking never clears a run's worktree assignment, so it is still there).

This re-enters the same Review Console live, and its own teardown is what invokes `/superpowers:finishing-a-development-branch` and `wrap-up/cleanup-procedures-execution.md` Section E (claim release, `auto:build`/`bot:in-progress` label removal) as one step — never hand-chain `/claude-tweaks:demo` (acceptance only, never merges — see its own Anti-Patterns table) with `/superpowers:finishing-a-development-branch` and then reconstruct Section E's claim/label bookkeeping by hand; that skips the console and its automated cleanup entirely, doing by hand what resuming the console already does as a unit. `{run-dir}` and `{target}` are the same values this run was invoked with — `{run-dir}` is this group's own minted directory (Step 4 above), the same value the claim's `runId` already carries, so re-adopting it is all resuming needs. Under `integration-model: pr-first`, the same PR `_shared/pr-early-run-lifecycle.md` opened at run start carries the same `### Resume` pointer.
