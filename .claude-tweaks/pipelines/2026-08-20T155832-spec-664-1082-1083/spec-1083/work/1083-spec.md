# 1083: reconcile/archive-branches: adopt the bulk PR screen

Surface: backend

## Overview

`archive-branches.js` runs the same per-branch `resolvePrState` loop over **local** branches that `prune-remote.js` ran over remote ones — one `gh pr list --head {branch}` network call per in-scope branch, the identical O(N) shape #932 measured. This sub-issue adopts `resolvePrStatesBulk` (shipped by #1082) as a *screen* for `archive-branches`, with the same structural safety framing: **every destructive verdict is confirmed with a fresh per-branch PR-state read before acting; screen evidence alone can only produce skips.**

The mapping differs from `prune-remote`'s because `decideArchive`'s table differs — it has **two** destructive verdicts, and cherry-equivalence alone (no PR needed) triggers one of them:

| Screen-based provisional verdict | Action |
|---|---|
| `skip` (`pr-open`, `too-young`, `merged-pr-without-cherry-equivalence`) | Skip on screen evidence — fail-closed, a mis-read only delays archival |
| `delete` (cherry-equivalent) or `tag-and-delete` (nothing-landed + aged) | **Candidate**: re-run per-branch `resolvePrState`, re-run `decideArchive` on `(cached cherryEquivalent, confirmed prState)`, act only on that final verdict — the recorded entry's `reason` always comes from the final call, never the provisional one |

Cherry-equivalence is **not** recomputed at confirm time: it was computed in this same pass against the same local ref snapshot (no fetch happens in between), so a recomputation is deterministically identical — the confirm re-reads only the evidence that can actually have been wrong (the screen's PR state).

## Current State

- `plugin/bin/lib/reconcile/archive-branches.js` — loop over `refs/heads` (`for-each-ref` with committerdate + tip): `inScope` guard, `isCherryEquivalent` per branch, then `resolve(root, branch)` per branch, feeding `decideArchive` (pure). Destructive actions: `git branch -D` (after `decideArchive: 'delete'`) and annotated `archive/…` tag + `branch -D` (`'tag-and-delete'`). `dryRun` is checked *after* the per-branch resolve today, so dry-run output reflects final, confirmed reasons.
- `decideArchive`'s check order (load-bearing below): failure classes → `OPEN` → `cherryEquivalent` → nothing-landed/age → merged-without-cherry. The OPEN check precedes the cherry check, and its per-branch failure classes (`gh-absent`/`network-failure` → skip) already exist.
- `plugin/bin/lib/reconcile/pr-state.js` — after #1082 lands, per its contract: `resolvePrStatesBulk(repoRoot, branches, deps?) -> Map<branch, {number,state,mergedAt,updatedAt}|null> | 'gh-absent' | 'network-failure'`. **All-or-nothing:** a returned Map is complete for every requested branch — `null` means genuinely no governing PR/ref for that branch, never "chunk missing"; any incomplete/degraded response classifies as the check-level `'network-failure'` instead. A partial-node GraphQL failure therefore can never be silently read as "no PR."
- Tests: `tests/bin-lib/reconcile/archive-branches.test.js` — injectable `resolvePr` fake is the established pattern.

## Acceptance Criteria

1. With an injected fake runner/screen, a pass over N in-scope local branches where every provisional verdict is `skip` performs zero per-branch `gh pr list` calls — asserted by call counts.
2. A branch whose ref was deleted on origin after merge (screen sees `ref: null` → no PR) but whose confirm returns a MERGED PR without cherry-equivalence is **skipped** (`merged-pr-without-cherry-equivalence`), not tag-and-deleted — the deleted-ref screen blind spot from #1082's Task 0 probe is covered by a test here, since local branches (unlike `prune-remote`'s origin-enumerated ones) routinely outlive their remote refs.
3. Every `branch -D` and every archive-tag creation in the restructured pass is preceded, in the same pass, by a per-branch `resolvePrState` call for that branch (cherry-equivalence is computed once per pass before the destructive action; the confirm re-reads PR state only) — asserted via fake-call ordering.
4. `decideArchive`'s source and existing unit tests are unchanged, and the order-pinning sentinel test exists and passes.
5. Under `dryRun`, candidate branches still run the confirm, and their reported reasons match a non-dry run's — asserted by a dry-run test.
6. `npm test` passes in full.

## Technical Approach

Mirror #1082's landed `pruneRemote` shape exactly: screen → provisional pure decision → confirm destructive candidates → act. Keep `decideArchive` as the single decision function, called twice for candidates (provisional on screen evidence, final on confirmed evidence) — never fork a second decision table; both calls take the same `{branch, tipAgeDays, cherryEquivalent, prState}` shape, with only `prState`'s provenance differing (screen map entry vs `resolvePrState` result — #1082's screen already normalizes to the same governing-PR object shape `resolvePrState` returns, so no adapter is needed; if #1082 lands a different shape, add the adapter there, not here). The confirm reuses the sync `resolvePrState`. Confirm volume is bounded by construction: worst case (every branch a candidate — e.g. right after a mass merge) equals today's per-branch call count exactly, so the restructure strictly reduces network calls on every input; no separate cap is needed, and it self-clears as branches archive.

## Gotchas

- **Local branches routinely have no origin ref** (never pushed, or deleted after merge) — the screen's `ref(qualifiedName:)` returns null there even when PRs exist for that head name. That is precisely why *both* destructive verdicts confirm per-branch; do not "optimize away" the confirm for the cherry-equivalent `delete` path.
- **Cherry ordering:** today cherry runs before PR state for every branch; after the restructure it must still run for every branch that isn't screen-OPEN-skipped (cherry-equivalence, not PR state, is what triggers `delete`). Only the OPEN-screened branches legitimately skip cherry — and only via the pinned sentinel pattern, never by assuming `decideArchive`'s internal order silently.
- **`windowsHide: true`** on any new spawn (#931 regression class).
- The `tipAgeDays`/`shouldAgeTag` thresholds and the tag-aging sweep further down the file are out of scope — don't reorder them while restructuring the loop.
