# 1672: run-integrity.js: fallback evidence when deriveBranch can't resolve a torn-down worktree

Surface: backend

## Overview

Add a fallback evidence path to `checkRunIntegrity()` in `plugin/bin/lib/hooks/run-integrity.js` for when `deriveBranch()` can't resolve a live worktree (the common case once a finished run's worktree is torn down), so the session-start banner's `shipped-unclosed` hint still fires instead of silently degrading to a generic re-listing forever.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Not fixing #1463's separate false-positive-on-fresh-worktree bug in `mergedEvidence()`'s `ancestor` path — different failure direction (false-positive vs. this record's fail-open-to-in-progress), already tracked and ready separately.
- Not implementing #1673, which adds reconcile's auto-close criterion consuming this evidence path.
- Not fixing #1012's `record-worktree --help` positional-arg misparse.

## Current State

- `plugin/bin/lib/hooks/run-integrity.js` — `checkRunIntegrity()`'s `deriveBranch()` resolves a run's branch exclusively from `git worktree list --porcelain` matched against the recorded `worktree` path. Once that worktree is torn down (the normal end state of a finished run), `deriveBranch` returns `null` and `checkRunIntegrity` fails open to `in-progress` — permanently, for that run.
- `plugin/bin/lib/hooks/session-start.js` — renders the specific "work appears shipped... close out with `close-run`" hint only when `checkRunIntegrity` returns `shipped-unclosed`; otherwise falls back to the generic re-listing.
- `plugin/bin/lib/hooks/close-run-state.js` — a run that reached materialize and shipped typically carries a recorded PR URL/branch from a `record-pr` stamp, or a branch name logged in `decisions.md` — both artifacts survive worktree teardown even though the live worktree does not.

## Deliverables

- [ ] Add a fallback evidence function in `run-integrity.js`, invoked only when `deriveBranch()` returns `null`: try (1) a recorded `record-pr` stamp's branch/PR field from `run-state.json`, then (2) a branch name parsed from a `decisions.md` log line, in that order.
- [ ] Feed whichever source resolves into the same "merged" check `checkRunIntegrity` already runs for the live-worktree path (`git merge-base --is-ancestor {branch} {integration}`), rather than duplicating that logic.
- [ ] When neither fallback source resolves a branch, keep today's fail-open-to-`in-progress` behavior unchanged — no field may fabricate an answer it can't support.
- [ ] Verify `session-start.js`'s banner renders the specific `shipped-unclosed` hint for a torn-down-worktree run exactly as it does for a live one, once this fallback resolves.
- [ ] Add test coverage: a torn-down-worktree run with a `record-pr` stamp (resolves via source 1), one with only a `decisions.md` branch mention (resolves via source 2), and one with neither (falls open to `in-progress`, unchanged).

## Acceptance Criteria

1. A run whose worktree has been torn down but whose branch merged into the integration branch — evidenced by a recorded `record-pr` stamp or a `decisions.md` branch mention — is rendered by the session-start banner with the specific "work appears shipped... close out with `close-run`" hint, not the generic re-listing.
2. A run whose worktree is torn down and carries neither a `record-pr` stamp nor a `decisions.md` branch mention still resolves to `in-progress` — the existing fail-open behavior is unchanged for this case.
3. The live-worktree path (`deriveBranch` resolves normally) is unchanged — this deliverable only adds a fallback, it never replaces or short-circuits the existing check.
4. `npm test` passes, including new `run-integrity` test cases covering both fallback-resolves scenarios and the fallback-fails-open scenario from Deliverable 5.

## Technical Approach

Add a fallback resolution function called only when `deriveBranch()` returns `null`. Two candidate evidence sources, tried in order: (1) `run-state.json`'s own recorded PR/branch field from a prior `record-pr` stamp, if present; (2) a branch name parsed from `decisions.md`'s log lines. Feed whichever resolves into the same "merged" check `checkRunIntegrity` already runs for the live-worktree path, rather than duplicating that logic. Preserve the existing per-field fail-open discipline: any field that still can't be determined falls back to `in-progress`, never a fabricated answer.

Coordinate with #1463: that record changes `mergedEvidence()`'s `ancestor` corroboration logic in the same function this deliverable extends. Land after #1463 to avoid two concurrent edits to the same evidence-resolution code path.

### Key Files

- `plugin/bin/lib/hooks/run-integrity.js` — `checkRunIntegrity`/`deriveBranch`: add the torn-down-worktree fallback evidence path
- `plugin/bin/lib/hooks/session-start.js` — banner rendering: verify the `shipped-unclosed` hint now fires for the torn-down-worktree case
- `plugin/bin/lib/hooks/close-run-state.js` — read-only reference for the run-state fields available (the `record-pr` stamp shape)

## Gotchas

- Blocked by #1463 landing first — it edits `mergedEvidence()`'s `ancestor` path in the same file/function this deliverable extends; building on the pre-#1463 shape risks a rebase conflict or reintroducing the false-positive #1463 fixes.
- Keep the "any field null → in-progress" fail-open discipline — this fallback trades off precision for coverage, so it must not lower the bar to make more runs auto-detectable at the cost of false "shipped" verdicts.
- #1673 consumes this evidence path for `reconcile`'s new auto-close criterion — don't change this deliverable's return shape without checking that consumer.
