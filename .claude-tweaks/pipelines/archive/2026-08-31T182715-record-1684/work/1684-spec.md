# 1684: /flow's two-Task-call sessions never stamp record-worktree, permanently stalling reconcile's archival of runs whose merge is deferred

Defer-reason: genuinely-larger

## Current State

`/flow`'s standard invocation shape runs `build,test` and `review,polish,wrap-up` as two separate Task calls, each a distinct `session_id`. `record-worktree` (the CLI verb at `plugin/bin/hooks.js`, stamping a `worktree` field into `run-state.json`) is meant to be called once per run during build's Common Step 1 (`plugin/skills/build/worktree-setup.md`, "Record the assignment" — marked non-skippable). In practice each Task call's attempt gets classified "foreign" by the ownership-stamp gate (`checkBookkeepingStampsGate` in `plugin/bin/lib/hooks/pre-tool-use.js`), which is warn-only — it logs a `wd-foreign-session` event and lets the write through, but never itself performs the stamp. The result: `run-state.json` can carry no `worktree` field for a run's entire life, even though a real worktree backed every phase.

`plugin/bin/lib/reconcile/archive-merged.js`'s `archiveMerged` loop checks `if (!state || !state.worktree) { skipped.push({ reason: 'no-worktree' }); continue; }` (line 515) — before ever reading PR or console state. A run stuck this way never self-archives via the reconcile sweep, no matter how long after merge reconcile runs.

Reproduced live on run `2026-08-29T161123-record-1653` (record #1653, PR #1665): the merge succeeded and reconcile released the claim cleanly, but the run dir stayed skip-reason `no-worktree` across two further reconcile passes. `events.jsonl` for that run shows repeated `wd-foreign-session` warn events across the run's lifetime, never escalating into a forced remediation. Manual recovery worked: `node bin/hooks.js record-worktree --run <dir> <worktree-path>`, then `close-run`, then `archive-run` — all three succeeded once the stamp existed, confirming the workaround and pinpointing the missing automatic step.

This most likely affects every `/flow` run whose merge does not complete synchronously within the same session that ran build/test — i.e. any `needs-human`, parked, or otherwise resumed-later run, which is a routine occurrence, not an edge case.

## Deliverables

One of:
(a) Make the ownership-stamp gate recognize `/flow`'s known two-Task-call shape as same-run rather than foreign — e.g. treat a shared `PIPELINE_RUN_DIR`/run-id across sessions as authorization to stamp, rather than only warning.
(b) Give `archive-merged.js`'s sweep a fallback branch that does not hard-require `state.worktree` when the run's `run-state.json` PR object shows the PR is confirmably `MERGED` — resolving the branch another way (e.g. `gh pr view --json headRefName`) instead of only via the worktree-list lookup.

Either fix should also cover the archival precondition itself so a run stuck at `no-worktree` today does not require the three-command manual recovery sequence above.

## Acceptance Criteria

A `/flow` run structured as two separate Task-call sessions (build,test then review,polish,wrap-up) ends its life with a `worktree` field stamped in `run-state.json` without manual intervention, OR reconcile's `archive-merged.js` archives such a run once its PR is confirmed `MERGED`, without requiring `state.worktree` to be present. Existing reconcile/hooks test suites (`tests/bin-lib/reconcile/`, `tests/bin-lib/hooks/`) pass unchanged plus new coverage for whichever branch is chosen.
