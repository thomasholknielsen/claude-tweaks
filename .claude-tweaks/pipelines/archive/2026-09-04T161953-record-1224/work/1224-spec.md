# 1224: dispatch: queue-pull does not exclude issues with an already-open PR

Surface: backend

## Current State

Dispatch's queue-pull (`SKILL.md` Step 2, driven by `queue-pull-script.md`) selects eligible candidates by label/dependency filters only: **open + `auto:build` + no `bot:*` + no open `Blocked by #N` dependency + unclaimed**. It never checks whether a candidate already has an open, unmerged PR referencing it.

#257 has an open draft PR #869 (build/test/review/wrap-up complete, awaiting a human merge verdict) yet was re-selected by dispatch hours after a prior firing (`2026-08-21T105702-spec-252-257-899-266-316-644-652`) explicitly released its claim on #257 for this exact reason and posted a comment documenting it. This same record's own dispatch reproduced the bug again (run `2026-08-21T181739-record-257`) — a repeatable failure mode, not a one-off.

## Deliverables

- Step 2's eligibility filter additionally excludes any candidate that already has an open PR referencing it via a closing keyword (`Closes`/`Fixes`/`Resolves #N`) or GitHub's native "Development" linkage.
- The exclusion is surfaced in this firing's own reporting, following the existing Blocked-exclusion report's rendering convention (`SKILL.md` Step 3) — a named line when non-empty, silent when nothing was excluded.
- All four selection forms (bare, `next`, `#N`, `#N,#M,...`) inherit the exclusion uniformly, since they all read Step 2's `dispatch-groups.json` output.

## Acceptance Criteria

- A record carrying an open PR (draft or ready-for-review) that will close it is excluded from Step 2's eligible pool, even when it still carries `auto:build` and no `bot:*` label.
- The exclusion is reported the same firing it fires, naming the excluded record and the linked PR number.
- Direct `#N` dispatch and the explicit `#N,#M,...` list form both re-check this exclusion against Step 2's live queue — consistent with how they already re-verify `auto:build`/`bot:*` there — rather than only the bare/`next` forms picking it up.
- A record with no linked PR is unaffected — no new false exclusions on the steady-state queue.

## Technical Approach

Add a linked-PR check to `queue-pull-script.md`'s eligibility pipeline, parallel to the existing `partitionByOpenBodyBlockers`/`partitionByOpenNativeBlockers` pair in `record.js`. Fetch, per eligible candidate, whether it has an open PR that will close it via the GraphQL `Issue.closedByPullRequestsReferences` connection, batched into one query across the eligible set (mirroring `buildNativeDependencyQuery`'s batching shape) rather than a per-candidate `gh pr list --search` loop. Unlike the native-dependency query, this check must run unconditionally — it isn't gated behind `work-links: native`, since PR-linkage exclusion prevents wasted re-dispatch rather than encoding a dependency-tracking policy choice.

Partition eligible candidates into `{eligible, excludedByOpenPR}` (same shape `partitionByOpenNativeBlockers` returns), write the excluded set to a new session-scoped file alongside `dispatch-blocked-excluded.json`, and thread it into `SKILL.md` Step 3's Blocked-exclusion report so both exclusion reasons render under one convention.

### Key Files

- `plugin/skills/dispatch/queue-pull-script.md` — add the batched linked-PR GraphQL query and partition step to the eligibility pipeline
- `plugin/bin/lib/issues/record.js` — add a `partitionByOpenLinkedPR` function alongside `partitionByOpenBodyBlockers`/`partitionByOpenNativeBlockers`
- `plugin/skills/dispatch/SKILL.md` — update Step 2's queue definition sentence and Step 3's Blocked-exclusion report to cover the new exclusion reason

## Gotchas

- GraphQL's `closedByPullRequestsReferences` only captures PRs using a closing keyword in their body — a PR that merely mentions the issue without one won't be caught this way; verify #257/#869's actual linkage uses a closing keyword before assuming this field covers it, and treat a non-closing-keyword mention as an open gap if so.
- The check must run independently of `work-links: native` — see Technical Approach; getting this gated wrong would silently disable the exclusion for any project not using native work-links.
- Keep the query batched across the whole eligible set in one call — a per-candidate loop repeats the same slow-fallback pattern `queue-pull-script.md` already warns about for the per-dependency open-state check.
