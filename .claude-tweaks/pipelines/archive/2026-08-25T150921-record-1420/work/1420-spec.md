# 1420: dispatch grouping: generic Key Files directory entries merge unrelated records into one mega-group

Surface: backend

**Related:** #1421

## Current State

`groupByFileOverlap` (`plugin/bin/lib/issues/grouping.js`) unions two records into one dispatch bundle whenever `extractKeyFiles` returns a matching literal file-path string for both, treating a bare directory-level `### Key Files` entry (e.g. `tests/`) identically to a genuine single-file collision for union-find bridging purposes.

A prior incident (#1365, fixed by `e2a57b55`/PR #1394) added frequency-based hub-path exclusion: a path referenced by at least `HUB_PATH_MIN_COUNT` (3) records, or at least `HUB_PATH_FRACTION` (10%) of the eligible batch — whichever is larger — is excluded from ever bridging two records together. That fix does not close this bug; it only raises the bar, and the bar rises with batch size. During a live `/claude-tweaks:dispatch next` firing over 162 open `auto:build` issues (run `2026-08-24T221615-dispatch-standalone`, after #1365's fix had already merged), this produced 76 file-overlap groups, one with 75 members — the generic path `tests/` appeared in 15 records' Key Files sections, `plugin/bin/hooks.js` in 7, `docs/donts.md` in 5. At 162 eligible records, `hubPathFraction` (10%) computes a threshold of `ceil(162 * 0.1) = 17`, so `max(3, 17) = 17` — `tests/`'s 15 references no longer clear the hub bar, even though 15 unrelated records citing a bare directory is exactly the same generic-path signal the #1365 fix was built to catch at a smaller pool size (139 records, threshold 14, where 15 references *did* clear it). The fraction term scales the wrong way for this failure mode: a larger eligible queue should not require proportionally *more* citations of a generic path before treating it as generic — it makes recurrence a certainty as the queue grows, not an edge case.

Dispatch's Step 3 `next` ranking (priority-then-age) selected this 75-member group as the top pick, representative #626 (priority:high, oldest). Dispatching it would have attempted `/claude-tweaks:flow` against 75 unrelated GitHub issues as a single bundle — far outside the intended bundle semantics of 2-3 tightly-coupled records sharing a real file collision. The firing refused to dispatch it (logged as REFUSED in that run's `decisions.md`) and manually selected the next-ranked legitimate singleton instead, but the same poisoned pick recurs on every future `next`/bare firing as the eligible pool keeps growing, regardless of the #1365 fix already in place.

## Deliverables

- Add a syntactic, count-independent exclusion to `extractKeyFiles`/`extractKeyFilesSection` (or `groupByFileOverlap`'s file-collection step) in `plugin/bin/lib/issues/grouping.js`: a bare directory-level `### Key Files` entry — a path ending in `/` with no filename component — is never eligible to bridge two records via union-find, regardless of how many or how few records cite it. This is additive to, not a replacement for, the existing #1365 frequency-based `hubPaths` exclusion (which still applies to a generic-looking but non-directory path, e.g. a frequently-cited specific file).
- A regression test in `tests/bin-lib/issues/grouping.test.js` pinning the failure mode: two records whose only shared Key Files entry is a bare directory path must land in separate singleton groups even when only 2 records share it (i.e., below `HUB_PATH_MIN_COUNT`/`HUB_PATH_FRACTION` — the scenario the existing hub-path tests around line 97 confirm is currently *not* excluded). Two records sharing an actual specific file path must still be correctly unioned.
- Do not alter the existing #1365 hub-path exclusion behavior (`HUB_PATH_MIN_COUNT`/`HUB_PATH_FRACTION`, the `fileCounts`/`hubPaths` logic) — the two exclusions are independent and both need to hold: this fixes the case frequency-based exclusion structurally cannot (a directory path shared by only 2 records, or any count below threshold), while frequency-based exclusion keeps handling a generic *specific file* (e.g. `plugin/bin/hooks.js`) that isn't syntactically a directory.

## Acceptance Criteria

- Two eligible records whose Key Files sections both list only a bare directory path (e.g. `tests/`) are placed in separate singleton groups, not unioned — including when only 2 records share it (below the existing hub-path count/fraction threshold).
- Two eligible records sharing an actual specific file path (not a bare directory) are still correctly unioned into one group.
- The existing #1365 hub-path exclusion tests (`tests/bin-lib/issues/grouping.test.js`, the block starting around line 69) continue to pass unmodified — this fix is additive, not a replacement.
- `npm test` green including the new pin test.

## Technical Approach

Add a directory-path check (a path ending in `/` — or more precisely, a path with no filename segment after its last `/`) to the union-eligibility test inside `groupByFileOverlap`'s file-collection loop, or as a pre-filter in `extractKeyFiles`/`extractKeyFilesSection` before paths reach `groupByFileOverlap`. Filtering earlier, in `extractKeyFilesSection`, keeps the exclusion co-located with the other syntactic filters already there (`TEMPLATE_PLACEHOLDER_RE`), and keeps `groupByFileOverlap` itself agnostic to path shape — but a directory-level entry legitimately naming the file the record concerns (a record whose Key Files section, for whatever reason, has nothing more specific to give) would then silently vanish from Key Files entirely, which changes what `extractKeyFilesSection` returns for reasons other callers (`multi-spec.md`'s Cross-spec conflict detection, `help/status-scan.md`) rely on. Filtering inside `groupByFileOverlap`'s own file-collection loop (alongside the existing `hubPaths.has(file)` check at the line that populates `fileToId`) keeps the directory-path stays a "thing this item has" for every other purpose, and only loses its power to bridge two items into a shared group — the same scoping the existing hub-path exclusion already uses, so the new check is a straightforward second condition alongside it rather than a new subsystem.

### Key Files

- `plugin/bin/lib/issues/grouping.js` — add a directory-path (trailing-`/`) exclusion to `groupByFileOverlap`'s file-collection loop, alongside the existing `hubPaths.has(file)` skip, so a bare directory entry never bridges two records regardless of citation count
- `tests/bin-lib/issues/grouping.test.js` — add a regression test pinning that 2 records sharing only a bare directory path land in separate singletons (below the existing hub-path threshold), and confirm existing hub-path/specific-file tests are unaffected

## Gotchas

- The #1365 fix's `hubPathFraction` term scales its threshold with batch size (`ceil(items.length * hubPathFraction)`), which means the *same* generic path, at the *same* absolute citation count, flips between excluded and included purely as the eligible queue grows or shrinks between firings — this record's fix (a syntactic, count-independent directory check) sidesteps that instability for the directory-entry case specifically, but the underlying scaling behavior remains for any non-directory generic path that isn't syntactically a bare directory (e.g. a frequently-touched specific file like `plugin/bin/hooks.js`) — out of scope here, flagged for awareness only.
- Distinguishing "directory-level" from "specific file" syntactically (trailing `/`) will not catch every generic-but-technically-specific path (e.g. a widely-touched top-level file like `package.json` or `CLAUDE.md` with no trailing slash) — those still rely solely on the existing frequency-based `hubPaths` exclusion, which is known (per the Current State above) to under-exclude as the pool grows. This record's fix narrows the recurrence surface; it does not eliminate every variant of the underlying "generic path treated as real coupling" problem.
- The original request's third deliverable — "consider a sanity cap or warning when `groupByFileOverlap` produces an outlier-sized group" — is deliberately left out of this record's Deliverables/Acceptance Criteria: it was framed as a suggestion ("consider"), not observed-evidence-backed, and a size-cap/warning mechanism would need to reach into `groupByFileOverlap`'s return contract and its callers (`dispatch/SKILL.md`'s Step 3 ranking, `materialize.md`) — a second, separable unit of work rather than an extension of this single-file syntactic fix. Not silently dropped: flagged here for a follow-up `/claude-tweaks:capture` if a future incident shows the two exclusions (frequency + directory) still aren't sufficient.
