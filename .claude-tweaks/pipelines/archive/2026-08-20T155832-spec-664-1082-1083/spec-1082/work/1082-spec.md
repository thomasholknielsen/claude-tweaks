# 1082: reconcile/pr-state + prune-remote: bulk GraphQL PR screen with per-branch confirm for delete candidates

Surface: backend

## Overview

One session-start background reconcile pass is O(branches) in both subprocesses and network round-trips: `prune-remote.js` issues one `git cherry` **and** one `gh pr list --head {branch}` per in-scope remote branch (measured on this repo, plugin 6.97.0: 10,347 ms wall clock, 34 subprocesses for 11 branches — the ~9s of per-branch `gh pr list` calls dominate; #932). The reconcile family already treats API-call count as a first-class budget (`budget.js` 18s ceiling, `gh api rate_limit` preflight), so a 50-branch repo paying 50 sequential API calls per pass violates a real constraint, not just a feel-slow one.

This sub-issue inverts the evidence order: **one bulk GraphQL query screens the whole in-scope branch set; today's exact per-branch evidence is re-run only for branches the screen nominates as delete candidates** (typically 0–2 per pass). The hard constraint from #932 — the delete verdict must be preserved *identically, not approximately* — is scoped precisely: **nothing is ever deleted that today's evidence would not delete** (a delete only follows the same per-branch `gh pr list --head` + `git cherry` evidence that gates it today). The screen can only *under*-act: a mis-read toward *skip* delays or, if the divergence is systematic for that branch shape, forgoes a prune that today's path would have made — the branch then stays in `tidy`'s existing staged-path territory, never wrongly deleted; a mis-read toward *candidate* wastes one confirm call. Task 0 exists to establish empirically whether any systematic under-read shape exists for this repo's in-scope branch names. Typical pass drops from 2N+ per-branch subprocesses and N API calls to 1 GraphQL round trip + k cherries + k confirms.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- No change to `decideRemotePrune`'s verdict table — this work changes evidence *acquisition order and batching* only; the pure decision function stays byte-identical.
- No bulk cherry-equivalence computation (`git cherry` is local, ~5% of wall clock, and has no true single-call bulk form — each branch needs its own symmetric diff). Screen-first already eliminates cherry calls for non-candidates as a side effect.
- No verdict caching in `cache.js` and no per-pass branch cap (rejected in the decomposition — the `skipIfFresh` TTL gate and the 18s budget already cover those cases; see parent #1080's Decision Rationale).
- No REST per-branch fallback on screen failure — a failed screen skips the whole check this pass (same availability tradeoff `fetch-failed` already makes today: one network failure already skips the entire check) and the next pass retries. Reintroducing per-branch REST as a fallback would reintroduce the O(N) shape this record removes.
- No `archive-branches.js` adoption — that is #1083, the follow-up sub-issue in this decomposition (blocked by this one).
- No change to the #664 tie-break semantics themselves — but see Gotchas for the required coordination.

## Acceptance Criteria

1. With an injected fake runner, a pass over N in-scope branches with zero delete candidates performs exactly `ceil(N/chunk)` gh invocations (the screen chunks; owner/name for the GraphQL variables resolves from `git remote get-url origin` — a git call, never an extra `gh` call) and zero `git cherry` / per-branch `gh pr list` invocations — asserted by call counts.
2. Screen says MERGED but confirm returns an OPEN PR, no PR, or a failure → the branch is skipped with the final `decideRemotePrune` call's reason, and no `push --delete` includes it — asserted for each disagreement shape.
3. Screen failure returns `{ entries: [], failure: 'pr-screen-failed' }` (network/degraded) or `{ entries: [], failure: 'gh-absent' }` before any per-branch work, mirroring `fetch-failed`; a *confirm* failure skips only its own branch and the pass completes.
4. `decideRemotePrune`'s source and its existing unit tests are unchanged (`git diff` on the function body is empty), and the sentinel order-pinning test exists and passes.
5. Per-branch entry `reason` vocabulary is unchanged — `pr-open`, `no-merged-pr`, `not-cherry-equivalent`, `cherry-failed`, `merged-pr-cherry-equivalent`, `delete-failed` — no new per-branch reasons (screen failure is check-level only).
6. Under `dryRun`, candidate branches still run the confirm, and their reported reasons match a non-dry run's — asserted by a dry-run test.
7. `npm test` passes in full.

## Technical Approach

Build the GraphQL seam per the `gh-api-module-pattern` project skill (injectable runner so tests never spawn `gh`; argv arrays with flag-injection separators; per-call fail-safe). Query shape: resolve `owner`/`name` once from `git remote get-url origin` (a git spawn, keeping AC1's gh count exact), then per chunk `gh api graphql -f query='query($owner:String!,$name:String!){repository(owner:$owner,name:$name){ b0: ref(qualifiedName:"refs/heads/…"){...} b1: … }}' -F owner={owner} -F name={name}` — branch names embedded as JSON-escaped string literals in the alias arguments (they come from `for-each-ref`, but escape via `JSON.stringify` anyway), owner/name as typed `-F` variables. Reuse the `FETCH_TIMEOUT_MS`-style timeout convention (a bulk call may warrant a higher ceiling than 5s — pick one and state it in the module header).

## Gotchas

- **Every new spawn must pass `windowsHide: true`** — #931's console-window storm regression class; `cbc2bd54` fixed the reconcile lib's existing spawn sites, don't reintroduce it.
- **#664 sequencing (why it blocks):** #664 changes the destructive-caller tie-break so a newer OPEN PR outranks an older MERGED PR. Build only after it merges, on its landed shape — concretely, a branch with *any* OPEN PR must screen as `pr-open` skip even when a merged sibling PR exists, and the confirm inherits the same rule through `resolvePrState`. Don't re-derive the tie-break here.
- **The identical-verdict constraint is directional:** it guarantees no wrong delete, not perfect prune coverage. A systematic screen under-read (a shape where `associatedPullRequests` misses a `--head`-visible PR) would leave affected branches permanently unpruned-but-safe; Task 0's halt condition exists to catch that empirically rather than assume it away.
- **GraphQL rate-limit accounting is deliberately out of scope:** `budget.js` bounds wall clock, not call counts, and the `gh api rate_limit` preflight covers the REST pool; one aliased query per pass replaces N REST calls, so pressure strictly drops. Record the probe's observed query cost in the module header; revisit only if Task 0 shows a surprising cost.
- **Never use search-index-backed lookups** (`gh pr list --search`, GraphQL `search`) — the index lags fresh writes; `ref()` aliases and `--head` resolve live (Task 0 confirms).
- **No partial screens:** one failed chunk fails the whole screen (sequential, short-circuit). A partial map would make missing branches indistinguishable from no-PR branches — a silent wrong-verdict class.
- **`gh api graphql` value mechanics:** `-f` for raw strings (the query), `-F` for typed/resolved values — and `{owner}`-style placeholder substitution is a REST-path feature; GraphQL gets variables instead (see the `gh-api-module-pattern` skill and the repo's `gh api -f vs -F` memory).
- **Flaky CI test in this seam:** #984 reports `'pr-first repo with a working remote actually reaches the remote-prune dispatch'` failing reproducibly in GitHub Actions — the restructure touches that fixture's path; fix or explicitly account for it rather than papering over.
