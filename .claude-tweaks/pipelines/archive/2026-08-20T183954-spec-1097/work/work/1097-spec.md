# 1097: Trust fetch: batch native sub-issue enumeration and session-snapshot the result

Surface: backend

## Current State

`_shared/trust-table.md`'s Fetch section, under `work-links: native`, enumerates decomposed sub-issues with one sequential `gh api repos/{owner}/{repo}/issues/{n}/sub_issues` REST call per `parent-issue` record inside a `while read` loop — 33 sequential round-trips on this repo, on every invocation, with no caching. The closed-record set and the git-log dump that feed the same table are already session-cached (#645's record-snapshot convention in `plugin/bin/lib/issues/record-snapshot.js`), so this loop is the one remaining per-invocation fetch cost, and it dominates `/claude-tweaks:backlog overview` bare-mode wall-clock (origin: #877). The same per-parent REST loop pattern is restated at two sites in `_shared/github-pr-scan-acceptance.md` (the `acceptance-gap` scope and the comment-scan sweep near its line 381).

The machinery for a batched alternative already exists: `capabilities-probe.js` probes the GraphQL `subIssues` field (`probeCapabilities().subIssues`), and `buildNativeDependencyQuery` (`plugin/bin/lib/issues/record.js:413`) implements the aliased GraphQL pattern for `blockedBy`. Note the precedent's actual shape: that function takes the number array it is given and builds one query — chunking (at 50 aliases per request) is applied **caller-side**, documented in the calling prose (`backlog/overview-mode.md`), not inside the function. Its existing tests (`tests/bin-lib/issues/record.test.js`) cover alias/query shape and empty/non-array input; there is no chunking-boundary test to mirror.

## Acceptance Criteria

- On a repo with N parent-issue records and the `subIssues` field available, one trust-table Fetch performs at most `ceil(N/50)` GraphQL requests for sub-issue enumeration (plus per-parent REST retries only for parents hit by the error/overflow ladder below), not N REST requests.
- **Error ladder (one rule, no alternatives):** a GraphQL alias that errors or is missing from an otherwise-successful batch response puts that parent on a retry list served by its own single REST call (`gh api --paginate`); a parent whose REST retry also fails causes the run to fail loud — a visible error naming the parent, no verdict rendered. A failed parent is never coerced to "no sub-issues": undercounting sub-issues re-admits them into trust cells as ungraded evidence, the one direction the trust table must never fail in. When any parents were retried, one warning line names them (same posture as the existing truncation warnings).
- A parent whose `subIssues` connection reports `pageInfo.hasNextPage` joins the same REST retry list (fetched with `--paginate`) — the partial first-100 page is never used as that parent's final set. This is an invariant guard: GitHub's documented per-parent sub-issue cap is 100, so the branch should be unreachable today (verify the cap at build time); the guard exists so a raised platform cap degrades to a complete fetch, not a silent undercount.
- Both paths write `/tmp/trust-table-sub-issues.json` canonicalized — flattened, numerically sorted, deduplicated — and produce identical files for the same data (the downstream consumer is a `Set`, so canonicalized equality is the meaningful bar, not raw append order).
- The snapshot is written only after every parent has resolved (batch plus retries complete); a run with any unresolved parent writes no snapshot. A repeat invocation within the TTL after a fully-successful run performs zero sub-issue fetch calls.
- With the probe unavailable or failed, the REST-loop fallback runs end-to-end and satisfies the same canonicalized-output contract.
- `npm test` passes: new unit tests for `buildNativeSubIssuesQuery` and the snapshot helper, plus every updated conformance suite.
- Trust grading semantics unchanged: all-time record set, `hasParent` filter, every existing truncation warning, bare-mode consequence line, full-table trust lens.

## Technical Approach

Mirror `buildNativeDependencyQuery`'s shape: `repository(owner:$owner, name:$repo) { i{n}: issue(number: {n}) { subIssues(first: 100) { nodes { number }, pageInfo { hasNextPage } } } }`. Parse each alias into `{parent, subIssueNumbers, hasNextPage}`; the caller (trust-table.md prose) chunks at 50, routes errored/missing/overflowing aliases onto the REST retry list, canonicalizes (flatten, numeric sort, dedup), writes the session-suffixed snapshot, and copies it to the shared `/tmp/trust-table-sub-issues.json`. The snapshot helper stores the canonicalized array keyed by session id, TTL-checked exactly like `gitLogPath`'s consumer. Prose changes cite the helper and keep the fallback block byte-compatible with today's loop so the GHE path needs no new testing surface.
