# 1864: stampAdHocRunDir always writes its one-shot marker on ExitWorktree(remove), even when the git lookup is guaranteed to fail

## Current State

Wiring `checkPostTeardownReanchor` into `plugin/hooks/hooks.json` for `ExitWorktree`/`git worktree remove` (landed via #703's continuation, commit range `42a8bbb05..afd33e3e9`) means `post-tool-use.js` now receives `ExitWorktree` events for the first time. This activates `stampAdHocRunDir`'s non-EnterWorktree branch (`plugin/bin/lib/hooks/post-tool-use.js:445`) against an input shape it was never exercised against: it calls `resolveWorktreePathViaPorcelain(ctx)`, which shells out `git -C <cwd> worktree list --porcelain` against the just-deleted worktree directory — guaranteed to fail — but unconditionally writes `ADHOC_WORKTREE_CHECKED_MARKER` regardless of that outcome.

Found by the whole-branch review gating the v6.116.0 release (CLAUDE.md's Releasing section) — confirmed, not yet fixed. Narrow/edge-case severity: requires an ad-hoc (non-pipeline) session that later creates a different worktree via a raw `git worktree add` (bypassing `EnterWorktree`) within the same session.

## Deliverables

- Guard the marker write in `stampAdHocRunDir`'s non-EnterWorktree branch so it is only written on a successful resolution (or otherwise distinguishes "checked and found nothing" from "the lookup itself couldn't run because the target no longer exists").
- Add a regression test: an `ExitWorktree(action:'remove')` event must not permanently defeat the #1333 ad-hoc-stamping mechanism for a later raw `git worktree add` in the same session.

## Acceptance Criteria

- An `ExitWorktree(action:'remove')` PostToolUse event does not write `ADHOC_WORKTREE_CHECKED_MARKER` when the porcelain lookup fails because the target directory is already gone.
- A session that runs `ExitWorktree(remove)` and later creates a worktree via raw `git worktree add` still gets that worktree stamped by `stampAdHocRunDir`.

## Failure scenario this fixes

An ad-hoc (non-pipeline) session runs `ExitWorktree(action:'remove')`. `stampAdHocRunDir` calls `resolveWorktreePathViaPorcelain(ctx)` against the now-deleted directory; it fails, but the marker file is still written. If that same session later creates a different worktree via a raw `git worktree add` (bypassing `EnterWorktree`), `stampAdHocRunDir`'s non-EnterWorktree path is now permanently skipped for the rest of the session (marker already exists) — no run-dir is ever stamped for that later worktree, silently defeating the #1333 mechanism this branch exists for.
