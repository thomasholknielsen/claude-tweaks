# 1544: dispatch teardown: second call attempts a teardown it cannot perform; archive-merged.js skips clean-status dirs and strands engine-state.json

Surface: infra

## Current State

Two teardown defects observed live in one headless dispatch firing (Dispatch hub run #9, 2026-08-26, group [#251], merged as PR #1518):

1. **Teardown ownership is ambiguous.** Call 2 of the two-call gate ran `ExitWorktree {"action":"remove"}` and got a structural refusal ("cannot be called from a subagent with a cwd override … this agent is already isolated"). It recovered correctly — logging a decision explaining it wasn't the worktree's creator and leaving teardown to the dispatcher — but only after the attempt, the error, and several minutes reading `cleanup-procedures.md`/reconcile sources to figure out what it *could* do. Nothing in the task prompt currently states, up front, that teardown belongs to the dispatching session and that the second call must not attempt worktree removal or run-dir archival.
2. **`archive-merged.js` skips already-clean run dirs and drops `engine-state.json`.** After `close-run` set the run dir to `status: clean, worktree: null`, the dispatcher checked whether the reconciler would archive it: `bin/lib/reconcile/archive-merged.js` skips run dirs whose `run-state.json` is already `status: clean`, and its file-move list does not include `engine-state.json` (present in this run dir since the wrap-up curation engine ran). The dispatcher had to archive manually with a plain `mv` (the dir is gitignored) and log it. Without that manual intervention, the dir sits in `pipelines/` indefinitely and every future session-start hook lists it as leftover state. Related but distinct: #1282 tracks a `move-failed` archival case; this is the skip-and-strand case.

## Deliverables

- `dispatch/task-prompt.md`'s Task-prompt composition for the second call states explicitly that worktree removal and run-dir archival are the dispatching session's responsibility, not the second call's — so a second call never attempts `ExitWorktree {"action":"remove"}` or run-dir archival at all.
- `bin/lib/reconcile/archive-merged.js` archives a run dir whose PR is merged even when its `run-state.json` already reads `status: clean` (removing or narrowing the clean-status skip condition).
- `bin/lib/reconcile/archive-merged.js`'s file-move list includes `engine-state.json` alongside the files it already moves, so archival never strands it.

## Acceptance Criteria

- A second two-call-gate Task call, given the corrected prompt text, does not call `ExitWorktree {"action":"remove"}` and does not attempt run-dir archival — teardown is the dispatching session's job in the prompt text itself, not something the second call has to discover by trial and error.
- Given a run dir with `run-state.json: {status: clean, worktree: null}` and a merged PR, `archive-merged.js` archives it (previously: skipped).
- Given a run dir containing `engine-state.json`, archiving that run dir moves `engine-state.json` along with the rest of the run dir's contents (previously: stranded).
- Existing `archive-merged.js` behavior for non-clean-status dirs and the `move-failed` case (#1282) is unchanged.

## Technical Approach

Two independent fixes: a task-prompt text addition (ownership statement, no logic change) and a targeted `archive-merged.js` change (remove/narrow the clean-status skip condition; extend the file-move list).

### Key Files

- `plugin/skills/dispatch/task-prompt.md` — add the teardown-ownership statement to the second call's prompt composition
- `plugin/skills/dispatch/two-call-gate.md` — cross-reference the ownership statement if the gate's own prose also implies otherwise
- `plugin/bin/lib/reconcile/archive-merged.js` — remove/narrow the clean-status skip; add `engine-state.json` to the archived file set

## Gotchas

- Don't broaden the clean-status skip removal so far that it archives a run dir a human is still actively reviewing — clean-status plus merged-PR is the specific combination this issue's evidence covers; confirm the merged-PR check stays a required condition, not just the status field.
- #1282's `move-failed` case is a different failure mode (an archival attempt that started and failed to complete) from this issue's skip-and-strand case (an archival attempt that never started); keep the two code paths distinguishable so a fix here doesn't mask or duplicate #1282's fix.
