# 1465: wrap-up: a dispatched run's curation fix can land after its own PR already merged

Surface: backend

## Current State

Wrap-up's Phase 2 (ROUTE) applies approved curation-row fixes (`apply-or-stage` disposition, `curation-engine.md`) as their own commits before Phase 4 (CLOSE) runs the Wrap-Up Review Console, whose Auto-merge short-circuit (`review-console.md`) merges the run's PR under `integration-model: pr-first`. The two phases rely on step sequence alone for their ordering — nothing asserts that every Phase 2 apply commit has landed before Phase 4's merge executes.

One `/claude-tweaks:dispatch`-driven `review,polish,wrap-up` run under `pr-first` observed a Skills curation-row fix (a handful of stale line-number citations in a skill doc) commit *after* that same run's own PR had already merged via the Auto-merge short-circuit. Caught immediately by the run's own self-report and corrected with a small, low-risk follow-up PR (docs-only, zero behavior change). Isolated single occurrence; no root-cause visibility beyond the self-report.

## Deliverables

- Trace the exact interleaving that let a Phase 2 curation-row apply commit land after Phase 4's Auto-merge short-circuit merge step within a single wrap-up call — identify which step, call, or async path executed out of the documented order.
- Determine whether the finding is a one-off (e.g., a specific dispatch/timing quirk in that run) or a systemic ordering gap, and record that determination in the closing commit/PR.
- If systemic: add an explicit ordering assertion or guard between Phase 2's curation apply and Phase 4's Auto-merge short-circuit — e.g., verify no pending/uncommitted curation-apply work remains immediately before the merge step executes — so a future interleaving fails loud instead of merging early.
- If one-off: document why the current step-sequence-only ordering is sufficient, and what would have to change for it to break again, so the risk is knowingly accepted rather than silently dropped.

## Acceptance Criteria

- The root cause of the observed interleaving (or a documented reason none could be reproduced) is written up in the closing commit/PR description.
- Either: an explicit ordering assertion/guard exists between `curation-engine.md`'s apply step and `review-console.md`'s Auto-merge short-circuit, with a test or a reproducible manual trace showing it fires when the ordering is violated; or: a documented decision explains why no code change is warranted, referencing the specific evidence that ruled out a systemic bug.
- No change weakens or removes the existing Phase 2-apply-then-Phase-4-merge sequence for the common (non-interleaved) case.

## Technical Approach

Read `plugin/skills/wrap-up/curation-engine.md`'s invocation sequence (its own "Ordering is load-bearing" note) and `plugin/skills/wrap-up/review-console.md`'s Auto-merge short-circuit section to map exactly which steps commit curation-row fixes and which steps trigger `_shared/pr-first-merge.md`'s merge procedure. Cross-reference `plugin/skills/wrap-up/SKILL.md`'s Phase 2 (ROUTE) and Phase 4 (CLOSE) sections for the documented sequence, and check whether any async/parallel dispatch (curation-engine's Task-agent fan-out) could let a commit land after the main thread has already moved on to Phase 4. If a guard is warranted, the natural seat is immediately before `_shared/pr-first-merge.md`'s merge call — assert the run's own worktree has no pending curation-apply output before merging.

### Key Files

- `plugin/skills/wrap-up/curation-engine.md` — Phase 2's apply-or-stage invocation sequence; ordering rule and rationale
- `plugin/skills/wrap-up/review-console.md` — Auto-merge short-circuit (Phase 4's merge trigger)
- `plugin/skills/wrap-up/SKILL.md` — Phase 2/Phase 4 phase definitions and their documented sequence
- `plugin/skills/_shared/pr-first-merge.md` — the merge procedure the Auto-merge short-circuit invokes

## Gotchas

- Isolated single occurrence with no root-cause visibility beyond the originating run's self-report — the investigation may conclude "unreproducible, accept as one-off" rather than find a mechanical cause; that is an acceptable outcome per the Acceptance Criteria above, not a failure to close this record.
- Any guard added must not introduce a new mid-flow stop in `auto` mode beyond the HARD-GATE exemption list (`_shared/auto-mode-contract.md`) — a defensive assertion that fires should fail loud (abort/report), not silently retry or prompt mid-flow.
