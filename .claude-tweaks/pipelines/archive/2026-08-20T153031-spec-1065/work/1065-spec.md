# 1065: resolve-profile.js/resolve-policy.js: anchored-or-outside guard for --run-dir/--run

Surface: backend

## Overview

`bin/resolve-profile.js` (`--run-dir`) and `bin/resolve-policy.js` (`--run`) are the last two `bin/*.js` CLIs accepting a run-directory argument with no anchoring validation — the same `[IL-127]` class #790 closed for `bin/hooks.js`/`bin/wrap-up-engine.js`/`bin/materialize.js`, and named as "the known unguarded holdouts" in `_shared/pipeline-run-dir.md`. A blind copy of #790's main-checkout-only guard is wrong here: `docs/journeys/resolve-dispatch-model-profile.md` documents `--run-dir /tmp/mp-journey` as a legitimate unanchored invocation, and test suites spawn both CLIs against `os.tmpdir()` fixtures.

This unit implements the **anchored-or-outside** rule (human-chosen direction, see Decision Rationale): a resolved run-dir path lying inside any git checkout must be anchored under the main checkout resolved from cwd; a path outside any checkout is accepted as-is. This rejects both observed [IL-127] shapes — a bare relative path resolving under a worktree cwd, and an absolute path into a linked worktree's shadow copy — with zero new flag surface and no journey/test churn.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- No opt-out/escape flag (`--allow-unanchored` was explicitly rejected — see Decision Rationale)
- No change to the three #790 guard sites (`hooks.js`, `wrap-up-engine.js`, `materialize.js`) or their exit-2 main-checkout-only semantics

- No change to `resolve-policy.js`'s existing nonexistent-dir exit-1 check — it stays, running after the new guard

## Technical Approach

Mirror #790's implementation shape, with the one semantic change. The predicate composes the two existing primitives: `mainRoot = mainCheckoutRoot(cwd)`; `resolved = path.resolve(cwd, candidate)`, then realpath'd via its nearest **existing** ancestor (the module's own `nearestExistingDir` + `safeReal` exports are exactly these primitives — reuse them, then rejoin the non-existing tail) so a symlinked alias (macOS `/tmp` → `/private/tmp`) classifies by its real location; accept if `isAnchoredUnderRoot(resolved, mainRoot)`; otherwise determine whether `resolved` lies inside *some* git checkout — walk up from its nearest existing ancestor looking for **any** `.git` entry, file or directory, counted as "inside" regardless of whether it parses as a worktree-admin pointer (do NOT test via `mainCheckoutRoot(resolved) !== null`; see the Deliverables bullet for why its null conflates two facts) — inside ⇒ reject as foreign-checkout shadow; outside (a completed walk to the filesystem root, no `.git`, no error) ⇒ accept. A walk error (e.g. unreadable ancestor) rejects — fail closed, never "outside". A null `mainRoot` with the path inside some checkout is the distinct "could not determine a repository root" case.

In `resolve-policy.js`, the guard is deliberately **orthogonal to the injectable `gitRoot` runner seam**: that seam exists so tests can control *policy-resolution's* repo root (`resolvePolicyConfig`), and it keeps doing exactly that, untouched. The guard is a filesystem-boundary check on the run-dir argument, calling `worktree-detect` directly — the same direct-call shape all three #790 sites use (`pipeline-run-dir.md`'s seam warning concerns binaries whose run-dir handling already flows through a deps seam, which this CLI's does not). Tests exercise the guard by spawning the real CLI against real fixture repos, as `resolve-policy-cli.test.js` already does, so no new injectability is needed.

## Gotchas

- **Exit-code deviation is deliberate:** the #790 family exits 2; these two CLIs keep their documented exit-1 `fail()` contract. The rewritten `pipeline-run-dir.md` paragraph must state this split explicitly — do not "fix" either side to match the other.
- **Worktree-cwd acceptance is the production path:** skills invoke both CLIs from worktree sessions with a main-anchored `$PIPELINE_RUN_DIR`. `mainCheckoutRoot(cwd)` maps a worktree cwd to the MAIN root, so those calls must keep passing — AC 1 pins this; don't accidentally anchor against the worktree root.
- **Reject before any I/O:** `resolve-profile.js`'s tally append must be unreachable on reject (AC 3's "not created or appended anywhere"); `resolve-policy.js`'s reject runs before its existing `statSync` check, and that check stays for accepted paths.
- **Point the error at `resolve-run-dir`** like the family's messages do, and keep the foreign-checkout vs no-repo-root messages distinct — collapsing them sends a reader hunting for the wrong problem (`pipeline-run-dir.md`'s own warning).
- **Concurrent-edit territory:** #1017 and #280 both propose changes to `pipeline-run-dir.md`'s Anchoring/guard prose, and #604/#538 touch `resolve-policy.js` — re-read the live paragraph and file state immediately before editing rather than trusting this spec's excerpts.
- **#280 interaction:** if a sanctioned worktree-local run-dir fallback ever ships for harness-isolated sessions, it will need a carve-out from this guard — the rejection message pointing at `resolve-run-dir` is what keeps that future diagnosable; don't add speculative support for it now.
- **Ambient-repo environments are an accepted loud-failure case:** in an environment where the temp dir's own ancestry contains a `.git` (a container with a repo at `/`, a git-managed `$HOME` that covers tmp), journey/demo invocations against that tmpdir will reject with exit 1 and the foreign-checkout message — a diagnosable refusal, never silent shadow I/O. This is accepted and deliberately not special-cased; AC 10 pins the mechanics. Do not add environment-conditional logic for it.
- **Prose-pin discipline:** `pipeline-run-dir.md` is byte-pinned by `tests/pipeline-run-dir-adoption-anchoring.test.js` — run that suite after the prose edit, and expect `npm test` (not just the new suites) to be the real gate, since conformance tests pin prose repo-wide.
- **Test discrimination:** after writing the reject-case tests, revert the guard call sites and confirm the tests fail (AC 8) — don't trust that they read correctly.

## Decision Rationale

Three directions were weighed (brainstorm, 2026-08-20, origin #853):

- **(b) conformance-tests-only** (no runtime guard; pin production prose call sites) — rejected: structurally the approach that failed twice before #790; both incidents were runtime path resolution invisible to prose scans, which is why #790's human decision chose runtime defense-in-depth.
- **(a) family guard + `--allow-unanchored` escape flag** — rejected: a flag existing solely for demos, noise in a journey that teaches model resolution rather than run-dir guarding, and cargo-cult risk of the flag leaking into production prose.
- **(c) anchored-or-outside** — **chosen (human decision):** closes the observed hazard at runtime with zero flag surface and no journey/test churn. The semantic split from the #790 family is honest, not accidental — the three #790 sites have no legitimate outside-repo use; these two CLIs do. A path inside an unrelated repo also rejects: surprising-but-safe, and it keeps the rule one sentence.
