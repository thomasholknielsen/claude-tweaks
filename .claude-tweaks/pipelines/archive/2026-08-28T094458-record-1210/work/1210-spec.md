# 1210: materialize.js accepts a main-checkout-anchored --run-dir and silently writes work/ outside the worktree

Surface: backend

## Current State

`plugin/bin/materialize.js` implements `plugin/skills/flow/materialize.md`'s resolve +
shape-gate + header-compose + write in one command. That skill file's "When this runs"
section is explicit about ordering: composing, writing, and committing the file needs a
resolved `$PIPELINE_RUN_DIR`, and the remedy is to create the worktree first, then
scaffold the run dir and materialize inside it — the file is written and committed on
the feature branch, where it is already in the right place. It warns explicitly against
writing on the pre-worktree branch under `worktree-always: true`, since that write
"lands in the main checkout, which the policy gate denies."

`materialize.js`'s own `--run-dir` anchoring guard (its header comment cites #790/#959)
rejects a `--run-dir` with no determinable git repository root, and separately accepts a
`--run-dir` that resolves inside the current linked worktree (#959). What it does not do
is compare *where cwd's worktree lives* against *where the resolved `--run-dir` lives*:
a `--run-dir` anchored to the main checkout passes the anchoring guard unconditionally
whenever it resolves to a real git root — including when cwd is itself inside a linked
worktree, which is exactly the case `materialize.md`'s own prose warns against.

Reproduced empirically (throwaway clone + `git worktree add`, invoked from inside the
worktree):
- `--run-dir /path/to/main-checkout/.claude-tweaks/pipelines/{run-id}` (the standard
  `$PIPELINE_RUN_DIR` value every other `bin/*.js --run`/`--run-dir` consumer in this
  codebase expects — `resolve-policy.js --run`, `log-decision.js --run`, `hooks.js
  spec-status --run`, `stage-item.js --run`) → exit 0, writes `work/{n}-spec.md` into
  the **main checkout**, not the worktree.
- `--run-dir /path/to/worktree/.claude-tweaks/pipelines/{run-id}` (a worktree-local
  mirror of the same run-id) → exit 0, writes correctly **inside the worktree**.

A caller following the same `$PIPELINE_RUN_DIR` convention used everywhere else in this
codebase gets a silent, exit-0 "success" that actually left an untracked file in the
main checkout — the failure mode `materialize.md`'s own prose warns against, with no
CLI-level guard catching it.

## Deliverables

- [ ] `materialize.js` detects when its own cwd sits inside a linked worktree (reuse
  `plugin/bin/lib/hooks/worktree-detect.js`'s existing main-checkout/worktree-root
  resolution rather than re-deriving it) and, when the resolved `--run-dir` is anchored
  to the main checkout instead of that worktree, derives the worktree-local
  `work/{n}-spec.md` target itself — substituting the worktree root for the
  main-checkout root in the resolved path, same run-id, same relative structure —
  rather than trusting the caller to pass a worktree-rooted `--run-dir`
- [ ] Failing that (or as a defense-in-depth backstop alongside it), a runtime
  warning/refusal — non-zero exit naming both the cwd worktree root and the resolved
  `--run-dir` — when cwd is inside a linked worktree but the resolved `--run-dir` is
  anchored to the main checkout instead: the exact combination that silently produces a
  main-checkout stray write today
- [ ] A case in `tests/materialize-run-dir-anchoring.test.js` (the existing suite
  covering #790/#959's anchoring guard) pinning that a worktree-cwd invocation with a
  main-checkout-anchored `--run-dir` either writes into the worktree or refuses — never
  silently writes to the main checkout

## Acceptance Criteria

1. From inside a linked worktree, invoking `materialize.js <n> --run-dir <main-checkout-
   anchored path>` no longer leaves an untracked file in the main checkout — it either
   resolves the worktree-local target itself, or exits non-zero naming the mismatch
2. The existing worktree-rooted-`--run-dir` invocation shape (#959, already correct)
   keeps working unchanged
3. `npm test` passes with the new regression case included

## Technical Approach

The anchoring guard lives in `materialize.js`'s option-parsing block (roughly lines
101-142: the #790/#959 comment block through the `resolvedRunDir` check). It already
calls into `worktree-detect.js` to classify `--run-dir`; extend that same call site to
also classify cwd. When cwd resolves to a linked worktree and the resolved `--run-dir`
resolves to that worktree's main checkout root instead of the worktree root itself,
either:
- rewrite the write target (the `workDir`/`outFile` composition further down the file)
  to the worktree-local equivalent path, or
- exit 2 with a message in the same style as the existing
  `unanchoredRunDirShadowMessage`/`unanchoredRunDirNoRepoMessage` helpers in
  `worktree-detect.js`, naming both roots.

`worktree-detect.js` already exposes the main-checkout-root resolution
(`mainCheckoutRoot`) used by the existing anchoring guard — reuse it for cwd's own
classification rather than adding a second, parallel implementation.

### Key Files

- `plugin/bin/materialize.js` — option-parsing/anchoring block; add the cwd-vs-run-dir
  worktree comparison and either the path-rewrite or the refusal
- `plugin/bin/lib/hooks/worktree-detect.js` — reuse (or extend, if a new export is
  needed) the existing main-checkout/worktree-root resolution helpers
- `tests/materialize-run-dir-anchoring.test.js` — add the worktree-cwd +
  main-checkout-anchored-`--run-dir` regression case

## Gotchas

- AC #2 requires the existing worktree-rooted `--run-dir` shape (#959) to keep working
  unchanged — the fix must not regress the case that's already correct.
- The non-worktree case (cwd not inside any linked worktree) must keep accepting a
  main-checkout-anchored `--run-dir` as-is; the new comparison only applies when cwd
  itself is inside a linked worktree.
- `materialize.js` is on the hot path for every `/claude-tweaks:flow` spec-materialization
  call under `worktree-always` policy — verify the fix against a real `git worktree add`
  reproduction (as the original report did), not just unit-level path-string assertions.
