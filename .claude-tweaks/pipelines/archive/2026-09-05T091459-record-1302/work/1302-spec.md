# 1302: Implement create_webhook_trigger integration for /claude-tweaks:routine (#211 core deliverable)

Surface: infra

## Current State

Refs #211. `RemoteTrigger` exposes a `create_webhook_trigger` action (`POST /v1/code/webhook-triggers`) attaching a GitHub event source to an existing routine, with a filter grammar covering author, title, body, base branch, head branch, labels, is-draft, and is-merged. `/claude-tweaks:routine`'s body-assembly logic (`skills/routine/create-and-update.md`) only ever populates `cron_expression` today — `create_webhook_trigger` is unused anywhere in the plugin. The public routines documentation separately states GitHub triggers are 'configured from the web UI only', which the tool surface appears to contradict; that contradiction is unresolved.

**Shaping-time fact-check (2026-08-23):** two prior build sessions (the original build and a ledger-resolution session, both on 2026-08-23) confirmed `RemoteTrigger` unavailable via `ToolSearch select:RemoteTrigger`, and this record was filed as `Defer-reason: blocked-dependency` on that basis. The same probe in this shaping session **succeeded** — `RemoteTrigger` is now available, with `create_webhook_trigger` in its action enum and a documented required-fields shape: the request body names a `source`/`scope` (e.g. a repository), an event list, a structured filter, and the `routine_trigger_id` of the routine to fire. The blocking dependency this record was deferred on appears resolved, at least in this session's environment — this may be a rollout that has now reached this account/environment, or may vary by session type (interactive vs. cloud/routine); the build session should re-verify via the same `ToolSearch` probe before assuming it holds unconditionally.

## Deliverables

- Call `create_webhook_trigger` against a real (or documented dry-run) routine and record its actual required fields, response shape, and any App-not-installed error behavior — the tool's own description now documents the required body shape (source/scope, events, filter, `routine_trigger_id`), so this deliverable is verification against a live call, not blind discovery.
- Resolve the doc-vs-tool contradiction: correct whichever of the public routines doc's "web UI only" claim or the tool surface itself is stale, cross-referenced from every place that repeated the old claim.
- Extend `skills/routine/create-and-update.md` with a webhook-trigger creation path parallel to the existing cron path, exposing the filter grammar's fields and operators rather than one hardcoded filter shape.
- Update `skills/_shared/routine-template-schema.md` (or the instantiated-record schema) if tracking a trigger's type/filter needs a new field, so `status`/`fleet status` can report on webhook-triggered routines.
- Surface both preconditions (Claude GitHub App install state; hourly event cap's drop-not-queue behavior) to the user at trigger-creation time.

## Acceptance Criteria

- The "web UI only" claim and the `create_webhook_trigger` tool surface no longer contradict each other in the shipped docs.
- `/claude-tweaks:routine` can create a GitHub event trigger via `create_webhook_trigger`, verified against a real (or explicitly documented dry-run) call, with the filter grammar's fields and operators exposed to the caller.
- Attempting to create a webhook trigger on a repo without the Claude GitHub App installed produces a clear, distinct message rather than a silent failure.
- The hourly event cap and its drop-not-queue behavior are documented somewhere a user configuring a webhook trigger will see before creating one.

## Technical Approach

The build session should re-run `ToolSearch select:RemoteTrigger` first to confirm tool availability holds in its own environment (interactive vs. cloud/routine sessions may differ) before proceeding. With the tool available, follow `create_webhook_trigger`'s documented body shape (`source`/`scope`, event list, structured filter, `routine_trigger_id`) to add a webhook-trigger creation path in `skills/routine/create-and-update.md`, parallel to the existing `cron_expression` path — expose the filter grammar's fields (author, title, body, base branch, head branch, labels, is-draft, is-merged) and operators to the caller rather than hardcoding one filter shape. Resolve the doc contradiction by checking which claim is actually current — the tool's existence suggests the "web UI only" doc line is stale, but confirm rather than assume. Extend the routine schema only if tracking trigger type/filter requires a new field for `status`/`fleet status` reporting.
