# 1321: /specify's Key Files derivation misses a target file's own generator/source-of-truth module

Surface: backend

## Current State

`/claude-tweaks:specify`'s Key Files composition — shaping mode (`plugin/skills/specify/shaping-mode.md`) and decomposition Step 3, both governed by `plugin/skills/specify/spec-template.md`'s `### Key Files` guidance — has no check for whether a named file is itself generated by another module in the repo. (The original filing said "materialize procedure"; `/flow`'s materialize only *reads* Key Files — the composing home is the two files above.) When a target file has a generator, the generator is what must be edited: #326's spec named only `.github/workflows/track-issue-fixes.yml`, while its source of truth, `plugin/bin/lib/issue-branch-tracking.js`'s `generateWorkflowYaml()` — whose header comment names the generated path verbatim — was never listed, so the build edited the generated file. Only review's independent `tests/` search caught it.

The rename-grep paragraph in `spec-template.md`'s `### Key Files` (incident `[IL-132]`) is the structural precedent: a documented grep that finds a surface's *consumers*. This work adds its mirror — a grep that finds a file's *producer*.

The multi-signal heuristic the original filing proposed (export-name matching on `generate*`/`render*`/`build*`, `tests/` import tracing, output-plausibility judgment) was evaluated and rejected at design time: ~20 modules in `plugin/bin/lib/` match the export-name pattern and most are runtime renderers that never produce a committed file, so that signal is mostly noise, and "output plausibly matches" is not a repeatable procedure.

## Deliverables

- [ ] A **generated-file grep** paragraph in `plugin/skills/specify/spec-template.md`'s `### Key Files` guidance, directly after the rename-grep paragraph, same voice: for each composed Key Files entry, grep executable code (`plugin/bin/`, `plugin/hooks/`, `scripts/`, `tools/`) for the entry's basename, excluding the entry itself and the rename-grep's historical-mention skip list — shared by reference (one list, the rename-grep's own; never a diverging copy), with a build-time check on whether it needs generator-specific additions. **Fallback trigger (concrete, not judgment):** when the basename matches more than one tracked file (`git ls-files | grep -c "/{basename}$"` returns > 1) or the bare-basename grep returns too many hits to read, re-grep with the entry's repo-relative path instead; the byte-pinned snippet covers the basename form only, and the path fallback is stated in the same paragraph as documented guidance, not a second pinned snippet. Read each hit and classify: a module that generates or writes the target's content is its source of truth — a hit that both reads and writes still counts as a producer — so add a Key Files bullet naming that module as the generator of the target and treat the generator as the primary edit target; a hit that merely reads the target is a consumer (rename-grep territory) and is skipped. The paragraph carries the grep as a byte-pinnable snippet with a `{basename}` placeholder and anchors the #326 incident.
- [ ] Once a generator is identified, the generated file's own Key Files bullet is annotated in place — `generated by \`{module}\` — edit the generator, not this file` — so the derivative entry can never again read as the primary edit target (#326's exact failure mode: the build edited the generated file even though it was listed).
- [ ] `plugin/skills/specify/shaping-mode.md`'s Key Files sentence (the one citing the rename-grep) gains one clause naming the generated-file grep alongside it.
- [ ] A conformance suite `tests/spec-template-generator-grep.test.js` per the `skill-prose-conformance-tests` skill's conventions (read that skill before writing the suite): pins that the paragraph and snippet exist; extracts the byte-pinned snippet, substitutes `track-issue-fixes.yml`, executes it against the live repo, and asserts `plugin/bin/lib/issue-branch-tracking.js` appears in the output; a negative control substitutes a producer-less basename and asserts zero executable-code hits.
- [ ] Verify whether `plugin/skills/specify/record-creation-subissues.md` carries a parallel Key Files citation needing the same one-clause touch (design-time grep found none — decomposition Step 3 inherits via its wholesale `spec-template.md` reference); touch it only if it does.

## Technical Approach

Mirror the rename-grep paragraph's structure exactly — one grep, a skip list, a read-and-judge classification, an incident anchor. The four searched directories (`plugin/bin/`, `plugin/hooks/`, `scripts/`, `tools/`) are this repo's closed conventional set of executable-code locations — the paragraph states that explicitly, and a generator living anywhere else is a second accepted miss, recorded alongside the first. Conservative by construction: a module naming the exact path/basename either produces, consumes, or documents the target, and one read disambiguates. Accepted misses, by design: a generator that assembles the target path by string concatenation never matches, and a generator outside the four conventional directories is not searched — the conservatism the original filing's Gotcha asks for. Suggested snippet shape: `grep -rln "{basename}" plugin/bin plugin/hooks scripts tools 2>/dev/null`.

# Reflect — staged finding 1

**Category:** tangential

Origin: reflect wrap-up from #326
Defer-reason: tangential

## Current State

`/claude-tweaks:specify`'s materialize procedure writes a spec's Key Files section from the
files a human/agent identifies as directly relevant to the change. It has no check for whether
one of those files is itself generated by another module in the repo (e.g. a `bin/lib/*.js`
`generate*()` function, documented in that target file's own header comment or exercised by a
`tests/` fixture that imports the generator). #326's spec named only
`.github/workflows/track-issue-fixes.yml` in its Key Files section; the actual single source of
truth, `plugin/bin/lib/issue-branch-tracking.js`'s `generateWorkflowYaml()`, was never listed and
was consequently never touched by the build — a defect only caught because review independently
searched `tests/` for coverage of the target file before trusting the diff (`ceremony-profile:
fast-lane` skips /review's own Step 1 Spec Compliance Check, so no gate would have caught this
otherwise).

## Deliverables

- [ ] When materializing a spec's Key Files list, check each named file for a generator
  relationship — a `tests/*.test.js` that `require()`s a `bin/lib/*.js` module whose exported
  function name matches (`generate*`, `render*`, `build*`) or whose output the file's own content
  plausibly matches, or a header comment naming a generator — and if found, add the generator
  module to Key Files alongside the generated file.
- [ ] Document the check in `specify`'s materialize procedure so the derivation is repeatable,
  not ad hoc.

## Acceptance Criteria

1. A spec whose Key Files include a file with a discoverable generator module also lists that
   generator module in Key Files.
2. The check has a test fixture exercising at least one real generator/generated pair in this
   repo (e.g. `issue-branch-tracking.js` / `track-issue-fixes.yml`).

## Gotchas

- Keep the detection heuristic conservative — false positives (flagging an unrelated file as
  "generated") add noise to every spec's Key Files section for no benefit.
