# 1435: specShapedBody: $` in a literal replacement string triggers String.replace() self-splicing corruption

Surface: backend

## Current State

`specShapedBody`&#39;s body composer can silently corrupt a filed record&#39;s body when a composed literal string handed to JS&#39;s `String.replace(pattern, literalReplacement)` contains a `` $` `` (dollar-backtick) sequence — `.replace()`&#39;s replacement-string grammar treats `` $` `` as &#34;everything before the match&#34; and splices the preceding text back in. Observed on issue #1391 (filed via `capture`&#39;s `specShapedBody`): Deliverable bullet 1 was meant to read the literal backtick-quoted regex pair `` `^RECOMMEND_BUILD: (true|false)$` / `^RECOMMEND_MERGE: (true|false)$` ``, and the entire preceding body got spliced in three times, nested, in its place. The materialization shape gate (`## Current State`/`## Deliverables`/`## Acceptance Criteria` present and non-empty, no unresolved-placeholder markers) does not catch this — the sections stay nominally present; only their content is garbled. (#1391&#39;s body has since been manually corrected.)

Confirmed during this shaping pass: `specShapedBody` itself (`plugin/bin/lib/issues/record.js`) composes its output via array `push`/`join(&#39;\n\n&#39;)`, not `.replace()` — `git log -p -S&#34;specShapedBody&#34;` shows it has never used `.replace()` in its history, so the corruption did not originate inside that function&#39;s own body. The exact call site is therefore still unconfirmed and is this record&#39;s first deliverable, not a foregone conclusion. Two candidates surfaced by a repo-wide `.replace(pattern, )` sweep:

- The &#34;hand-rolled compose-then-extract `node -e` pair&#34; `plugin/skills/capture/SKILL.md` (line ~176) says `plugin/bin/compose-record.js` (#686/#800) replaced — worth checking whether that pre-migration snippet, or an equivalent still-uninlined pattern elsewhere, used `.replace()` on composed prose.
- `plugin/skills/specify/record-creation.md`&#39;s post-create recompose steps (the `**Related:** #N` cross-link write and the origin-collapse body carry-forward) describe &#34;recompose each record&#39;s full body ... and write it once&#34; — if any executable path backing these prose instructions does that recomposition via `.replace(oldSection, newComposedText)` rather than full reassembly, it inherits this exact bug whenever `newComposedText` contains `` $` ``, `$&amp;`, `$&#39;`, `$$`, or `$`.
- One live, lower-risk example of the same unsafe shape: `plugin/bin/lib/feedback/file-feedback.js`&#39;s `embedFingerprint` (line 136) does `String(body).replace(marker, line)` where `line` is a variable, not a literal. Not exploitable today — `line` is always ``  `` — but shares the shape and should be hardened defensively.

## Deliverables

- [ ] Identify the exact call site(s) inside `specShapedBody`&#39;s callers (or wherever captured/shaped bodies are composed) that build body text via `.replace(pattern, literalTemplateString)` where `literalTemplateString` can itself contain a raw `$`-prefixed replacement token (`` $` ``, `$&amp;`, `$&#39;`, `$$`, `$1`...) — start from the two candidates named in Current State plus `file-feedback.js:136`.
- [ ] Fix every confirmed site to use a function replacer (`.replace(pattern, () =&gt; literalTemplateString)`) or escape `$` as `$$` in the substituted text before passing it as a literal replacement argument.
- [ ] Sweep already-filed records (open + recently closed) for the same corruption shape — a Deliverables/body section containing an implausibly repeated/nested copy of earlier body text — and fix any found.
- [ ] Add a regression test asserting a substituted value containing `` $` `` survives composition unchanged, at every fixed call site.

## Acceptance Criteria

1. A unit test feeding a literal replacement string containing `` $` `` through each fixed composition path produces output with that literal string intact, not the preceding text spliced in.
2. `npm test` passes.
3. The sweep&#39;s findings (fixed records, if any) are reported.

## Technical Approach

Reproduce first: write a throwaway Node repro (`&#34;abc&#34;.replace(/b/, &#34;$\`&#34;)` style) to confirm the exact splice shape described in Current State, then grep for it. Since `specShapedBody` itself is already clean, treat this as a call-site audit rather than a single-function patch — check `plugin/bin/compose-record.js` and its `plugin/bin/lib/compose-record/` helpers for any `.replace()` usage introduced or left over from the `node -e` pair it replaced, and check whether `record-creation.md`&#39;s prose-described recompose steps correspond to an executable helper (vs. being executed ad hoc by the invoking agent) — if the latter, the fix is a documentation/contract change instructing full reassembly instead of `.replace()`, not a code change. Harden `file-feedback.js:136`&#39;s `embedFingerprint` regardless, since it&#39;s the one surviving instance of the unsafe pattern in current code. For the sweep, script a search across `work/*.md` / open GitHub issues for a body section whose content looks like a truncated-then-repeated copy of an earlier section (heuristic: a section&#39;s text containing another section&#39;s heading string) rather than manually reading every record.

### Key Files

- `plugin/bin/lib/issues/record.js` — `specShapedBody`; reference composition function (array-push + join, confirmed already safe) — the call sites consuming its output are the actual audit target
- `plugin/bin/lib/feedback/file-feedback.js` — `embedFingerprint`&#39;s `body.replace(marker, line)` call; harden with a function replacer
- `plugin/bin/compose-record.js` and `plugin/bin/lib/compose-record/` — the CLI that replaced the hand-rolled `node -e` pair; confirm no `.replace()`-based composition survived the migration
- `plugin/skills/specify/record-creation.md` — post-create recompose steps (`**Related:**` cross-link, origin-collapse carry-forward); confirm the described procedure is full reassembly, not a `.replace()` substitution

## Gotchas

- `specShapedBody` (record.js) has never used `.replace()` in its own history (verified via `git log -p -S&#34;specShapedBody&#34;`) — don&#39;t assume the fix is inside that function; it&#39;s the callers that need auditing.
- #1391&#39;s body has already been manually corrected, so the sweep&#39;s job is finding *other* still-corrupted records, not re-checking #1391.
- Fixing `file-feedback.js:136` is precautionary hardening, not proof of a live corruption there today — `fingerprint` values are always hex, so `` $` `` cannot appear in practice yet, but the shape is identical to the confirmed-exploitable one.
