# 1348: file-lock.js's acquireLock fails open on first use against a brand-new store — lost decline entries under concurrency

**Related:** none

Context: Surfaced while resuming build+test for #614 — `node --test tests/bin-lib/declined-learning/store-concurrency.test.js` failed 5/5 consecutive isolated runs on a freshly-merged `origin/main`, unrelated to #614's own (CLAUDE.md-only) diff (`git diff origin/main -- tests/bin-lib/declined-learning/store-concurrency.test.js plugin/bin/lib/declined-learning/ plugin/bin/lib/file-lock.js` is empty).

## Current State

`plugin/bin/lib/file-lock.js`'s `acquireLock(lockPath)` calls a plain (non-recursive) `fs.mkdirSync(lockPath)`. When `lockPath`'s parent directory does not yet exist — true the first time anything writes to a given store, e.g. `.claude-tweaks/declined-learning/` before any `recordDecline` call has run — `mkdirSync` throws `ENOENT`, not `EEXIST`. The catch block only distinguishes `EEXIST` (retry/wait) from everything else, which it treats as "nothing to lock" and returns `null` immediately (fail-open). The parent directory only gets created later, as a side effect of `json-store.js`'s `writeJsonFile` (which does `mkdirSync(dir, { recursive: true })` before writing) — inside the very critical section the lock was supposed to guard.

Net effect: when N processes race to be the *first* writer against a brand-new store, every one of them hits the ENOENT path in `acquireLock` before any of them has created the parent directory, so all N return `null` (unlocked) and proceed concurrently with no synchronization at all. Deterministic, not timing-load-dependent — reproduced 5/5 runs, worker completion times ~2ms, far under any staleness/timeout window, confirmed by direct code read of the ENOENT branch, not just repro.

`tests/bin-lib/declined-learning/store-concurrency.test.js`'s first test exists specifically to guard against a lost-update race in this exact module (its docstring cites a prior whole-branch-review finding, "fixed" per the 6.104.1 release notes: "declined-learning store race + atomic writes") — the fix evidently didn't cover the fresh-store bootstrap case, so the regression test still fails against current `main`.

`bin/lib/hooks/context.js`'s `acquireRunStateLock` is the sibling implementation `file-lock.js`'s own header says this module was generalized from — worth checking whether it shares this gap or already avoids it.

## Evidence

- Repro (8 concurrent child processes, `CLAUDE_TWEAKS_LOCK_WAIT_MS=60000`, effectively-unbounded wait budget) against a fresh `fs.mkdtempSync` project: 3 of 8 fingerprint entries silently lost, all 8 workers exit 0 (no errors, no timeouts), all writes timestamped within ~2ms of each other.
- `node --test tests/bin-lib/declined-learning/store-concurrency.test.js` failed 5/5 consecutive isolated runs post-merge-from-origin/main.
- `git diff origin/main -- tests/bin-lib/declined-learning/ plugin/bin/lib/file-lock.js` empty — unmodified origin/main content.

## Deliverables

- Fix `acquireLock` so a missing parent directory doesn't short-circuit straight to fail-open: create the lock path's parent directory (`mkdirSync(path.dirname(lockPath), { recursive: true })`, tolerating a concurrent creator) before attempting `fs.mkdirSync(lockPath)`, so the ENOENT branch can no longer fire on legitimate first-use races. Re-verify the `EEXIST`/stale-reclaim branches are unaffected.
- Check `bin/lib/hooks/context.js`'s `acquireRunStateLock` for the same gap.
- Confirm the regression test passes reliably post-fix across several consecutive isolated runs.

## Acceptance Criteria

- [ ] `acquireLock` no longer fails open when the lock path's parent directory doesn't yet exist — it creates the parent (tolerating a concurrent creator) and proceeds to the normal mkdir-based mutex attempt.
- [ ] `node --test tests/bin-lib/declined-learning/store-concurrency.test.js` passes reliably across several isolated runs.
- [ ] `bin/lib/hooks/context.js`'s sibling lock implementation is checked for the same gap; fixed or noted if found.

## Gotchas

- Don't widen the `EEXIST` check to swallow all errors — that would mask real permission/disk failures as "nothing to lock." Handle "parent directory missing" specifically, by creating it.
- `withLock`'s fail-open contract elsewhere (timeout, unreadable lock) is intentional ("never break a caller over bookkeeping state") — preserve it; this fix only closes the fresh-directory bootstrap gap.
