# 1423: capture/specify: declare a blocked-by edge when Current State narrates another record's not-yet-merged follow-up as fact

Surface: backend

## Current State

Record #1315's materialized spec narrated `bin/lib/issues/grant-maturation.js`'s `evaluateMaturation` and its two call sites (`settle-and-merge.md`'s Auto-merge gate, `auto-merge-short-circuit.md`'s Authorization layer) as already existing — "added in a #309 fix-wave follow-up" — in its Current State section. In fact #309 was, and remains, open and unimplemented: a repo-wide grep for `evaluateMaturation`/`vetoWindowHours`/`grant-veto-window-hours` found zero matches, confirmed against a worktree caught up with `origin/main`. The record carried no `blocked-by:` dependency edge against #309 (the mechanism exists per `_shared/work-record-config.md`'s `work-links` config key — `native` sub-issue/blocked-by APIs or `body-text` `Blocked by #N` lines), so nothing structural deferred the record. `/claude-tweaks:build`'s own prerequisite-check grep caught the gap at build time — three attempts deep, per the dispatch retry ceiling — rather than at authoring time.

## Deliverables

- `/claude-tweaks:capture` (or whichever authoring path produces a record narrating dependent work as settled fact in its Current State/Deliverables text) detects a reference to another record/PR number describing "added/introduced in a #N follow-up" or equivalent phrasing, and either prompts for or auto-populates a `blocked-by: #N` edge via the project's configured `work-links` mechanism.
- `_shared/work-record.md` (or the capture skill's own SKILL.md) documents this as an authoring-time check, not just a build-time recovery.

## Acceptance Criteria

- A record whose body text describes work "added in #N's follow-up" is either rejected without a `blocked-by:` edge, or has one auto-populated, at authoring time (capture/specify), before it reaches `ready`.
- Dependency-aware ordering (`flow/SKILL.md`'s Multi-Spec pre-flight DAG, `dispatch`'s queue) can then defer such a record structurally without relying on build's own late verification.

## Technical Approach

Add a phrase-detection pass over the record's body text — regex/heuristic matching on patterns like "added in #N", "introduced in #N('s) follow-up", "will be added by #N" — run at authoring time rather than only at `/claude-tweaks:build`'s late prerequisite-check grep. Wire it into whichever authoring path actually composes the narrating text: `/claude-tweaks:capture`'s Shaped-body branch, and/or `/claude-tweaks:specify`'s shaping-mode body-composition step for records shaped outside `/capture`'s chain. When a match is found and no existing `blocked-by:`/`Blocked by #N` edge already names the same number, either prompt (interactive modes) or auto-populate (`--chained`/auto mode) the edge, branching on the project's `work-links` config key (`native` sub-issue/blocked-by APIs vs. `body-text` `Blocked by #N` lines — `_shared/work-record-config.md`) rather than hardcoding one form.

### Key Files

- `plugin/skills/capture/SKILL.md` — Shaped-body branch composes the record body; add the phrase-detection + blocked-by prompt/auto-populate step here.
- `plugin/skills/specify/shaping-mode.md` — shaping mode's body-composition step; add the same detection for records shaped outside `/capture`'s chain.
- `plugin/skills/_shared/work-record.md` — document the check as an authoring-time safeguard, alongside the existing `Blocked by #N` / Decomposition rules content.

## Gotchas

- The phrasing heuristic needs care to avoid false positives — a record can legitimately reference another record/PR number by name without implying a dependency (e.g. "similar to the fix in #309" is not "depends on #309's follow-up").
- Whether the check lands in `/claude-tweaks:capture`, `/claude-tweaks:specify`, or both is an implementation decision for the build — both are authoring paths that can produce a narrating body, and `/capture` can chain into `/specify --chained` in the same turn.
- Auto-populating the edge must branch on the live `work-links` config value rather than assuming one form, since the two mechanisms (`native` vs `body-text`) are structurally different writes.
