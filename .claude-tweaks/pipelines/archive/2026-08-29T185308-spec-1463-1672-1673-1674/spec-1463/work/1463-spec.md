# 1463: SessionStart hook: "work appears shipped" heuristic false-positives on a freshly-created, zero-commit worktree

Surface: backend

## Current State

`checkRunIntegrity()` in `plugin/bin/lib/hooks/run-integrity.js` reports a run as `shipped-unclosed` (SessionStart's "work appears shipped" advisory) whenever `mergedEvidence()` finds the recorded branch is an ancestor of the integration branch, plus a non-wrap-up `skill_invoked` ledger event. But `merge-base --is-ancestor branch integration` is trivially true for a branch that has never diverged from its base at all — a freshly created worktree with zero commits of its own is, by definition, an ancestor of the branch it forked from. The heuristic cannot currently distinguish "already shipped via a real fast-forward/plain merge" from "hasn't started building yet," both of which produce identical `ancestor` evidence.

This was observed live: a fresh worktree was flagged as shipped and merged, a bookkeeping-only `close-run` was recommended and attempted, `close-run`'s own ownership check refused it ("recorded by another session"), and a follow-up check moments later showed the branch had since gained real commits — the run was genuinely in progress. No data was lost, but the guidance was actively misleading, and a caller without that ownership backstop (or one using `--force`) would not have been so lucky.

The `cherry` evidence path (squash-equivalent detection) does not share this flaw: `git cherry integration branch` only returns non-empty when the branch has at least one commit not present on integration, so cherry evidence already implies real divergent work exists.

## Deliverables

- `mergedEvidence()`'s `ancestor` result is corroborated before `checkRunIntegrity()` treats it as shipped evidence: the branch must have at least one commit dated at or after the pipeline run directory's own start time.
- The run's start time is derived from the run directory's existing ISO-timestamp-prefixed name (`YYYY-MM-DDTHHMMSS-{slug}`, the same encoding `run-dir-resolve.js`'s `formatTimestamp()` produces) — no new fields written to `run-state.json`, no schema change.
- When the branch has zero commits at or after that timestamp, `checkRunIntegrity()` falls back to `in-progress` instead of `shipped-unclosed`, even though `mergedEvidence()` still returns `'ancestor'`.
- The `cherry` evidence path is untouched — it already requires at least one divergent commit by construction.

## Acceptance Criteria

- A worktree/branch created from the integration branch with zero commits of its own (branch trivially an ancestor of integration) yields `in-progress`, not `shipped-unclosed`, even when a non-wrap-up ledger event is present.
- The existing AC1 scenario (real commit on the feature branch, then fast-forward/plain-merged into integration) still yields `shipped-unclosed` via `ancestor` evidence — the fix must not regress genuine shipped detection.
- The existing AC2 scenario (squash-merge, `cherry` evidence) is unaffected.
- All existing `tests/run-integrity.test.js` cases continue to pass; a new test covers the zero-commit false-positive case.

## Technical Approach

Add a helper that parses the run directory's ISO-timestamp prefix (matching the existing `RUN_ID_RE`/`formatTimestamp()` convention in `context.js`/`run-dir-resolve.js`) into a `Date`, then, only on the `ancestor` branch of `mergedEvidence()`'s result, run a bounded git query (e.g. `git log {branch} --since={run-start-ISO} --oneline`, via the existing `runGit()` wrapper) to check for at least one commit at or after that time. Indeterminate git results fail open to `in-progress`, consistent with every other field in this module's fail-open contract. The `cherry` branch is unchanged.

The run directory's own timestamp is used as the corroboration reference rather than the alternative the original report floated (a recorded "branch creation point" commit count): `run-state.json` records no base SHA today, and adding one would be a schema change to a file multiple hook verbs (`record-worktree`, `record-pr`, `close-run`) already read/write. The run directory name already encodes exactly the reference point needed (its creation timestamp), so reusing it avoids a schema change while answering the same question — has any commit landed on this branch since this run started.

### Key Files

- `plugin/bin/lib/hooks/run-integrity.js` — add the run-start-corroboration check to the `ancestor` evidence path in `mergedEvidence()`/`checkRunIntegrity()`
- `tests/run-integrity.test.js` — add a test for the zero-commit ancestor false-positive; verify existing AC1/AC2 tests still pass

## Gotchas

- `--since` filters by commit date, which can be affected by rebases/amends with altered timestamps — an edge case, not the common path this fix targets.
- Fail-open is per-field in this module: if the run-start timestamp can't be parsed from the directory name, or the git query is indeterminate (timeout/spawn/no-git), the corroboration check must resolve toward `in-progress`, not toward `shipped-unclosed` — mirrors every other evidence field's fail-open convention already documented in the file's header comment.
- A non-canonical run-dir name (`NON_CANONICAL_RUN_ID_RE`, no dashes in the timestamp) is out of scope here — `session-start.js` only calls `checkRunIntegrity()` on dirs already filtered by `iterRunDirsWithState()`, which matches the canonical `RUN_ID_RE` form.

## Original request

SessionStart hook: "work appears shipped" heuristic false-positives on a freshly-created, zero-commit worktree

**Summary:** SessionStart's unfinished-pipeline-run notice can claim a branch was merged when it has simply never diverged from its base yet.

**Kind:** Defect

**Affected component:** SessionStart hook (unfinished-pipeline-run detection)

**Repro steps:**
1. Create a pipeline run's worktree (0 commits ahead of its base).
2. Before any work lands on it, let a SessionStart check run against it.

**Expected vs. actual:**
Expected: the hook should not assert the branch was merged when it has no commits of its own yet.
Actual: it reported "work appears shipped (branch merged into the integration branch, no wrap-up recorded)" and recommended a bookkeeping-only `close-run`. Attempting that (with user confirmation) was refused by `close-run` itself — "recorded by another session" — and a follow-up check moments later showed the branch had gained real commits: the run was genuinely live, not shipped or abandoned. No data was lost — `close-run`'s own ownership check is what prevented it — but the heuristic's guidance was actively misleading, and a caller without that backstop (or one that used `--force`) would not have been so lucky.

Suggested fix: the "work appears shipped" check should require either a nonzero commit count ahead of the branch's own creation point, or actual PR-merge evidence, before asserting the branch was merged — ancestor-of-integration-branch alone is not sufficient, since it's also true of a branch that simply hasn't started building yet.
