# 1674: pre-tool-use.js: bound hasMaterializeCommit git log range to integration..HEAD

Surface: backend

## Overview

`hasMaterializeCommit` in `plugin/bin/lib/hooks/pre-tool-use.js` runs an unbounded `git log --oneline -1` over a worktree's full reachable history, so a fresh worktree that merely inherits an unrelated, already-merged run's materialize commit gets denied by the IL-131 edit guard as if it carried its own unstamped one. Bound the range to `{integration}..HEAD` so only commits unique to the worktree count, and update the guard's documented contract to match.

**Complexity:** Low
**Estimated tasks:** 4

## Non-Goals

- Not changing the evidence path for `shipped-unclosed` detection (#1672) or reconcile's auto-close criterion (#1673).
- Not changing `record-worktree`'s unknown-flag handling — that's #1012's territory (open, `ready`, `auto:build`).
- Not tracking worktree "ownership" as a new concept — the fix is a range bound on an existing check, not a new data model.

## Current State

- `plugin/bin/lib/hooks/pre-tool-use.js` — `hasMaterializeCommit(wtRoot, ctx.runDir)` runs `runGit(['log', '--oneline', '-1', '--', ...], worktreeRoot)` with no ref-range bound, walking all of `HEAD`'s reachable history rather than commits unique to `wtRoot`. Once a run's materialize commit has shipped and merged into the integration branch, it becomes part of every later worktree's inherited history, so this unbounded check false-positives against any fresh worktree.
- `plugin/bin/lib/hooks/worktree-reap.js` — exports `resolveIntegrationBranch`, already imported by `run-integrity.js`, resolving the integration branch per `_shared/integration-branch.md`'s canonical ladder.
- `docs/hooks.md` — documents the IL-131 guard's current (unbounded) behavior implicitly through the incident-log entry; needs updating once the range bound lands.

## Deliverables

- [ ] Change `hasMaterializeCommit`'s `runGit` call to bound the range: `${integration}..HEAD` instead of an unbounded `-1` walk, resolving `integration` via `resolveIntegrationBranch` (imported from `./worktree-reap`, the same helper `run-integrity.js` already uses).
- [ ] A failure to resolve the integration branch fails open (skip the check / return `false`) — matching this file's existing "ambiguity resolves toward not alarming" convention.
- [ ] Update `docs/hooks.md`'s IL-131 guard description to document the range-bounded behavior.
- [ ] Add a `docs/incident-log.md` entry (or update the existing IL-131 entry) noting this correction, per this repo's convention of documenting IL-131-adjacent fixes.

## Acceptance Criteria

1. A fresh worktree with zero commits beyond the integration branch, whose only "materialize commit" match comes from history it inherited from an unrelated, already-merged run, is never denied by the IL-131 guard.
2. A worktree that itself carries an unmerged materialize commit (i.e., within `{integration}..HEAD` for that worktree) with no recorded `record-worktree`/`record-pr` stamp is still denied exactly as before (record #991's original fix) — a regression check, not new behavior.
3. A failure to resolve the integration branch causes the check to fail open (skip / `false`), never a false denial.
4. `npm test` passes, including new `pre-tool-use` coverage for the inherited-history case (AC1), the regression case (AC2), and the integration-branch-unresolvable case (AC3).

## Technical Approach

Replace the unbounded `git log --oneline -1 -- {paths}` call with the same call scoped to `${integration}..HEAD`, resolving `integration` via `resolveIntegrationBranch` from `./worktree-reap` — the identical helper `run-integrity.js` imports for the same purpose, so this fix reuses existing resolution logic rather than adding a second one. Get the range direction/inclusivity right: `{integration}..HEAD` means "commits reachable from HEAD but not from integration" — exactly the worktree's own unique history.

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — `hasMaterializeCommit`: bound the `git log` range
- `plugin/bin/lib/hooks/worktree-reap.js` — `resolveIntegrationBranch`: reused, not modified
- `docs/hooks.md` — update the IL-131 guard contract description
- `docs/incident-log.md` — record this fix's own incident-log entry

## Gotchas

- Get the range direction/inclusivity wrong and both this fix and IL-131's original protection break silently — no test failure until a real regression scenario is exercised. Test both directions explicitly (Acceptance Criteria 1 and 2).
- This deliverable's `docs/hooks.md`/`docs/incident-log.md` updates are prose-only for this specific fix — don't conflate with #1100's broader run-state ownership-contract documentation work (a separate, already-specified record).
