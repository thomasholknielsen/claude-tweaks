# 1011: residue.js blast-radius scope filter tags any merged branch/pipeline-run repo-wide, not just this run's own artifacts

Origin: reflect wrap-up from #630
Defer-reason: pre-existing-outside-diff

## Current State

`plugin/bin/lib/residue/probes/branches.js`'s `probeBranches()` tags every merged-but-undeleted remote branch as `scope: 'blast-radius'` unconditionally (excluding only the integration branch and the current run's own head branch) — it never checks whether the branch was actually created by the current run's own worktree/record. `plugin/bin/lib/residue/scope-filter.js`'s `--scope blast-radius` CLI flag only filters by each finding's own `scope` field, trusting the probe's tagging. This contradicts `skills/wrap-up/residue-sweep.md`'s stated intent for the `--scope blast-radius` flag: "a finding belongs on this run's ledger only if it is this run's own blast radius (a branch this run's worktree left behind, a PR from this run's own head branch...)".

Discovered during record #630's wrap-up: running `node bin/residue.js --base <merge-base> --integration-branch origin/main --scope blast-radius` from the `worktree-dispatch-record-630` worktree returned `origin/worktree-record-766` and `origin/worktree-record-860` as blast-radius branch findings — both belonging to other, concurrently-running dispatch sessions (record-860's worktree was confirmed still live and locked by an active session at the time). The same run also returned 5 "clean but unarchived" pipeline-run-dir findings for records 861, 789, 627, 767, 879 — none of them #630's own run directory. A likely-identical gap exists in the pipeline-run probe (not independently verified against source, but the finding shape matches).

## Deliverables

- [ ] Add a same-run/same-record ownership check to `probeBranches()` before tagging a merged branch `scope: 'blast-radius'` — e.g. compare the branch's own record/spec-slug component against the current run's own head branch, or restrict to branches this run's own worktree(s) created (git reflog / branch creation provenance), consistent with the file's own stated purpose.
- [ ] Audit the pipeline-run-dir probe (find its file under `plugin/bin/lib/residue/probes/`) for the same class of gap and apply the same fix if present.
- [ ] Add a regression test asserting that a merged branch belonging to a *different* concurrent worktree/record is NOT tagged `blast-radius` when probed from this run's own worktree.

## Acceptance Criteria

1. `probeBranches()` (and the pipeline-run probe, if it has the same gap) only tags a finding `scope: 'blast-radius'` when it can attribute the artifact to the current run's own worktree/record — not merely "merged into the integration branch, from anywhere."
2. A new test reproduces the #630 discovery shape: two concurrently-existing merged branches, only one belonging to the probing run's own worktree, and asserts only that one surfaces under `--scope blast-radius`.
3. `npm test` passes in full.

## Why this matters

A wrap-up's Phase 1 ledger fix-exhaust step auto-applies `remedy: auto` findings that qualify (per `_shared/deferral-gate.md`'s fix-now criteria) without further per-item confirmation. If a future wrap-up's own ledger legitimately reaches Phase 1 fix-exhaust for a `kind: branch`/`kind: pipeline-run` item sourced from this over-broad tagging, it risks auto-deleting a remote branch or archiving a pipeline run directory that actually belongs to a different, live, concurrently-running dispatch session — the exact cross-session interference class this project's own CLAUDE.md memory notes (`hooks.js record-worktree without --run corrupts another session's state`, `check-sibling-sessions-before-starting-a-record`) already warn about elsewhere in the pipeline.
