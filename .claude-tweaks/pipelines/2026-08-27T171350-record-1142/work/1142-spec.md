# 1142: materialize.js cannot write work/ into the worktree its own contract mandates

Surface: backend

Origin: reflect full from #1071
Defer-reason: tangential

## Current State

`flow/materialize.md`'s "When this runs" mandates the materialized spec's `work/` directory be created inside the run's worktree at the matching relative path and committed as the branch's first commit. But `bin/materialize.js` conflates its `--run-dir` anchoring guard with its write target: it rejects any worktree-resolving path (`isAnchoredUnderRoot` — a worktree's `.git` FILE fails the check) and writes `{runDir}/work/` only under the main checkout. The `pre-tool-use` pipeline-shadow guard additionally blocks Bash `mkdir`/`Write` of the worktree run-dir path with no carve-out for the documented `work/` tracked exception. Run 2026-08-20T154424-spec-1071 (and, by layout evidence, sibling flow runs) worked around this by letting the CLI compose into the main run dir, then hand-moving the file via `node -e` fs calls and deleting the main copy.

## Deliverables

- [ ] `bin/materialize.js` gains an explicit worktree write mode (e.g. `--worktree <path>`, or auto-detection of a linked-worktree cwd) that keeps the `--run-dir` anchoring guard for run-dir *identity* while writing `work/{n}-spec.md` to the worktree's matching relative path, per `materialize.md`'s documented sequence.
- [ ] The `pre-tool-use` pipeline-shadow guard (`shadowPipelineRunDir`) allows creation of `{run-id}/work/` under a worktree when the anchored main-checkout run dir for the same `{run-id}` already exists — the documented tracked exception — while still refusing config/decisions/staged shadows.
- [ ] `flow/materialize.md`'s "When this runs" names the CLI invocation for the worktree write instead of leaving the mechanics to the caller.
- [ ] Tests: a materialize-cli case pinning the worktree write path, and a hooks-gate-coverage case pinning the narrowed shadow-guard carve-out.

## Acceptance Criteria

1. From a linked-worktree cwd, one documented `materialize.js` invocation produces `{worktree}/.claude-tweaks/pipelines/{run-id}/work/{n}-spec.md` with no file left in the main checkout's run dir (pinned by test).
2. The shadow guard still refuses creating `{run-id}/config.yml`/`decisions.md`/`staged/` (or a run dir with no anchored twin) inside a worktree (pinned by test).
3. `flow/materialize.md` documents the invocation; `npm test` passes.

## Technical Approach

Keep `isAnchoredUnderRoot` for the `--run-dir` argument (identity stays anchored, [IL-127] intact); add a separate resolved write root. The guard carve-out keys on the last path segment being `work` (or a `spec-{N}/work` tail) plus the anchored twin existing.

### Key Files

- `plugin/bin/materialize.js` — split guard target from write target
- `plugin/bin/lib/hooks/pre-tool-use.js` — `shadowPipelineRunDir` work/ carve-out
- `plugin/skills/flow/materialize.md` — document the invocation
- `tests/materialize-run-dir-anchoring.test.js` — worktree write pin
- `tests/hooks-gate-coverage.test.js` — carve-out pin

## Gotchas

- Evidence from run 2026-08-20T154424-spec-1071: `materialize.js` exit-2 refusal on the worktree-relative run dir, then the shadow guard refusing both `mkdir -p` and the Write tool on the same path; workaround was `node -e` fs calls (the guard is a tool-call text-shape heuristic).
- Cost: a ~4-tool-call detour plus a hand-move step every flow run pays silently.
