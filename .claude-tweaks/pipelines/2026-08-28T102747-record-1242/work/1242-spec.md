# 1242: hooks-dispatcher.test.js: run-dir fallback tests aren't isolated from real .claude-tweaks/pipelines/ state

**Related:** #1270

Surface: backend

## Current State

`tests/hooks-dispatcher.test.js`'s `record-worktree`/`close-run`/`record-pr`/`spec-status` tests (e.g. "record-worktree writes run-state, prints a confirmation line, and close-run marks clean") call `runHook([...], { cwd: project })` against a `tmpProject()` fixture and expect the hook's run-dir fallback resolution (no explicit `--run`) to only ever see that fixture's synthetic `.claude-tweaks/pipelines/2026-07-01T090000-spec-1` directory.

In practice, when a real, active pipeline run directory exists in the actual repo checkout under `.claude-tweaks/pipelines/` (e.g. a `/claude-tweaks:flow` run mid-flight, `run-state.json` status `active`, timestamp newer than the test fixture's `2026-07-01T090000`), these tests were observed to fail — the hook's "newest non-terminal run" fallback picked up the real run directory instead of the fixture, producing output like `claude-tweaks: worktree recorded for {real-run-id}` instead of the expected `2026-07-01T090000-spec-1`.

Observed live (prior session): 13/39 tests in this file failed in isolation (`node --test tests/hooks-dispatcher.test.js`) while this repo had a genuine active run directory (`.claude-tweaks/pipelines/2026-08-21T224609-record-257`, `run-state.json` status `active`) present from an in-flight `/claude-tweaks:flow #257 review,polish,wrap-up` run. That was re-verified at the time not to be the diff under review (a 2-file, prose-only change to `plugin/skills/build/{SKILL.md,plan-audit.md}` with no relation to `bin/hooks.js` or `bin/lib/hooks/run-dir-resolve.js`) — the same 13 tests were already exposed before any code edit landed that session, purely from that run directory's presence.

Re-run at shaping time, in this checkout, with several genuine non-terminal run directories present under `.claude-tweaks/pipelines/` (including `2026-08-22T004058-record-257`, `2026-08-22T003629-dispatch-standalone`, `2026-08-22T001057-record-817`): `node --test tests/hooks-dispatcher.test.js` passed 39/39. The failure did not reproduce against this checkout's current real-run-dir state — see Gotchas.

`tests/hooks-dispatcher.test.js`'s own `tmpProject()` already runs `git -C dir init -q` on the fixture directory (added under #790, so an explicit `--run` resolves under a real git checkout), which should anchor `worktree-detect.js`'s `mainCheckoutRoot()` to the fixture itself rather than walking up to the real repo. Three sibling files — `hooks-pre-tool-use.test.js`, `hooks-session-start.test.js`, `hooks-context.test.js` — each define their own same-named `tmpProject()` helper that does **not** `git init` the tmp directory at all; their isolation instead depends on `mainCheckoutRoot()` returning `null` for a `.git`-less tmp dir and `bin/lib/hooks/context.js`'s `iterRunDirsWithState`/`findNonCanonicalRunDirs` falling back to `root = wtDetect.mainCheckoutRoot(start) || start` — correct only as long as no ancestor directory between the tmp dir and the filesystem root happens to contain a `.git`, which is an environmental assumption rather than a structural guarantee.

- [ ] Audit the other three `tmpProject()` fixtures (`hooks-pre-tool-use.test.js`, `hooks-session-start.test.js`, `hooks-context.test.js`) for the same latent isolation gap, since a fix scoped only to `hooks-dispatcher.test.js` could leave siblings exposed to the identical failure mode under different environmental conditions.
- [ ] Fix the fixture/harness so these tests are hermetic regardless of what real pipeline run directories exist in the actual repo checkout at test-run time.

## Acceptance Criteria

## Technical Approach

Start by reproducing deterministically rather than assuming the original observation still holds: construct a controlled repro (a `tmpProject()` fixture plus a second, sibling real-looking `.claude-tweaks/pipelines/{later-timestamp}-record-N` directory with `run-state.json` status `active`, created directly in this repo's own checkout) and confirm the fallback actually crosses the boundary before changing anything. If it doesn't reproduce even under a constructed adversarial case, the isolation gap may already be closed (e.g. by #790's `git init` addition) and the remaining work is the sibling-fixture audit below plus hardening assertions, not a functional fix.

If it does reproduce: trace `bin/hooks.js`'s `record-worktree`/`close-run`/`record-pr` handlers' `process.cwd()` argument through `resolveRunArg` → `ctxLib.resolveRunDir`/`resolveRun` → `iterRunDirsWithState` → `wtDetect.mainCheckoutRoot()`, confirming at which point (if any) the tmp fixture's own `.git` fails to anchor `mainCheckoutRoot()` to itself instead of walking up past it. Candidate causes to check: whether `execFileSync`'s `cwd` option in the test's `runHook()` reliably becomes the child process's `process.cwd()` at the point `hooks.js` reads it; whether a fixture's `git init` can race the child process spawn; and whether an inherited environment variable (e.g. `GIT_DIR`) could redirect `git -C dir init` or a later `git rev-parse`-based check away from the fixture directory.

Once root-caused, harden all four `tmpProject()` fixtures the same way — either every fixture `git init`s its own tmp dir (matching `hooks-dispatcher.test.js`'s existing `#790` pattern) so isolation is structural rather than incidental, or the shared resolution path takes an explicit root override the tests can pass instead of relying on cwd-based anchoring at all.

### Key Files

- `tests/hooks-dispatcher.test.js` — the affected suite; its `tmpProject()`/`runHook()` fixture helpers
- `tests/hooks-pre-tool-use.test.js` — sibling `tmpProject()` helper, no `git init`
- `tests/hooks-session-start.test.js` — sibling `tmpProject()` helper, no `git init`
- `tests/hooks-context.test.js` — sibling `tmpProject()` helper, no `git init`
- `plugin/bin/lib/hooks/context.js` — `resolveRun`/`resolveRunDir`/`iterRunDirsWithState`/`findNonCanonicalRunDirs`, the "newest non-terminal run" fallback and its `mainCheckoutRoot(start) || start` anchoring
- `plugin/bin/lib/hooks/worktree-detect.js` — `mainCheckoutRoot()`, the pure-`fs`-based walk-up anchoring logic
- `plugin/bin/hooks.js` — `record-worktree`/`close-run`/`record-pr` command handlers, which pass `process.cwd()` into `resolveRunArg`/`ctxLib` calls

## Gotchas

- Re-running `node --test tests/hooks-dispatcher.test.js` at shaping time (2026-08-22), with several genuine non-terminal run directories present in this checkout's own `.claude-tweaks/pipelines/`, passed 39/39 — the originally reported 13/39 failure did not reproduce here (unvalidated — no controlled repro captured against this exact checkout state yet). Treat the original observation as needing re-confirmation via a deliberately constructed adversarial fixture before assuming a functional bug still exists, rather than building a fix on an unreproduced premise.
- `hooks-dispatcher.test.js`'s `tmpProject()` already `git init`s its fixture (`#790`), which should anchor `mainCheckoutRoot()` correctly; if the bug still reproduces under a controlled repro, the root cause is more subtle than "the fixture isn't a git repo" and needs the trace described in Technical Approach.
- This is a test-harness fix only — it must not weaken `mainCheckoutRoot()`/`resolveRun()`'s real (non-test) anchoring behavior, which existing production callers (`record-worktree`, `close-run`, session-start's stale-run report) depend on.
