# 1821: dispatch can re-select an issue that already has an open, pending-review PR from a prior run

## Current State

Dispatch (and/or `/build`'s worktree setup) does not appear to check for an existing open PR on a record before claiming and building it fresh, even when that PR's own run-marker shows it already reached `pending-review` under a prior run.

Observed on #1058: a run on 2026-08-28 (`2026-08-28T080617-record-1058`) completed build/test/review and reached `pending-review`, opening draft PR #1602 on branch `worktree-dispatch-record-1058` — then sat unmerged for about a week. A fresh dispatch run on 2026-09-04 (`2026-09-04T080101-record-1058`) claimed and rebuilt #1058 from scratch on a freshly created local branch with the SAME deterministic name, producing a second, fully-diverged commit history for the identical fix. `_shared/pr-early-run-lifecycle.md` documents a Step 1.6 "Remote-only stale branch check" that is supposed to catch a same-name branch left on origin by a prior attempt and stop for a human decision before `EnterWorktree` ever runs — but the 2026-09-04 run's build phase evidently never hit that stop (or it was bypassed), since it proceeded to materialize, build, and commit without incident.

Root cause not yet diagnosed — candidates: (a) the claim on #1058 was released once the 2026-08-28 run reached `pending-review` (per the documented "reconciler finishes armed/pending-review later" model), making the record eligible for dispatch selection again despite an open PR already existing for it; (b) `build/worktree-setup.md`'s Step 1.5/1.6 stale-branch checks have a gap that let a remote-only collision through; (c) dispatch's own selection query doesn't exclude records with an already-open PR.

## Deliverables

- Diagnose why the 2026-09-04 run's build phase did not stop at `pr-early-run-lifecycle.md` Step 1.6 (or equivalent) despite PR #1602 already existing on the same deterministic branch name.
- Either: (a) have dispatch's selection query skip records with an existing open PR (reuse it instead of reclaiming), or (b) fix the Step 1.6 stale-branch check gap that let this run past it, or both.

## Acceptance Criteria

- A record with an existing open PR from a prior run cannot be silently re-claimed and rebuilt from scratch on a colliding branch name; either the existing PR is reused/resumed, or a human is stopped for a decision before any new work is committed.
