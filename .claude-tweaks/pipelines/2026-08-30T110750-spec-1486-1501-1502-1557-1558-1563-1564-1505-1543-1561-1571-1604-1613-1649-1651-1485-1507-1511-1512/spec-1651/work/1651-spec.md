# worktree session Bash guard false-positives on the bare word "complete" in non-git commands

## Current State

In a worktree-isolated session, the Claude Code CLI harness's Bash-shape guard refuses any command whose text contains the literal token `complete`, pattern-matching it as an unverifiable git operation — even in commands with no git content at all. `_shared/scratch-worktree.md` Section 7 documents several other refusal shapes (2026-08-15, 2026-08-25 addenda) but not this one. `flow`'s per-spec completion transition (`spec-status --status complete`) hits this on every multi-spec run.

## Deliverables

- Add a dated addendum to Section 7 documenting the refusal shape, the confirmed workaround, and the concrete trigger site.
- Check whether `bin/hooks.js spec-status`'s callers can avoid the literal token without changing the CLI's public surface; apply the workaround at the call site if one exists.

## Acceptance Criteria

- Section 7 documents this refusal shape and workaround, in the same dated-addendum format as existing entries.
- Every in-repo call site passing `--status complete` as a literal argv token from a worktree session either avoids the token or is confirmed not to run there.
- `npm test` passes.

## Investigation Findings

**Reproduced live, today (2026-08-30).** `echo complete` alone — no git content whatsoever — is refused with: `"a worktree-isolated session... runs a string through complete, which can't be verified to stay inside the worktree... a worktree-isolated session's git operations must target its own worktree."` Confirms the record's premise exactly; this is the same false positive this session's own materialize/spec-status calls have hit repeatedly throughout this 19-record run (worked around each time via `["c","o","m","p","l","e","t","e"].join("")`).

**Addendum added** to `plugin/skills/_shared/scratch-worktree.md` Section 7, dated 2026-08-30, refs #1651 — documents the refusal, the confirmed reproduction, and the workaround (compose the token inside a single `node -e` expression, since a `;`-separated multi-statement composition at the outer shell level is itself refused per the pre-existing 2026-08-15 observation — the composition has to happen inside one JS expression via `child_process.execFileSync`, not as a sequence of shell statements).

**Call-site sweep.** Grepped the whole `plugin/` and `docs/` trees for `--status complete` as a literal argv token. Exactly one live invocation site exists: `plugin/skills/flow/multispec-progress-banner.md`'s "Per-spec completion summary" (the doc instructing `/flow`'s Step 4 to call `spec-status --status complete --phase wrap-up` at a spec's wrap-up exit under `MULTISPEC_REVIEW_DEFER=1`) — the exact trigger the record describes, hit once per spec on every multi-spec `/flow` run. Updated that call site to the `node -e` composition (using `process.env.CLAUDE_PLUGIN_ROOT`/`process.env.MULTISPEC_PARENT_DIR` instead of shell `${VAR}` expansion, so the whole call resolves inside one JS expression with no outer-shell variable substitution). The sibling `--status failed` call (HARD-GATE abort) is untouched — `failed` isn't a git-pattern-matched token, confirmed by every prior `--status running`/`--status failed` call in this session's own history passing cleanly. `multi-spec.md`'s three `status: complete` lines are YAML documentation of the manifest schema's possible enum values, not executable invocations — correctly left as literal prose.
