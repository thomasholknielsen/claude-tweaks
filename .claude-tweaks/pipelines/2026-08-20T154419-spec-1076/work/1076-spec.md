# 1076: flow multi-spec: per-spec boundary freshness check + batch-curation diff-basis generalization

Surface: backend

## Overview

Multi-spec `/flow` runs check origin freshness at worktree creation (`_shared/worktree-setup.md`'s post-creation catch-up, cited from `flow/multi-spec.md` Shared-worktree Step 1) and immediately before end-of-run finish (`multi-spec.md` Shared-worktree Step 3) — but never between spec boundaries. Observed failures: #856 (the v6.95.0 `plugin/` subtree cutover merged *cleanly* into an in-flight batch, invalidating the specs' assumed paths; caught only by an improvised KEPT-PROMPT) and batch #967–970 (135 commits of drift resolved only at PR-merge time, commit `9126efb7`, after four specs had built on the stale base).

This sub-issue adds the boundary check as a new `flow/` sibling file cited from the per-spec execution loop, and generalizes the batch-curation diff basis so boundary merges don't pollute the batch diff.

**Complexity:** Medium
**Estimated tasks:** 5 (4 deliverables plus the central full-suite verification)

## Non-Goals

- No mid-build re-checks inside a single long-running spec — the "sequence merge-then-suite, never the reverse" rule (`multi-spec.md` Shared-worktree Step 3) cuts against landing merges while a spec's verification is in flight; the boundary is the safe point.
- No change to single-spec `/flow` runs — creation-time catch-up plus the pre-finish re-check already bound their exposure.
- No wall-clock/threshold cadence machinery and no new policy lever — the check is unconditional at every boundary.
- No new `bin/` executable — this is skill prose; the check runs as agent-executed git commands like the rest of the worktree lifecycle it joins.
- No restating of `_shared/worktree-setup.md`'s fetch/merge, conflict-resolution, or fail-open machinery — cite it (its own Anti-patterns table forbids restating).
- No conformance-test pinning of the escalation gate's option-1 re-validation prose — the suite pins Acceptance Criteria 1–3's contract points; the re-validation flow is deliberately unpinned interactive prose.

## Technical Approach

The check runs at each spec boundary — spec 2..N, after spec N-1's pipeline completes (or fails, or is skipped under `MULTISPEC_KEEP_GOING` — the boundary check fires before every remaining spec regardless of the prior spec's outcome) and before spec N's per-spec scaffold:

1. `git fetch origin {integration-branch}` — `{integration-branch}` per `_shared/integration-branch.md`'s canonical ladder, never hardcoded. On fetch failure, **skip this boundary's check entirely** and log the distinct fail-open line per `_shared/worktree-setup.md`'s convention — never compute `BEHIND` against a stale ref, where a false zero would be indistinguishable from a genuine clean no-op.
2. `BEHIND=$(git rev-list --count HEAD..origin/{integration-branch})` — zero → silent no-op, nothing logged.
3. Behind: compute the **incoming file set** from `git diff --name-status HEAD...origin/{integration-branch}` (three-dot — incoming side only), where a rename entry (`R{score}\told\tnew`) contributes **both** its old and new path; and two comparison sets: **run-modified paths** = `git diff --name-only $(git merge-base HEAD origin/{integration-branch})..HEAD` (the merge-base isolates the run's own side even after an earlier boundary merge; no dependency on `manifest.yml`'s conditional `baseSha`), and **remaining specs' Key Files** (from Validation Step 3's pre-flight collection — specs N..last only, not completed ones). **Overlap formula:** `incoming ∩ (run-modified ∪ remaining-Key-Files) ≠ ∅` — exact-path equality after rename expansion, no prefix matching; either intersection alone escalates.
4. **No overlap** → `git merge origin/{integration-branch}`; on success, one `AUTO` entry in the **parent** run directory's `decisions.md` using `worktree-setup.md`'s entry format (before/after short shas, commit count). A conflict during this "trivial" merge → `git merge --abort` to restore the clean tree, then escalate — git overruled the heuristic, and the gate must open on a clean tree like the overlap path's.
5. **Overlap** → escalate *before* merging, so the decision point sees a clean tree in this path too.

Escalation (run-level HARD-GATE, `_shared/auto-mode-contract.md` structural-coupling class — fires even in `auto`; `MULTISPEC_KEEP_GOING` does not bypass it): `AskUserQuestion` with (1) *Merge + re-validate remaining specs' premises* (Recommended) — merge, check each remaining spec's Key Files and stated assumptions against the new tip, write one verdict line per remaining spec to the parent `decisions.md`, and when anything broke, surface it as a follow-up decision within this same open gate (fix the spec / skip it / stop the run) — no new stop class; (2) *Merge and continue as-is*; (3) *Stop the run* per `multispec-failure-handling.md` (completed specs' commits stay in the shared branch). A merge performed under option 1 or 2 that itself conflicts is resolved per `_shared/git-discipline.md`'s merge-conflict procedure (read both sides; the human is already present at the gate — never reset or discard). Logging is both-entries, not either-or: any merge that advances the branch writes the `worktree-setup.md`-format `AUTO` entry, and the gate resolution additionally writes its own entry per `_shared/auto-decision-log.md`'s schema.

## Gotchas

- Frame the escalation under `_shared/auto-mode-contract.md`'s *existing* structural-coupling HARD-GATE class — never as a new mid-flow stop category, which the contract forbids skills from inventing.
- `MULTISPEC_KEEP_GOING` skips past a failed *spec*; boundary drift invalidates every remaining spec equally — the non-bypass must be stated explicitly, not left to inference.
- The overlap test is a plain path-set intersection over git output — not `groupByFileOverlap` (`bin/lib/issues/grouping.js`), which is record-keyed and solves a different problem. But the Key Files *values* do come from `extractKeyFiles` via `bin/preflight-records.js` — confirm at build time that its `keyFiles` arrays are clean paths with bullet prose already stripped, and note in the new file if a strip step is needed.
- Derive run-modified paths from `git merge-base HEAD origin/{integration-branch}`, not `manifest.yml`'s `baseSha`: `baseSha` is only written under `MULTISPEC_CURATION_DEFER=1`, and after the first boundary merge it would count merged-in upstream files as "run-modified" (false-positive escalations).
- The #856 signature is rename-shaped: a structural cutover arrives as `R` entries whose *old* paths are what the in-flight specs' Key Files name — the rename-contributes-both-paths rule is precisely what makes the overlap test catch it. The worked example in the new file must trace this.
- `BEHIND` and the merge-base derivation assume the integration branch's history is append-only (no force-push) — the project's standing git discipline. A rewritten remote history surfaces as divergence/conflict at merge time rather than being silently mis-counted; the count is best-effort, not a proof.
- A no-op check writes nothing to `decisions.md` (log-only-when-changed, mirroring `worktree-setup.md` and the pre-flight verify sweep); a fetch failure is logged distinctly from a clean no-op — a reader must be able to tell "checked, clean" from "check didn't run."
- The interplay note on `/test` attribution: failures appearing after a boundary merge may come from merged upstream code — attribute against the drift-merge `decisions.md` entry, not the pre-flight sweep ledger, before re-diagnosing.
- Cite the new file from `multi-spec.md` with the sibling-file convention ("read `multispec-freshness.md` in this skill's directory…"); sibling files are not skill-graph nodes — add no edge to `docs/skill-graph.md`.
- Conformance greps: content-anchored and case-insensitive where sensible; prove each new assertion can go red by reverting the pinned edit (memory: count-mismatch greps are usually test bugs). `grep -c` counts lines, not occurrences — use `grep -o | wc -l` for exactly-once assertions.
- In command prose use `--end-of-options` (not `--`) with `rev-parse`/`merge-base` when an argument could be dash-led.
