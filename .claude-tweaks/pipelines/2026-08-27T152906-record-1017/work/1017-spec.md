# 1017: materialize.js worktree anchoring guard silently contradicts pipeline-run-dir.md's documented work/ design

Surface: backend

## Current State

`bin/materialize.js`'s `--run-dir` anchoring guard (added by #790/[IL-127], via `bin/lib/hooks/worktree-detect.js`'s `isAnchoredUnderRoot`) rejects ANY `--run-dir` whose nearest `.git` ancestor is a linked-worktree FILE rather than the main checkout's `.git` DIRECTORY — confirmed by `tests/materialize-run-dir-anchoring.test.js`'s "accept" case, which asserts the only accepted `--run-dir` is one anchored under the MAIN checkout even when cwd is inside a linked worktree.

This directly contradicts `plugin/skills/_shared/pipeline-run-dir.md`'s own Anchoring section, stated as settled design: "`work/{n}-spec.md` is the exception and stays inside the worktree. It is git-tracked and must be committed onto the feature branch; it reaches the main checkout by merge." No skill doc (`flow/materialize.md`, `flow/SKILL.md` Step 4.2, `build/SKILL.md` Common Step 1) documents how a real invocation reconciles this — none mention a bridge/copy step from the main-checkout write into the worktree.

Empirically (discovered while build+testing #758 from inside worktree `worktree-record-758`): invoking `bin/materialize.js` with `--run-dir` anchored at the worktree fails outright ("resolves outside the main checkout"); a plain `mkdir -p` of the same worktree-relative pipelines run-dir path is independently blocked by a SEPARATE guard, `checkPipelineShadowGuard` (`bin/lib/hooks/pre-tool-use.js`). The only way to actually get the materialized file onto the worktree's branch was an undocumented workaround: materialize into the main checkout (satisfying materialize.js's own guard), then plain `cp -r` the resulting directory into the worktree (bypasses `checkPipelineShadowGuard`, since `cp` isn't in its Edit/Write/Bash-mkdir pattern match), then `git add`+`git commit` inside the worktree, then manually delete the stray untracked copy left behind in the main checkout.

A prior successful materialize commit on `worktree-dispatch-record-841` (commit b812525b, 2026-08-20, landed after the anchoring guard) shows this same undocumented `cp` bridge is in fact how every worktree-mode `/flow`/`/build` run materializes its spec file today — nothing in the skill docs says so.

## Deliverables

- [ ] Either give `bin/materialize.js`'s anchoring guard an explicit carve-out for the `work/` subpath so it can write directly into a linked worktree's own checkout (matching `pipeline-run-dir.md`'s stated design, and closing the same class of gap `#959` already tracks for `checkPipelineShadowGuard`), OR update `flow/materialize.md`'s "When this runs" section (and `pipeline-run-dir.md`'s Anchoring section) to explicitly document the real main-checkout-write + `cp`-bridge + worktree-commit + stray-cleanup sequence as the sanctioned procedure.
- [ ] Whichever fix is chosen, add or update a test pinning the actual, correct end-to-end behavior for a worktree-mode materialize (not just the anchoring-rejection unit tests `tests/materialize-run-dir-anchoring.test.js` already has).

## Acceptance Criteria

1. A worktree-mode `/flow`/`/build` run's spec-file materialization step is either mechanically self-sufficient (no manual `cp` bridge needed) or explicitly documented step-by-step in `materialize.md`, and the two no longer disagree.
2. `docs/incident-log.md` gets an entry if the chosen fix confirms this was a live, silent gap in every worktree-mode build's materialize step since #790 landed (2026-08-17).

## Technical Approach

Start by deciding which of the two Deliverable paths to take: a code carve-out (teach the anchoring guard that a `work/` subpath under a linked worktree's own checkout is a valid target, not just the main checkout) or a documentation fix (state the `cp`-bridge sequence explicitly as the sanctioned procedure). The carve-out is the one that actually matches `pipeline-run-dir.md`'s stated design and removes the undocumented workaround; the doc-only path is cheaper but leaves the awkward bridge-and-cleanup sequence as permanent process. Cross-check `#959` (tracking the same class of gap for `checkPipelineShadowGuard`) before choosing, since a carve-out here may need a matching carve-out there to be internally consistent.

### Key Files

- `bin/materialize.js` — the `--run-dir` anchoring guard, if the carve-out path is chosen
- `bin/lib/hooks/worktree-detect.js` — `isAnchoredUnderRoot`, the function the guard calls
- `plugin/skills/flow/materialize.md` — "When this runs" section, if the documentation path is chosen (or in addition, to record the final decision either way)
- `plugin/skills/_shared/pipeline-run-dir.md` — Anchoring section, kept consistent with whichever path is chosen
- `tests/materialize-run-dir-anchoring.test.js` — existing anchoring-rejection tests; extend or add a worktree-mode end-to-end test

## Gotchas

- The undocumented `cp`-bridge workaround (main-checkout write → `cp -r` into worktree → `git add`/`commit` → delete the stray main-checkout copy) is, empirically, already how every worktree-mode build materializes its spec file today (see the `worktree-dispatch-record-841` commit cited above) — a code carve-out must not break that existing working path for any build already relying on it during the transition.
- `checkPipelineShadowGuard` (`bin/lib/hooks/pre-tool-use.js`) is a separate guard from the anchoring guard this record is about; `#959` tracks its own class of gap. Coordinate rather than duplicate if both need touching.
- This was filed as a blocking prerequisite discovered mid-build of #758, whose own diff does not touch `record.js`/`hooks.js`/`pre-tool-use.js`/`materialize.js` — treat this as an independent record, not part of #758's scope.
