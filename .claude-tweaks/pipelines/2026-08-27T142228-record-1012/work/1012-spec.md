# 1012: hooks.js mutating verbs: unknown-flag rejection, unambiguous-only implicit run resolution, composite ownership guard

Surface: backend

## Overview

Harden the five mutating run-state verbs in `plugin/bin/hooks.js` (`close-run`, `record-worktree`, `record-pr`, `spec-status`, `teardown-run`) against sibling-agent stomps: unknown-flag rejection, an unambiguous-only implicit fallback, and a write-time ownership guard built on `classifyOwnership` (prerequisite sub-issue). Extended under the #965 decomposition (see the parent record's Decision Rationale): the original remedy this record mandated — hard-require `--run` and remove the fallback — was considered and rejected during the #965 brainstorm in favor of unambiguous-only resolution, which keeps the one-session-one-run interactive case working while making a foreign stomp structurally impossible. This record's Deliverables and Acceptance Criteria below supersede the original ones.

## Original incidents (preserved)

- During a `/dispatch` firing, a Task-tool build/review subagent working on #860 omitted `--run` on one `record-worktree`/`close-run` call. The CLI fell through to its "newest non-terminal run" fallback and silently overwrote a LIVE sibling session's `run-state.json` (an unrelated, actively-in-use run for #758, different session, process still running) with `worktree:null`/`status:clean`/the wrong `sessionId`. The corruption was recovered manually; the original `sessionId` could not be recovered.
- #965 (2026-08-19/20): a mistyped `close-run --help` — not a known flag, silently ignored by `resolveRunArg` — fell through to the same fallback and overwrote spec-315's run-state three separate times, from three different sibling worktrees. All three siblings shared the parent session's `CLAUDE_CODE_SESSION_ID` (measured 2026-08-20), so `closeRunState`'s session-id-only foreign check read the victim run as "mine".

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- No change to `pre-tool-use.js` E-checks or `resolveRun`'s attribution — that is the enforcement-layer sibling sub-issue.
- No change to explicit-`--run` semantics: an explicit `--run` on a foreign run still proceeds with the advisory line (console execution and post-merge settlement depend on this override).
- No change to read-only verbs (`resolve-run-dir`, `reconcile`, `archive-run`'s own validation, etc.) beyond what the shared `resolveRunArg` seam carries.
- No removal of the implicit fallback for the genuinely unambiguous case — that rejection is recorded in the parent's Decision Rationale.

## Current State

- `plugin/bin/hooks.js` — `resolveRunArg(args, cwd, env)` (shared by all five verbs): looks only for `--run`; anything else silently falls through to `ctxLib.resolveRunDir(cwd, env)` — called WITHOUT a sessionId third argument, so resolution is the pre-#62 "newest non-terminal run" guess. `record-worktree` (writes `worktree`/`status`/`sessionId`), `record-pr`, and `spec-status` have no ownership check at all on the implicit path.
- `plugin/bin/lib/hooks/close-run-state.js` — `closeRunState(runDir, { explicit, sessionId })`: refuses an implicit close only when `prev.sessionId !== sessionId` — defeated by the shared session id. Also consumed by `teardown-run` (`teardown-run.js` passes `opts.sessionId` through).
- `plugin/bin/lib/hooks/context.js` — `resolveRun`'s env-first (`PIPELINE_RUN_DIR`) resolution; `findRunByWorktreePath`; `classifyOwnership` (from the prerequisite sub-issue): composite identity — a run's owner is `{ sessionId, worktree binding }`, a caller is `{ CLAUDE_CODE_SESSION_ID, cwd }` — returning exactly one of `'mine' | 'foreign' | 'indeterminate'`; `foreign` means provably another actor's (different session id, or same/missing id with the caller's cwd in a different live worktree than the recorded binding). The prerequisite's Data / API Surface table is the verdict contract; verify the shipped signature matches it at build start. A run with **no** worktree binding classifies `indeterminate` (or `mine` from the main checkout with equal ids) — never `foreign` — which is what makes the fail-open asymmetry below work.
- Tests: `tests/hooks-dispatcher.test.js` covers these verbs' current fallback behavior (its no-`--run` cases are also non-hermetic against an inherited `PIPELINE_RUN_DIR` — #1038).

## Deliverables

- [ ] Known-flag declaration per verb at the `resolveRunArg` seam: any `--*` argument not in the verb's declared set prints that verb's one-line usage and exits without reading or writing any run state. `close-run --help` must become a usage printout. The declared sets (source of truth: a `KNOWN_FLAGS` table in `plugin/bin/hooks.js` beside the handlers, consumed by `resolveRunArg`): `close-run`: `--run`; `record-worktree`: `--run`; `record-pr`: `--run`; `spec-status`: `--run`, `--spec`, `--status`, `--phase`, `--now`; `teardown-run`: `--run`, `--merged`, `--abandoned`.
- [ ] Implicit resolution (no `--run`) for the five mutating verbs replaced with the unambiguous-only order: (1) `PIPELINE_RUN_DIR` env — kept first, but no longer exempt from the write-time guard below (an *inherited* env var reaching a foreign run is a documented pollution vector, #1038; only explicit `--run` overrides a `foreign` verdict); (2) cwd-binding reverse lookup via `findRunByWorktreePath` on the caller's cwd — a hit is the caller's own run even with N siblings live; (3) after excluding candidates whose `classifyOwnership` verdict is `foreign` (verdicts `mine` and `indeterminate` both remain actionable — an unbound run may still be the caller's, the fail-open asymmetry), exactly one candidate remains → act on it; (4) otherwise refuse, listing **every** non-terminal candidate — foreign ones included, annotated `(recorded by another session/worktree)` so the operator sees why they were excluded — each as a paste-ready `node "<plugin>/bin/hooks.js" <verb> --run "<dir>"` line.
- [ ] `closeRunState`'s `foreignOwner` predicate upgraded from the raw session-id comparison to `classifyOwnership` (implicit and env-resolved paths refuse on `foreign`; explicit `--run` proceeds with the existing advisory). Signature: `closeRunState(runDir, { explicit, callerIdentity })` with `callerIdentity = { sessionId, cwd }` replacing the bare `sessionId` option — exact option naming at implementer's discretion, but both callers (hooks.js `close-run`, `teardown-run.js` Step 1) must thread cwd through.
- [ ] `record-worktree`, `record-pr`, and `spec-status` refuse an implicit write when the resolved run's `classifyOwnership` verdict is `foreign`, with the same refusal shape (message naming the run, its owner evidence, and the paste-ready explicit command).
- [ ] Named regression test, fixture pinned exactly: **four** non-terminal run dirs; callers A, B, C each cwd'd in their own worktree with their own run bound to it; run D bound to a fourth worktree whose agent is absent; all four runs record the same `sessionId`. Each caller invokes `close-run --help` (must hit the unknown-flag usage path — zero state reads/writes) and bare `close-run` (must hit resolution step 2, its own cwd-bound run). Assertions: run D's `run-state.json` ends byte-identical in every case; each caller's bare `close-run` closes only its own run. **Unbound-caller variant** (the #860/#758 incident shape, where the stray caller may have had no bound run): a fourth same-session caller cwd'd in a worktree with no bound run invokes bare `close-run` — step 2 misses, step 3 excludes A/B/C/D as `foreign` → zero candidates remain → refusal (exercising step 4), and no run-state file changes. All spawns clear `PIPELINE_RUN_DIR` explicitly (the #1038 hermeticity fix applied to these new cases from the start).
- [ ] Update `tests/hooks-dispatcher.test.js`'s existing no-`--run` cases to the new semantics, clearing `PIPELINE_RUN_DIR` in every spawn env.

## Acceptance Criteria

1. Each of the five verbs, given any undeclared `--*` flag (`--help`, a typo), prints usage and performs zero reads/writes of any `run-state.json` — asserted by fixture-file mtime/content equality.
2. Bare `close-run` with exactly one non-terminal candidate remaining after the foreign-exclusion filter acts on it (current interactive behavior preserved; one foreign + one non-foreign candidate therefore acts on the non-foreign survivor); with two or more surviving candidates, or with zero survivors (every candidate foreign, or none at all), it refuses and the refusal output contains one `--run` command line per non-terminal candidate, foreign ones annotated.
3. A caller whose cwd is inside worktree A can never implicitly resolve, close, or overwrite a run bound to worktree B, even with identical `CLAUDE_CODE_SESSION_ID` — the named regression test above proves the incident shape is dead.
4. Explicit `--run` on a foreign run still proceeds, printing the existing advisory (`closing run … recorded by another session`) — byte-compatible with today's message.
5. `record-worktree --run <dir> <path>` (the sanctioned, documented call shape) behaves byte-identically to today.
6. Bare `record-worktree <path>` (no `--run`) with two or more non-terminal runs present, or with its only candidate classified `foreign`, refuses without writing — the verb that creates bindings has no cwd-binding step-2 hit for a first-time record (its target is unbound at call time), so only `PIPELINE_RUN_DIR` or the single-surviving-candidate rule can resolve it; this AC pins that carve-out so a future edit to the shared resolution order can't silently regress it.
7. Full `npm test` green; reverting the hooks.js/close-run-state.js changes (keeping the new tests) makes the new tests fail.

## Technical Approach

Extend `resolveRunArg` to take the verb's known-flag list and return an `unknownFlag` field the caller turns into the usage line; thread a `callerIdentity = { sessionId: process.env.CLAUDE_CODE_SESSION_ID, cwd: process.cwd() }` object into the implicit-resolution path and the write guards. The unambiguous-only candidate scan reuses `iterRunDirsWithState` (newest-first) exactly as `resolveRun` does — do not build a second run-dir enumerator. `record-worktree` note: it *creates* the binding, so at call time its target has none — implicit resolution for it can only succeed via `PIPELINE_RUN_DIR` or the single-non-foreign-candidate rule; with siblings live it refuses, which makes the already-documented "always pass `--run`" discipline structural instead of prose.

### Data / API Surface

- `resolveRunArg(args, cwd, env, { knownFlags, callerIdentity })` → `{ runDir, invalidRunArg, unknownFlag, rest, explicit, candidates }` (exact shape at implementer's discretion; `candidates` non-empty only on the refusal path).
- Refusal message shape: a lead line whose wording is chosen by cause — `claude-tweaks: multiple candidate runs — pass --run explicitly:` when 2+ survive the filter, `claude-tweaks: the only candidate run(s) are recorded by another session/worktree — pass --run explicitly to act on one:` when zero survive — followed by one `node "<plugin>/bin/hooks.js" <verb> --run "<dir>"` line per non-terminal candidate (foreign ones annotated `(recorded by another session/worktree)`). Never the literal string "multiple/foreign".

### Key Files

- `plugin/bin/hooks.js` — `resolveRunArg` + the five verb handlers
- `plugin/bin/lib/hooks/close-run-state.js` — guard upgrade
- `plugin/bin/lib/hooks/context.js` — read-only consumption of `classifyOwnership`/`findRunByWorktreePath`
- `tests/hooks-dispatcher.test.js` — updated cases + the named regression test (or a sibling file if it grows past taste)

## Gotchas

- The shared session id means the old guard *passes* for siblings — any test asserting foreign-refusal must use identical session ids across callers to prove the new arm, plus a distinct-id case to prove the old arm still works.
- `spec-status`'s `--run` names the multi-spec PARENT run dir (where `manifest.yml` lives), never a per-spec subdirectory — the guard must classify against the parent dir's own run-state without breaking that contract.
- `teardown-run` reaches `closeRunState` via `teardown-run.js` Step 1 — verify both entry points get the upgraded guard (one implementation, two callers).
- `mv -n`-style silent-skip lesson applies to refusals: a refusal must exit with output naming what was refused and why — never print nothing and exit 0 (the pre-existing "printed nothing, indistinguishable from success" branches in these handlers were added for exactly this reason; extend them, don't regress them).
- #953 and #761 (open) also touch `plugin/bin/hooks.js`; #457 touches `tests/hooks-dispatcher.test.js` — check for merge overlap before building.
