# 1060: materialize.js writes work/{n}-spec.md into the main checkout instead of the invoking worktree

Surface: backend

## Current State

Discovered live during a /dispatch build for #844. `bin/materialize.js`'s `--run-dir` anchoring guard forces the run-dir argument to resolve under the main checkout, so it wrote `work/844-spec.md` into the **main checkout** instead of the group's linked worktree — contradicting `_shared/pipeline-run-dir.md`'s explicit rule that `work/{n}-spec.md` is the one exception that stays inside the worktree (it's git-tracked and must be committed onto the feature branch, reaching main only via merge). Caught via a stray untracked file showing up in the main checkout's `git status`; worked around by hand (moved the file into the worktree, deleted the main-checkout copy, committed it as the branch's first commit).

This is the mirror-image gap to #1068/#1103/#1122's "worktree-first ordering is unreachable" class: those describe the shadow guard refusing writes *into* a worktree; this describes `materialize.js` writing to the *wrong* location (main checkout) instead when a worktree already exists for the dispatch group.

## Deliverables

- Audit `bin/materialize.js`'s run-dir/worktree resolution so `work/{n}-spec.md` lands in the invoking worktree (per the documented exception), not the main checkout, while keeping the anchoring guard's protection against a run dir resolving inside a worktree for everything else.

## Acceptance Criteria

- A `/dispatch` build targeting an already-created worktree writes `work/{n}-spec.md` into that worktree, not the main checkout.
- The anchoring guard's protection against other run-dir paths resolving inside a worktree remains intact.
- No stray untracked `work/{n}-spec.md` appears in the main checkout's `git status` after a dispatch build.

## Technical Approach

`materialize.js`'s anchoring check needs a narrow exception mirroring the one #1068 investigates for the pipeline-shadow guard: when the caller is writing specifically `work/{n}-spec.md` and a worktree already exists for the invoking dispatch group, resolve the write target to that worktree's own run-dir path instead of forcing the main-checkout path. Check #1068's resolution first — the two records may share a fix (one mechanism governing both directions of the worktree-vs-main-checkout `work/` write).

### Key Files

- `plugin/bin/materialize.js` — the `--run-dir` anchoring guard forcing the main-checkout path
- `plugin/skills/_shared/pipeline-run-dir.md` — the documented `work/{n}-spec.md` worktree exception this violates

## Gotchas

- Coordinate with #1068/#1103/#1122's fix — all four records touch the same `work/{n}-spec.md` anchoring mechanism from different angles (worktree-write-refused vs. wrong-location-write); a shared fix is more likely correct than four independent ones.
- Don't weaken the anchoring guard's general protection while adding this exception — it exists specifically to stop other run-dir paths from resolving inside a worktree.
